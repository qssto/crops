# 05 线上质量闭环

本章描述 P2 阶段 worker 进程里的线上质量任务，以及配套的三组 HTTP 接口。worker 每天汇总上一天的可信度指标并出日报，把判分不确定的建议卡送进评测库给专家复核，每周汇总负向信号出归因周报，再把有问题的线上运行脱敏成评测样本草稿。
用户反馈接口为周报提供差评信号，专家评审接口把专家分写回业务库，问题处置接口让平台管理员更新周报里的问题状态。
另有两个清理任务，分别按保留期删除规则影子比对行和知识加载明细。
本章所有后台任务都只在 `cmd/worker` 中运行，HTTP 接口挂在 `cmd/server` 上。

## 共用机制

本章的后台任务都用同一种 Redis 互斥锁防止多副本重复执行，下文各节只写锁键和差异。

- 锁键为 `as:{env}:lock:p2job:{job}`，`{job}` 是任务名。锁由 `internal/repository/lock.go` 的 `Locker.AcquireLease` 获取：用 `SET key {随机 token} NX PX 10min` 写入（TTL 为 `LockP2JobTTL`，10 分钟），不阻塞等待。
- 锁已被持有时返回 `ErrLockHeld`，任务把这一轮当作跳过处理，不算出错。
- 持锁期间每处理完一个单位（一个农场、一张卡或一批行）就续期一次，续期用 Lua 脚本比对 token 后重设 TTL。token 不匹配时续期返回 `ErrLockLost`，任务立即停止本轮。
- 本轮结束时用不随请求取消的上下文释放锁，释放同样比对 token，只删除自己持有的锁。
- 各任务的周期循环都是「启动后立即执行一轮，之后每个周期执行一轮」。单轮出错只写一条 warn 或 error 日志，不退出循环，下个周期重试。

## 功能说明

### P2 后台任务登记

- 入口：worker 启动时 `internal/app/worker.go` 的 `App.WorkerLoops` 调用 `internal/app/worker_p2.go` 的 `App.p2WorkerLoops`，后者调用 `buildP2Loops`。
- 前置条件：各功能文件在包初始化时调用 `registerP2Loops(层号, 构造函数)` 登记。同包 init 按文件名顺序执行，登记顺序固定为 P2-L8（`attribution_l8.go`）、P2-L5（`kb_load.go`）、P2-L3（`quality.go`）、P2-L2b（`review_l2b.go`）、P2-L4（`rule_offload.go`）。
- 执行步骤：
  1. `buildP2Loops` 依次检查登记项：层号重复、构造函数为空时直接报错。
  2. 逐项调用构造函数。构造函数返回空列表且无错误时，表示依赖未装配或功能未启用，不起任务；返回错误时 worker 启动失败。
  3. 检查每个任务的名字非空、`Run` 非空、任务名在所有 P2 任务中不重复，否则报错。
  4. `WorkerLoops` 把 P2 任务追加在 outbox、扫描、分区、开关、积压、工单运维等 P1 任务之后，`StartLoops` 为每个任务起一个 goroutine。
- 结果与失败：全部启用时登记出的任务依次为 `attribution-weekly`、`backflow-collect`、`kb-load-retention`、`quality-daily`、`online-judge-review-enqueue`、`rule-shadow-purge`。其中 `attribution-weekly` 与 `backflow-collect` 来自同一个构造函数。
- 注：`worker_p2.go` 文件头注释写的是 L3 登记 `quality-metric-rollup / online-judge-sample` 两个任务，且只列了 L3、L4、L5；代码实际是 L3 只登记一个任务 `quality-daily`，那两个名字只是它内部两把锁的 job 名，另外 L2b 和 L8 也在这里登记。`worker.go` 中调用处的注释同样只写了 L3 / L4 / L5。

### 可信度日报

- 入口：worker 任务 `quality-daily`，周期为 `quality.interval`（缺省 1 小时）。构造在 `internal/app/quality.go` 的 `buildQualityLoops` 与 `App.qualityJob`，执行在 `internal/service/quality/job.go` 的 `Job.Run`、`Job.Tick`、`Job.RunOnce`。
- 前置条件：
  - `quality.enabled` 为 true，否则不起任务（缺省 false）。启用后缺对象存储、桶、知识库或模型配置任一项，返回 `ErrQualityDeps`，worker 启动失败。
  - `quality.judge_tier`（缺省 standard）必须是已配置的模型档位，否则启动失败。
  - 判分器从 `quality.judges_dir`（缺省 `eval/judges`，相对仓库根目录）加载事实一致性维度的提示词、判分器版本和录制回放。判分器只回放录制结果，没有录制的卡判为 UNKNOWN。
  - 推送渠道是 `RecordingNotifier`，只写日志，钉钉渠道未接入。
- 执行步骤：
  1. `Tick` 按 `quality.report_timezone`（缺省 Asia/Shanghai）算出昨天的日期，读 MinIO 桶 agri-steward-eval 下的 `report/daily/{yyyymmdd}.sent.json`。若标记已存在则本轮结束；若读取出错则返回错误，下个周期重试；否则调用 `RunOnce`。
  2. `farmDays` 执行 `SELECT tenant_id, farm_id, timezone FROM farm_profile` 列出所有农场。时区非法的农场写日志后跳过。每个农场按自己的时区取「昨天」，换算成 UTC 的起止时间窗口。
  3. 在锁 `lock:p2job:online-judge-sample` 下逐农场抽样判分，见[日报抽样与判分](#日报抽样与判分)。若锁被持有则本轮结束，不出日报。
  4. 在锁 `lock:p2job:quality-metric-rollup` 下汇总指标，见[日报指标汇总](#日报指标汇总)。若锁被持有则本轮结束。
  5. 仍在第 4 步的锁内生成并推送日报，见[日报生成与推送](#日报生成与推送)。
- 结果与失败：本任务不写 run_event、audit_log 或 outbox。数据库或对象存储出错时本轮返回错误，sent 标记未写，下个周期整轮重跑；指标写入都是 upsert，重跑结果相同。
- 注：`internal/service/quality/notify.go` 的注释写的是专家回写「暂无入口」；代码实际已由专家评审提交接口回写，见[在线判分回写](#在线判分回写)。

#### 日报抽样与判分

由 `internal/service/quality/sample.go` 的 `Sampler.Sample` 逐农场执行。若未装配 Sampler，所有农场都记为「未判」。

1. 读 online_judge_result 中本农场、本日、事实一致性维度的结果，只把当前判分器版本的行当作已判。
2. 执行 `SELECT DISTINCT category FROM advice_card WHERE outcome='ADVICE'`（限本农场和时间窗口）取当天出现过的问题类别。
3. 每个类别按 `ORDER BY CRC32(CONCAT(id, salt)) LIMIT 配额` 抽卡，配额为 `quality.sample_per_category`（缺省 5），salt 为 `quality.salt`（缺省 p2l3），同一天重跑抽到的卡相同。
4. 对每张抽中的卡：若已判则只计数；若本农场本日判分器已不可用则跳过；否则逐张判分：
   1. 读建议卡。若卡有引用，从 agent_run.knowledge_ref 取知识快照并打开，作为判分材料。
   2. 先取主链路共用的模型令牌 `rl:model:{tier}`（速率为档位每分钟限额），再取 `rl:judge:{tier}`（速率为 `quality.judge_qpm`，缺省 6）。判分令牌取不到时退还模型令牌，等一个判分令牌补充间隔后再试，最多等 3 次，仍取不到则把判分器记为不可用。
   3. 调用判分器。判分器报错同样记为不可用，本农场本日剩余的卡都不再判，记为「未判」，不返回错误。
   4. 判分结果格式校验失败时分数置空（UNKNOWN）。分数为空或等于 1 时状态记 NEED_EXPERT，否则记 SCORED。
   5. 写 online_judge_result，冲突时 `ON DUPLICATE KEY UPDATE id=id`（已有行不改），row_ver 为 0。
5. 每判完一张卡续期一次锁。读库或读知识出错时返回错误，本轮结束。

#### 日报指标汇总

由 `internal/service/quality/job.go` 的 `Job.rollup` 调用 `internal/service/quality/rollup.go` 的 `Rollup.Farm` 与 `Rollup.Platform`，指标写入 quality_metric_daily。

1. 逐农场执行 `Rollup.Farm`，每个农场完成后续期一次锁：
   1. 按 outcome、refuse_reason、degraded 分组统计窗口内的 advice_card，得到总数、建议数、拒答数、校验失败数（refuse_reason 为 VALIDATION_FAILED）和降级数。
   2. 若建议数大于 0，再统计「每个结论字段都在 advice_citation 中有引用」的建议卡数。
   3. 统计本农场本日当前判分器版本的判分结果。专家已复核（status 为 REVIEWED 且有专家分）时取专家分，否则取判分器分，得到已判数、满分（3 分）数和 UNKNOWN 数。
   4. 判定事实一致性状态：本农场在抽样步骤中被记为「未判」时为 UNJUDGED；没有样本时为 NO_SAMPLE；UNKNOWN 占比超过 10% 时为 UNDETERMINABLE；否则为 OK。
   5. 生成四项指标：引用覆盖率为有引用卡数除以建议数；数值准确率为建议数除以建议数与校验失败数之和；拒答率为拒答数除以总数；事实一致性只在状态为 OK 时生成，值为满分数除以已判数，并标为估计值。每项带 Wilson 置信区间，保留 5 位小数，slice_key 为 all，source 为 ONLINE。分母为 0 的指标不写。
   6. 以 `ON DUPLICATE KEY UPDATE` 写入 quality_metric_daily 的农场行。
2. 读离线评测结果：读 MinIO 的 `nightly/latest.json` 找到最新实验，再读 `{experiment_id}/metrics.json`。任一对象不存在时离线状态为 NO_DATA；实验被作废时为 VOID，日报显示「本期作废」。
3. 对每个涉及的业务日期执行 `Rollup.Platform`，写平台行（tenant_id=0、farm_id=0）：
   1. 对当日所有农场的 ONLINE、slice_key=all 行分别求分子与分母之和（跳过分子分母都为 0 的行），得到前三项平台指标。
   2. 事实一致性不由农场行相加，而是在平台范围重新统计判分结果，只在状态为 OK 时写入。
   3. 只有日报日期一并写入离线指标行：仅取离线状态为 OK 的指标，source 为 OFFLINE，带 experiment_id。
   4. 平台行同样以 upsert 写入 quality_metric_daily。

#### 日报生成与推送

由 `internal/service/quality/job.go` 的 `Job.report` 执行，仍持有 `lock:p2job:quality-metric-rollup`。

1. 若配置了 `quality.baseline_experiment_id`（缺省 0 表示无基线），读该实验的 metrics.json 作为对比基线。基线不存在时写一条 warn 日志，对比列显示「—」。
2. 读 quality_metric_daily 中日报日期的平台行。
3. 每项指标最多取 5 个 run 作为下钻样例：引用覆盖率取无引用的卡，数值准确率取校验失败的卡，拒答率取拒答的卡，事实一致性取状态为 NEED_EXPERT 的判分结果。
4. 渲染 HTML，以 text/html 写入 MinIO 的 `report/daily/{yyyymmdd}.html`。
5. 在锁内再读一次 sent 标记。若已存在则只重写报告、不再推送；否则生成标题「可信度日报 {日期}」的摘要并推送。
6. 推送后写 `report/daily/{yyyymmdd}.sent.json`，内容为日期、报告路径和发送时间。若标记写失败，本轮返回错误，下个周期整轮重跑并再次推送，即至少推送一次。

### 专家评审入队

- 入口：worker 任务 `online-judge-review-enqueue`，周期为 `eval_review.enqueue_interval`（缺省 1 小时）。构造在 `internal/app/review_l2b.go` 的 `reviewLoops`，执行在 `internal/service/review_enqueue_l2b.go` 的 `ReviewEnqueue.Run` 与 `ReviewEnqueue.Tick`。
- 前置条件：
  - `eval_review.enabled` 为 true，否则不起任务。启用后缺业务库、锁、Redis 或评测库连接任一项，返回 `ErrEvalReviewDeps`，worker 启动失败。
  - 评测库连接由 `OpenEvalReview` 单独打开：账号口令只从环境变量或密钥取，缺省库名 agri_eval，最大连接数 4。该账号只有 review_task 的查询、插入、更新权限和 trial 的查询权限。
  - 每页条数为 `eval_review.enqueue_batch`（缺省 200，上限 1000）。
- 执行步骤：
  1. 获取锁 `lock:p2job:online-judge-review-enqueue`。若锁被持有则本轮返回 0，不报错。
  2. 执行 `SELECT tenant_id, farm_id, timezone FROM farm_profile` 列出所有农场。
  3. 逐农场处理，每个农场完成后续期一次锁。续期失败时停止本轮。单个农场的处理如下：
     1. 读 Redis 游标 `cursor:review_enqueue:{tenant_id}:{farm_id}`，键不存在时从 0 开始。
     2. 每页查询业务库 online_judge_result 中 `status='NEED_EXPERT' AND id > 游标 ORDER BY id LIMIT 每页条数` 的行，最多翻 50 页。
     3. 每行生成一个评审任务：task_type 为 ONLINE_JUDGE，draft_ref 为 `ojr:{tenant_id}:{farm_id}:{结果 id}`，带维度、判分器版本、判分器分，评审人序号为 1。
     4. 在评测库的一个事务内按每 500 行一组写入 review_task，冲突时 `ON DUPLICATE KEY UPDATE id=id`。去重键 ref_key 是任务类型、实验、样本、序号、维度、draft_ref、评审人序号拼接后的 md5，同一判分结果重复入队不会产生新任务。
     5. 某页为空或不满一页时删除游标，下一轮从头扫描。翻满 50 页仍未扫完时，把最后一行的 id 写入游标，TTL 为 7 天。
- 结果与失败：本任务不写审计。写评测库出错时本轮返回错误，游标不前移，下个周期从原位置重试；重复入队由 ref_key 去重。已复核（REVIEWED）的结果不再满足查询条件，不会再入队。
- 补充：代码里没有评审任务的超时回收，专家领取后不提交的任务一直停在 ASSIGNED（`docs/dev-log.md` 记为待办）。

### 评审任务列表

- 入口：GET `/api/v1/admin/review-tasks`，查询参数 task_type、status、page、page_size。路由在 `internal/controller/review_l2b.go` 的 `MountReviewAdmin` 与 `ReviewListHandler`，业务在 `internal/service/review_l2b.go` 的 `ReviewService.List`，读库在 `internal/repository/eval_review.go` 的 `EvalReviewRepo.ListReviewTasks`。
- 前置条件：
  - 中间件依次为 `RequestID`、`PlatformAuth`（解析平台 Scope）、`RequireOps(review.read)`。权限矩阵里 review.read 只授给 kb_expert，不通过时记一条拒绝审计并返回 403 ROLE_INSUFFICIENT。
  - 服务层再检查调用人：必须是平台身份（tenant 0、farm 0）、用户 ID 非 0、角色含 kb_expert，否则 403 ROLE_INSUFFICIENT。
  - 若 `eval_review.enabled` 为 false，路由照常挂载、鉴权照常执行，之后返回 503 EVAL_REVIEW_DISABLED。
- 执行步骤：
  1. page、page_size 不是整数时返回 400。page 缺省 1，上限 1,000,000；page_size 缺省 20，范围 1 到 100。task_type、status 取值非法时返回 400。
  2. 在评测库执行 COUNT，再按 `ORDER BY id LIMIT OFFSET` 取一页 review_task。status 为空时只查 OPEN 和 ASSIGNED。
  3. 查询时同时判定每个任务是否属于 holdout：任务带实验或样本、但找不到对应 trial 时也按 holdout 处理。
  4. 每个任务按盲评视图返回：不返回判分器分；专家分只在任务属于本人时返回；holdout 任务不返回评审材料；ONLINE_JUDGE 任务的材料里附带解析后的目标（农场与判分结果 id）。
- 结果与失败：成功返回 200，内容为 items、total、page、page_size。只读，不写审计。评测库出错返回 500。

### 评审任务详情

- 入口：GET `/api/v1/admin/review-tasks/:id`。路由在 `internal/controller/review_l2b.go` 的 `ReviewGetHandler`，业务在 `internal/service/review_l2b.go` 的 `ReviewService.Get`。
- 前置条件：中间件、身份检查和关闭时的 503 与[评审任务列表](#评审任务列表)相同（需要 review.read）。
- 执行步骤：
  1. 路径 id 不是正整数时返回 400 bad id。
  2. 从评测库读 review_task 并判定是否属于 holdout，规则同列表。任务不存在时返回 404。
  3. 按盲评视图生成返回内容，规则同列表。
  4. 若任务不属于 holdout 且有评审材料，再查 trial 表取该任务对应试验的 suite、sample_version、status，条件中排除 `suite = 'holdout'`；任务没挂实验、样本或试验序号时不查。查到则附在材料里。
- 结果与失败：成功返回 200。holdout 任务只返回 ID 和状态类字段。只读，不写审计。

### 评审提交

- 入口：POST `/api/v1/admin/review-tasks/:id/submit`。路由在 `internal/controller/review_l2b.go` 的 `ReviewSubmitHandler`，业务在 `internal/service/review_l2b.go` 的 `ReviewService.Submit`，评测库读写在 `internal/repository/eval_review.go` 的 `EvalReviewRepo`。
- 前置条件：中间件依次为 `RequestID`、`PlatformAuth`、`RequireOps(review.submit)`，review.submit 只授给 kb_expert。服务层身份检查和关闭时的 503 与列表相同。
- 执行步骤：
  1. 路径 id 不是正整数时返回 400。请求体最多读 20KB（expect 上限 16KB 加 4KB 余量），按严格模式解码：有未知字段、尾随内容或超长时返回 400 bad body。
  2. 从评测库读 review_task。不存在时返回 404。
  3. 校验提交内容（不访问数据库）：
     - 打分类任务只要求分数在 1 到 3 之间。
     - BACKFLOW_EXPECT 任务不收分数。decision 为 MERGE 时 expect 必须是非空对象且不超过 16KB；为 DROP 时 reason 必填、不超过 512 字，且不能带 expect。
     - 校验不通过时返回 400 REVIEW_SUBMIT_INVALID。
     - ONLINE_JUDGE 任务解析 draft_ref 得到租户、农场和判分结果 id。解析失败说明入队数据损坏，返回 500。
     - BACKFLOW_EXPECT 任务要求 draft_ref 匹配 `^[A-Za-z0-9_-]{1,128}$`，否则返回 500。expect 解码后重新编码为键排序的紧凑 JSON。expect 的任一键或值、或 reason 经脱敏后发生变化，即判为含个人信息，返回 400 REVIEW_PII。分数置空。
  4. 在评测库事务中领取任务：
     1. 读任务，再按 ref_key 以 id 顺序 `SELECT ... FOR UPDATE` 锁住第一评审人和第二评审人两行。
     2. 若另一评审人的行已分给本人，返回冲突（同一专家不能双标）。本行必须是 OPEN（未分配或分给本人），或是本人持有的 ASSIGNED、DONE，否则返回冲突。
     3. 若本行是本人已完成的 DONE，重读后标记为已完成。若是 OPEN，则 `UPDATE ... SET assignee_id=本人, status='ASSIGNED' WHERE status='OPEN'`。
  5. 若任务已由本人完成，则判断是否原样重放：打分类任务比较分数，BACKFLOW_EXPECT 重读 MinIO 中的结论比较。内容一致则跳到第 8 步并标记为重放，否则返回 409 REVIEW_CONFLICT。
  6. 若任务未完成，执行副作用：
     - ONLINE_JUDGE 回写业务库，见[在线判分回写](#在线判分回写)。
     - BACKFLOW_EXPECT 写结论对象，见[回流期望写入](#回流期望写入)。
     - 其他任务类型没有副作用。
     - 副作用遇到无法通过重试解决的冲突时释放任务：先在平台链写一条 REVIEW_SKIP 审计（summary 含任务类型、request_id 和原因码），再执行 `UPDATE ... SET status='SKIPPED', done_at WHERE status='ASSIGNED' AND assignee_id=本人`。审计写失败时任务保持 ASSIGNED。释放后仍返回原冲突错误。
  7. 把任务从本人持有的 ASSIGNED 改为 DONE，写入 expert_score 和 done_at。改动 0 行时重读：已是本人以相同分数完成的 DONE 视为重放成功，否则返回 409。BACKFLOW_EXPECT 任务完成后再重读一次 MinIO 结论比对，不一致返回 409。
  8. 若任务类型不是 ONLINE_JUDGE，在平台链（tenant 0、farm 0）追加一条 REVIEW_SUBMIT 审计，target 为 `review:{id}`。重放时同样再写一条。
- 结果与失败：成功返回 200，内容为任务视图和 replayed 标记。审计 summary 只有任务类型、request_id、分数、decision、判分结果 id 和是否重放，不含样本 id、expect 和 reason 原文。状态冲突返回 409 REVIEW_CONFLICT；目标判分行不存在返回 404；其余数据库错误返回 500。同一专家原样重复提交不会重复产生副作用。

#### 在线判分回写

由 `internal/service/review_l2b.go` 的 `ReviewService.writeJudge` 执行，写业务库的 `internal/repository/quality_judge.go` 的 `QualityRepo.ReviewJudgeResultAudited`。

1. 以 draft_ref 中的租户和农场为 Scope，读业务库 online_judge_result 中对应 id 的行。行不存在（包括 draft_ref 指向别的农场）时以原因码 TARGET_MISSING 释放任务，返回 404。
2. 若该行的维度或判分器版本与任务不一致，以 TARGET_MISMATCH 释放任务，返回 409。
3. 按该行状态处理：
   - NEED_EXPERT：继续第 4 步。
   - REVIEWED 且是本人以相同分数复核的（上次在完成任务前中断）：跳过回写，视为成功。
   - REVIEWED 且是本人以不同分数复核的：返回 409，不释放任务，留给本人原样重放收尾。
   - REVIEWED 且是他人复核的：以 TARGET_REVIEWED 释放任务，返回 409。
   - 其他状态（如 SCORED）：以 TARGET_NOT_PENDING 释放任务，返回 409。
4. 在业务库的一个事务内执行：
   1. `UPDATE online_judge_result SET expert_score, expert_id, status='REVIEWED', row_ver=row_ver+1, updated_at WHERE tenant_id AND farm_id AND id AND row_ver=读到的值 AND status='NEED_EXPERT'`。改动 0 行时返回行版本冲突，事务回滚，接口返回 409。
   2. 在被回写行所属农场的审计链上追加一条 REVIEW_SUBMIT 审计，随事务提交封链。审计记录的农场与回写行不一致时直接报错。

回写后的专家分会在下一次[日报指标汇总](#日报指标汇总)中优先于判分器分参与事实一致性统计；专家分不高于 1 的行会作为「专家判错」信号进入[归因周报](#归因周报)。

#### 回流期望写入

由 `internal/service/review_l2b.go` 的 `ReviewService.putExpect` 执行，写 MinIO 桶 agri-steward-eval。

1. 生成结论对象：draft_ref、任务 id、decision、规范化后的 expect、reason、专家 id、提交时间。
2. 读 `review/backflow_expect/{draft_ref}.json`。若不存在，则以「对象不存在才写」的条件写入，成功即结束；若条件写发现对象已存在（并发写入），重读该对象。
3. 比较已存结论与本次结论（不比较提交时间）：一致则视为成功；不一致且已存结论是本人写的，返回 409 且不释放任务；不一致且是他人写的，以 EXPECT_TAKEN 释放任务，返回 409。

本步骤只写结论对象，不改评测样本文件。草稿合入或丢弃后的 MERGED、DROPPED 状态推进没有实现。

### 用户反馈

- 入口：POST `/api/v1/farms/:farm_id/advices/:advice_id/feedback`，请求体为 verdict、category、comment、request_id。路由在 `internal/controller/feedback_l8.go` 的 `FeedbackRoutes` 与 `FeedbackHandler`，业务在 `internal/service/feedback_l8.go` 的 `FeedbackService.Submit`，读写在 `internal/repository/feedback.go` 的 `FeedbackRepo`。
- 前置条件：挂在农场路由组下，经农场鉴权得到农场 Scope。路由对应操作 advice.feedback，权限矩阵授给 farmer、farm_manager、agronomist、operator、admin。
- 执行步骤：
  1. advice_id 不是正整数时返回 400 bad advice_id；请求体不是合法 JSON 时返回 400 bad body。
  2. 校验内容：request_id 必填，不超过 64 字节；verdict 只能是 ADOPT 或 DISLIKE。DISLIKE 必须带 category，取值为 DOSAGE、TIMING、PRODUCT、EVIDENCE、OTHER，OTHER 时 comment 必填，comment 不超过 512 字。ADOPT 不能带 category，comment 不超过 512 字。不通过时返回 400 FEEDBACK_INVALID。
  3. 执行 `SELECT run_id FROM advice_card WHERE tenant_id AND farm_id AND id` 确认建议卡属于本农场并取得 run_id。不存在（包括属于别的农场）时记一条 RESOURCE_NOT_IN_SCOPE 拒绝审计，返回 404。
  4. comment 经 `pii.Mask` 脱敏后再保存。
  5. 执行 `INSERT INTO advice_feedback ... ON DUPLICATE KEY UPDATE id=id`，request_id 在全表唯一。
  6. 按 (tenant_id, farm_id, request_id) 读回该行。读不到（request_id 已被别的农场用过），或读到的用户、建议卡与本次不同，返回 409 REQUEST_ID_CONFLICT。
- 结果与失败：首次写入返回 201，同一 request_id 重放返回 200 并带回首次的结果，内容为 feedback 和 replayed。本接口不写审计和 outbox。差评会在[归因周报](#归因周报)和[线上回流采集](#线上回流采集)中作为负向信号读取。

### 归因周报

- 入口：worker 任务 `attribution-weekly`，周期为 `attribution.interval`（缺省 1 小时）。构造在 `internal/app/attribution_l8.go` 的 `attributionLoops` 与 `App.attributionWeeklyLoop`，执行在 `internal/service/attribution/weekly.go` 的 `Job.Run`、`Job.Tick`、`Job.RunOnce`，出报告在 `internal/service/attribution/report.go` 的 `Job.report`，读写在 `internal/repository/attribution.go` 的 `AttributionRepo`。
- 前置条件：
  - `attribution.enabled` 与 `attribution.backflow.enabled` 都为 false 时本任务和[线上回流采集](#线上回流采集)都不起。任一为 true 时缺业务库或锁，或配置校验、时区解析失败，worker 启动失败。
  - `attribution.enabled` 为 true 时还需要对象存储和桶，否则启动失败。时区为 `attribution.timezone`（缺省 Asia/Shanghai），Top 条数为 `attribution.top_n`（缺省 20）。
  - 专家判错的评测库来源未接入，周报中注明「评测库 review_task 专家判错未接入」；业务库 online_judge_result 的专家判错照常读取。
- 执行步骤：
  1. `Tick` 按配置时区取上一个 ISO 周（周一 00:00 到下周一 00:00），周名形如 2026W44。读 MinIO 的 done 标记 `report/weekly/{周名}.json`：若已存在则本轮结束；若读取出错则返回错误，下个周期重试；否则调用 `RunOnce`。
  2. 获取锁 `lock:p2job:attribution-weekly`，若被持有则本轮结束。取锁后再读一次 done 标记，已存在则结束。
  3. 执行 `SELECT tenant_id, farm_id, timezone FROM farm_profile` 列出农场，逐农场读取上周信号和回流计数，每个农场完成后续期一次锁：
     - 信号见[周报信号来源](#周报信号来源)。
     - 回流计数从 audit_log 中 action 为 BACKFLOW 的事件统计：按 summary.status 分组、`COUNT(DISTINCT run_id)`，排除 RETRY。
  4. 按签名聚合信号：签名为「原因|问题类型|主知识库」的 md5。每个签名的命中数为本周信号条数，证据按命中时间从新到旧排列。
  5. 每 500 个签名一批写入 attribution_issue 平台行，每批后续期一次锁：
     1. 读这批签名已有的行，合并证据：本周在前、旧证据在后，按来源和来源 id 去重，最多保留 50 条。旧状态为 RESOLVED 或 VERIFIED 的签名记为「本周重开」。
     2. 在一个事务内逐行执行 upsert，tenant_id 和 farm_id 都为 0。新签名插入为 OPEN；已有签名更新 last_week、hit_count（用本周数覆盖）、evidence_refs，若原状态为 RESOLVED 或 VERIFIED，则 reopen_count 加 1 并改回 OPEN，row_ver 加 1。
  6. 生成周报：
     1. 读 last_week 为本周的行，按命中数降序、签名升序取前 Top 条。
     2. 读上一周的 done 标记快照，按签名查出上期 Top 问题现在的负责人、处置和状态，与上期状态并列展示。上期快照不存在时不展示该部分。
     3. 读本周重开签名对应的行。
     4. 读 MinIO 的 `attribution.kb_load_gaps_key`（缺省 `nightly/kb_load_gaps.json`），对象不存在时该部分显示「无」。
     5. 渲染 HTML 写入 `report/weekly/{周名}.html`。
  7. 写 done 标记 `report/weekly/{周名}.json`，内容为周名、报告路径、生成时间、Top 问题当时的状态快照和本周重开签名。
- 结果与失败：本任务不写审计和 outbox。取数、写库或写 MinIO 出错时本轮返回错误，下个周期整周重跑：命中数按本周重算覆盖，证据按来源去重，已改回 OPEN 的问题不会再次计入重开。只处理上一个 ISO 周，整周停机错过的更早的周不会补出。
- 注：`Tick` 的注释写的是「周一首个周期即出上周周报」；代码实际是只要上周的 done 标记不存在，本周任何一天的第一个周期都会出上周周报。
- 注：`Job.report` 的注释写的是补跑时沿用首次快照里的重开签名；代码实际是 `RunOnce` 在 done 标记已存在时直接返回，只有标记不存在时才会出报告，所以这一合并读不到首次快照。首次运行写标记失败后重跑，首次已重开的签名因状态已是 OPEN 不再被识别，不会出现在重跑生成的周报「重开」部分。

#### 周报信号来源

单个农场一条 UNION ALL 查询，时间窗口为上周 [起, 止)，问题类型取建议卡的 category（卡不存在时为 unknown），主知识库取该卡 seq 最小的 kb 引用：

- 驳回：rejection_reason 按 created_at 过滤，原因为 reason_code。
- 差评：advice_feedback 中 verdict 为 DISLIKE 且有 category 的行，按 created_at 过滤，原因为 category。
- 拒答：advice_card 中 outcome 为 REFUSED 的卡。refuse_reason 为 VALIDATION_FAILED 时原因记 GUARDRAIL、来源记 validation；为 KB_MISS 时原因记 KB_MISS、来源记 kb_miss。
- 专家判错：online_judge_result 中 status 为 REVIEWED 且 expert_score 不高于 1 的行，按专家回写时刻 updated_at 过滤，同一张卡只算一次，原因为 EXPERT_WRONG。

### 归因问题处置

- 入口：PATCH `/api/v1/admin/attribution-issues/:id`，请求体为 disposition、owner_id、status、resolution_ref、row_ver。路由在 `internal/controller/attribution_l8.go` 的 `MountAttributionAdmin` 与 `IssuePatchHandler`，业务在 `internal/service/attribution_l8.go` 的 `AttributionIssueService.Patch`，写库在 `internal/repository/attribution.go` 的 `AttributionRepo.PatchIssue`。
- 前置条件：中间件依次为 `RequestID`、`PlatformAuth`、`RequireOps(attribution.write)`，attribution.write 只授给 platform_admin，不通过时记拒绝审计并返回 403 ROLE_INSUFFICIENT。服务层再要求调用人是平台身份（tenant 0、farm 0）且角色含 platform_admin，否则 403。
- 执行步骤：
  1. 路径 id 不是正整数时返回 400 bad id；请求体不是合法 JSON 时返回 400 bad body。
  2. 校验内容：row_ver 必填且不小于 0；四个可改字段至少给一个；disposition 取值为 ADD_KB、FIX_LOADER、OFFLOAD_RULE、FIX_PROMPT、WONTFIX；status 取值为 OPEN、IN_PROGRESS、RESOLVED、VERIFIED；owner_id 大于 0；resolution_ref 为 1 到 256 字且不能全是空白。不通过时返回 400 ATTRIBUTION_PATCH_INVALID。
  3. 执行 `UPDATE attribution_issue SET disposition=COALESCE(?, disposition), owner_id=COALESCE(...), resolution_ref=COALESCE(...), status=COALESCE(...), row_ver=row_ver+1, updated_at WHERE tenant_id=0 AND farm_id=0 AND id=? AND row_ver=?`，没给的字段保持原值。
  4. 若改动 0 行，按 id 读平台行：不存在则返回 404；存在则说明 row_ver 不符，返回 409 ISSUE_ROW_VER_CONFLICT。
  5. 改动成功后读回该行返回。
- 结果与失败：成功返回 200 和更新后的行。本接口不写审计。状态没有流转限制，任一状态都可以直接改成另一状态。改成 RESOLVED 或 VERIFIED 的问题，若之后某周再次命中，会在[归因周报](#归因周报)中被重开。

### 线上回流采集

- 入口：worker 任务 `backflow-collect`，周期沿用 `attribution.interval`（缺省 1 小时）。构造在 `internal/app/attribution_l8.go` 的 `App.backflowLoop`，执行在 `internal/service/backflow/collect.go` 的 `Job.Run`、`Job.Tick`、`Job.RunOnce`，草稿生成在 `internal/service/backflow/draft.go`，读写库在 `internal/repository/backflow.go` 的 `BackflowRepo`。
- 前置条件：
  - `attribution.backflow.enabled` 为 true，并满足[归因周报](#归因周报)中共用的业务库、锁和配置要求。
  - 需要装配原文读取服务（`AuditService.ReadRaw` 与预签名），否则 worker 启动失败。取预签名原文的 HTTP 超时为 30 秒。
  - 配置项：草稿目录 `attribution.backflow.drafts_dir`（缺省 `eval/backflow/drafts`），KB_MISS 入选门槛 `kb_miss_min_hits`（缺省 3），每农场每轮最多处理的 run 数 `max_runs`（缺省 50），读原文用的服务账号 `service_user_id`（缺省 9900）。
- 执行步骤：
  1. `Tick` 按配置时区取上一个 ISO 周。若本进程已对该周成功跑完一轮，则本轮结束；否则调用 `RunOnce`。
  2. 获取锁 `lock:p2job:backflow-collect`，若被持有则本轮结束，不记为已跑完。
  3. 执行 `SELECT tenant_id, farm_id, timezone FROM farm_profile` 列出农场，逐农场处理。单个农场出错时记下错误继续下一个农场，每个农场后续期一次锁，续期失败时停止本轮。单个农场的处理如下：
     1. 用[周报信号来源](#周报信号来源)同一条查询取本农场上周信号。
     2. 选样：差评、专家判错、护栏拦截的信号直接入选；KB_MISS 拒答只在同一问题类型本周达到门槛次数时入选；驳回不入选。按 run 去重，最多 `max_runs` 个。
     3. 在一个事务内对入选的 run 执行 `SELECT ... FOR UPDATE`（只取 backflow_status 为空的行），`UPDATE agent_run SET backflow_status='SELECTED'`，并为每个 run 在农场审计链上写一条 BACKFLOW 事件（summary.status 为 SELECTED，操作人为系统，target 为 `run:{id}`）。
     4. 按 id 顺序取本农场所有 SELECTED 状态的 run（包括以前轮次留下的），最多 `max_runs` 个。
     5. 草稿时钟用农场时区，农场时区为空或非法时用配置时区。
     6. 对每个 run 生成草稿，见[回流草稿生成](#回流草稿生成)。生成出错时记一次失败尝试，做法见本节外层第 4 步。
  4. 第 3 步中某个 run 生成草稿出错时，在一个事务内记录失败尝试：锁住该 SELECTED 的 run，统计 audit_log 中该 run 已有的 RETRY 事件数，再写一条 RETRY 事件（带第几次尝试）。累计达到 3 次时把 backflow_status 改为 FAILED，否则保持 SELECTED，等下一轮再试。
- 结果与失败：
  - backflow_status 的取值为 SELECTED、DRAFTED、PII_FAILED、FAILED；MERGED、DROPPED 已定义但没有代码推进。
  - 单个 run 生成草稿失败不算本轮出错。取数或写库出错时本轮返回合并后的错误，本进程不记为已跑完，下个周期重跑；已置 SELECTED 的 run 不会重复入选。
  - 业务 worker 不写评测库。草稿生成后，由 `cmd/eval backflow import` 读取草稿目录并在评测库建 BACKFLOW_EXPECT 评审任务。
- 注：P2 路线文档（`智能农作物Agent管家-P2-质量优化期实施路线.md` §6.9 技术实现 4）写的是草稿「推到评测仓 `eval/backflow/drafts/`，并为每份草稿建 review_task(BACKFLOW_EXPECT)」，真实 ID 与合成码的对应「只写业务库 agent_run.backflow_draft_ref」；代码实际是 worker 只把草稿写到本机目录 `{drafts_dir}/{draft_ref}.yaml`，不写评测库也不写 MinIO，评审任务由 `cmd/eval backflow import` 建；agent_run.backflow_draft_ref 只存草稿编号，真实 ID 与合成码的对应只在内存中，草稿生成后即丢弃。
- 注：`collect.go` 中 `JobDeps.Interval` 的注释写的是「每个上一 ISO 周在本进程只跑一次」；代码实际是本轮返回错误或锁被他人持有时都不记为已跑完，下个周期会再跑。已跑完的记录只在进程内存里，进程重启后同一周会再跑一轮。

#### 回流草稿生成

由 `internal/service/backflow/collect.go` 的 `Job.draft` 对一个 SELECTED 的 run 执行。

1. 读材料（业务库，限本农场）：
   - agent_run 的田块、提问人、knowledge_ref，以及 field_profile 的作物。
   - audit_log 中该 run 的 ASK 与 KB_LOAD 事件：第一条 ASK 的时间作为提问时间，summary.question 作为问题原文；第一条 KB_LOAD 的 target 去掉 `kb:` 前缀后覆盖 knowledge_ref。
   - tool_call 中该 run 状态为 OK、未被替代、带原文对象 id 的调用，按 id 排序。
2. 为本 run 生成脱敏器，给农场、田块、提问人各生成一个合成码；生成草稿编号 `bf-` 加 16 个随机小写字母。
3. 对问题原文做自由文本脱敏，规则见[回流脱敏规则](#回流脱敏规则)。
4. 逐个工具调用读原文：
   1. 以服务账号身份（本农场 Scope、`service_user_id`、auditor 角色）调用 `AuditService.ReadRaw`。该调用在事务内核对原文归属、生成 5 分钟有效的预签名地址，并写一条 RAW_READ 审计；被拒绝时也写一条拒绝结果的 RAW_READ 审计。原文已过保留期时跳过该工具，其他错误使本 run 生成失败。
   2. 用 30 秒超时的 HTTP 客户端下载预签名地址，要求返回 200 且不超过 4MB，否则本 run 生成失败。
   3. 解析原文中的 data、source、collected_at，对 data 做结构化脱敏，source 做自由文本脱敏。原文无法解析时跳过该工具。
   4. 被跳过的工具名写进草稿 notes。
5. 组装草稿：字段与评测样本格式对齐，suite 为 capability，标签为 L8、backflow，expect 为空，author 为 backflow-draft，review_status 为 pending_expert，fixtures.clock 为提问时间（农场时区，RFC3339），每个工具的桩以田块合成码作为匹配条件，同名工具多次调用按次序合并。编码为两格缩进的 YAML。
6. 兜底扫描：每个桩的返回过 `piiclean.FirstLeak`，YAML 逐行过 `piiclean.Detect`，再检查租户、农场、田块、提问人、run 的真实 ID（3 位及以上）是否作为完整数字串出现。
7. 若扫描发现残留，则不写文件，在一个事务内执行 `UPDATE agent_run SET backflow_status='PII_FAILED' ... WHERE backflow_status='SELECTED'` 并写一条 BACKFLOW 事件；否则继续第 8 步。
8. 先写同目录临时文件再改名，原子写出 `{drafts_dir}/{draft_ref}.yaml`。然后在一个事务内把 run 改为 DRAFTED、写入 backflow_draft_ref，并写一条 BACKFLOW 事件（summary 不含草稿编号）。若这一步失败，删除刚写出的文件。
9. 第 7、8 步的 UPDATE 改动 0 行（run 已不是 SELECTED）时返回并发冲突，本 run 记一次失败尝试。

#### 回流脱敏规则

由 `internal/service/backflow/desensitize.go` 的脱敏器执行。真实 ID 到合成码的对应只在内存中，草稿生成后即丢弃。

- 结构化数据（JSON）按键名处理，键名本身不改：
  - 身份类键（name、owner、farmer、contact、address、phone、mobile、tel、id_card、id_no 等）下的标量整体换成 `syn-{类别}-` 加 8 个随机字母。
  - `id` 或以 `_id` 结尾的键下的数值换成合成码：farm_id 为 `farm-bf-`，field_id 为 `field-bf-`，user_id 为 `u-bf-`，其他为 `id-bf-`，后接 8 个随机字母。同一草稿内同一个值得到同一个码。字符串形式的业务编码不换。
  - 坐标类键（lat、lng、lon、latitude、longitude、location、position、point、geo、gps、coordinates）下的数值四舍五入到两位小数。
  - 其他字符串按自由文本处理，其他数值保持原样。
- 自由文本：
  1. 全角数字转成半角。
  2. 带「北纬、东经、纬度、经度」等标签的坐标，以及 piiclean 判定为坐标的精确数值对，四舍五入到两位小数。
  3. 中文数字写法的手机号换成合成值。
  4. 连续数字串（可带连字符、空格和末尾 X）若被 piiclean 判为手机号、证件号、账号等，换成对应类别的合成值。
- 注：`desensitize.go` 文件头注释写的是兜底扫描在 `gate.go`；代码实际是 `gate` 函数在 `draft.go` 中，包内没有 `gate.go`。

### 规则影子数据清理

- 入口：worker 任务 `rule-shadow-purge`，周期为 `rule_offload.purge_every`（缺省 24 小时）。构造在 `internal/app/rule_offload.go` 的 `ruleOffloadLoops`，执行在同文件的 `shadowPurger.Run`、`shadowPurger.tick`、`shadowPurger.purge`，删库在 `internal/repository/rule_shadow_diff.go` 的 `RuleShadowDiffRepo`。本节只写清理任务，主链路写影子比对行的逻辑不在本章。
- 前置条件：
  - 业务库或锁未装配时不起任务。
  - 保留天数 `rule_offload.shadow_diff_days`（缺省 180）和清理周期都必须大于 0，否则 worker 启动失败。配置为零值时取缺省值。
- 执行步骤：
  1. 获取锁 `lock:p2job:rule-shadow-purge`。若锁被持有则写一条 info 日志，本轮结束。
  2. 截止时间为当前时间减保留天数。执行 `SELECT tenant_id, farm_id FROM rule_shadow_diff GROUP BY tenant_id, farm_id HAVING MIN(created_at) < 截止时间 ORDER BY tenant_id, farm_id`，列出有过期行的农场。
  3. 对每个农场、每个下沉项（operation_window、tank_mix、pest_priority）循环执行 `DELETE FROM rule_shadow_diff WHERE tenant_id AND farm_id AND item AND created_at < 截止时间 LIMIT 5000`：
     - 每删一批续期一次锁，续期失败时停止本轮。
     - 某批删除不足 5000 行时，该农场该项删完，进入下一项。
  4. 本轮结束写一条 info 日志，记录删除总行数和保留时长。
- 结果与失败：不写审计。删除出错时本轮返回错误并写 error 日志，已删除的行不恢复，下个周期从头再删，删除条件只看时间，重跑结果一致。单轮不限批次，删到所有农场所有项都清完为止。

### 知识加载明细清理

- 入口：worker 任务 `kb-load-retention`，周期固定 1 小时。构造在 `internal/app/kb_load.go` 的 `kbLoadLoops`，执行在 `internal/service/kb_load_retention.go` 的 `KBLoadRetention.Run` 与 `KBLoadRetention.Tick`，删库在 `internal/repository/kb_load_item.go` 的 `KBLoadItemRepo`。
- 前置条件：
  - 业务库或锁未装配时不起任务。
  - 保留天数取 `retention.table_days.kb_load_item`，未配置时为 180 天。配置了但不大于 0 时 worker 启动失败。
- 执行步骤：
  1. 获取锁 `lock:p2job:kb-load-retention`。若锁被持有则本轮返回 0，不报错。
  2. 截止时间为当前时间减保留天数。执行 `SELECT tenant_id, farm_id FROM kb_load_item GROUP BY tenant_id, farm_id HAVING MIN(created_at) < 截止时间 ORDER BY tenant_id, farm_id`，列出有过期行的农场。
  3. 对每个农场循环执行 `DELETE FROM kb_load_item WHERE tenant_id AND farm_id AND created_at < 截止时间 LIMIT 5000`，直到某批不足 5000 行，或单个农场本轮已删 100 批。剩余的行留到下一轮。
  4. 每个农场完成后续期一次锁，续期失败时停止本轮并返回错误。
  5. 删除行数大于 0 时写一条 info 日志，记录行数、农场数和截止时间。
- 结果与失败：不写审计。删除出错时本轮返回错误并写 warn 日志，下个周期重试；删除条件只看时间，重跑结果一致。
