# 02 问答主链路

## 本章概述

用户在 `POST /api/v1/farms/:farm_id/ask` 提问后，server 校验参数、开关与限流，建一条 agent_run(RUNNING) 并立即返回 202 和 run_id，主链路在后台协程里执行。
主链路是一张 Eino 线性图（classify → … → finalize），由 runner 持 Redis 锁与心跳托管；规则层做判定与计算，模型只负责分类、在候选内选药和组织措辞，输出经护栏校验后落建议卡，作业类建议再转作业单草稿并开审批票，随后在 await_approval 中断等待审批。
本章还描述主链路用到的子流程（知识加载、计算器、约束与护栏、模型调用、工具网关）、检查点与续跑、记忆与长对话压缩，以及运行事件的写入与 SSE 推送、运行详情和原文读取接口。
审批票激活之后的审批、续跑触发、下发与回执见 [03-审批与工单下发](03-审批与工单下发.md)；审计链与原文清理见 [04-审计与观测](04-审计与观测.md)；中间件链与开关读取见 [01-启动与请求入口](01-启动与请求入口.md)。

所有 Redis 键实际都带 `as:{env}:` 前缀，下文省略前缀。

## 受理

### 提问受理

- 入口：`POST /api/v1/farms/:farm_id/ask`，请求体 `{field_id, text, prev_run_id}`。代码：`internal/controller/ask.go` 的 `AskHandler`，`internal/service/ask.go` 的 `AskService.Ask`。
- 前置条件：请求已经过 RequestID、FarmAuth、Authorize 三个中间件（见 01 的「农场路由通用链路」）。
  - RequestID：请求头 X-Request-Id 须匹配 1-64 位字母、数字、`.`、`_`、`-`，否则 400 `bad X-Request-Id`；没有时生成 16 字节十六进制 id。id 写回响应头并放进 ctx，后台主链路的日志带上它。
  - FarmAuth：校验 Bearer token 与路径 farm_id，每次请求按 user_role 解析 Scope（租户、农场、用户、角色）。
  - Authorize：本路由要求操作 OpAsk，角色不具备时 403 ROLE_INSUFFICIENT 并写拒绝审计。
- 执行步骤：
  1. handler 从 ctx 取 Scope，取不到回 401。
  2. 解析请求体，失败回 400 `bad body`。farm_id 只认 Scope，不读请求体。
  3. 调 `AskService.Ask`：
     1. 去掉 text 首尾空白。field_id 为 0、text 为空或超过 500 个字符时返回参数错误。
     2. prev_run_id 与 Supersedes（只由复检取代流程填写）同时非 0 时返回参数错误。
     3. 地块归属：`SELECT 1 FROM field_profile WHERE tenant_id=? AND farm_id=? AND id=?`。查不到返回「不在范围内」。
     4. 读开关 enable_advice（FlagService，30 秒缓存）。未装配开关读取器、读取失败或开关为关都不放行（失败关闭），关时返回 ADVICE_DISABLED。
     5. 农场提问限流：Redis 键 `rl:farm:{farm_id}:ask`，Lua 脚本 INCR 后首次设 PEXPIRE 1 分钟，固定窗口，上限每分钟 20 次（`internal/app/app.go` 的 AskPerMinute）。超限返回限流错误。
     6. 建 run，见[建 run 与会话续接](#建-run-与会话续接)。
     7. 用请求 ctx 去掉取消信号、保留取值（request id、Scope）后加 5 分钟超时，启动后台协程执行主链路，见[异步执行与失败收尾](#异步执行与失败收尾)。
     8. 立即返回 run_id。
- 结果与失败：
  - 成功：202 `{run_id}`。客户端随后用 SSE 或运行详情接口取结果。
  - ADVICE_DISABLED → 403 ADVICE_DISABLED。
  - 地块不在范围内或 ErrForbidden → 403，并写一条 RESOURCE_NOT_IN_SCOPE 拒绝审计（target 为 `field:{field_id}`），不暴露地块是否存在。
  - 参数错误 → 400；限流 → 429；数据库、Redis 等其他错误 → 500。
  - 接口不做幂等：同一问题重复提交会建多个 run，每次都计入限流。

### 建 run 与会话续接

- 入口：由[提问受理](#提问受理)第 6 步调用；复检取代旧 run 时由复检流程以 Supersedes 调用（见 03）。代码：`internal/service/ask_l6.go` 的 `AskService.createRun` / `AskService.sessionLink`，`internal/repository/run.go` 的 `RunRepo.CreateRun`，`internal/repository/run_l6.go` 的 `RunRepo.CreateRunLinked`。
- 前置条件：地块归属、开关、限流都已通过。
- 执行步骤：
  1. 确定会话关联：Supersedes 非 0 时关联类型为「取代」，对象是被取代的 run；否则关联类型为「会话」，对象是 prev_run_id，空闲上限取 compaction.session_idle（30 分钟）。
  2. 若关联对象为 0 或未装配会话建 run 能力，则直接走普通建 run（第 4 步）。
  3. 读开关 enable_compaction：读失败记 Warn 后按新会话处理；开关关也按新会话处理。两种情况都走第 4 步。开关开时走第 5 步。
  4. 普通建 run：`INSERT INTO agent_run (tenant_id, farm_id, field_id, user_id, status='RUNNING', graph_version, prompt_version, model_tier, knowledge_ref, created_at, updated_at)`。版本信息取主链路的 Meta（图版本、提示词版本 v1、档位 standard、知识引用）。
  5. 续接建 run，一个事务内：
     - 「会话」关联：`SELECT compaction_state FROM agent_run WHERE tenant_id=? AND farm_id=? AND id=? AND field_id=? AND user_id=? AND status IN ('COMPLETED','FAILED','CANCELED') AND updated_at >= now - 30 分钟`。命中时新 run 的 prev_run_id 取该 run，并复制它的 compaction_state。
     - 「取代」关联：`SELECT compaction_state, prev_run_id FROM agent_run WHERE tenant_id=? AND farm_id=? AND id=? AND field_id=?`。新 run 继承旧 run 的 prev_run_id 和 compaction_state（新 run 接到旧 run 的上一轮之后，而不是接在旧 run 之后）。
     - 未命中（不同地块或用户、旧 run 仍在 RUNNING / INTERRUPTED、超过空闲时间），或取代对象既无 prev_run_id 也无 compaction_state 时，按普通 INSERT 开新会话。
     - 命中时 INSERT 额外写 compaction_state 与 prev_run_id 两列。
  6. 记一条 Info 日志（关联类型、来源 run、是否续接成功）。
- 结果与失败：返回新 run_id。数据库错误向上返回，提问受理回 500。续接校验不通过不报错，只是开新会话。

### 异步执行与失败收尾

- 入口：[提问受理](#提问受理)第 7 步启动的后台协程。代码：`internal/service/ask.go` 的 `AskService.run`。
- 前置条件：run 已是 RUNNING；协程 ctx 不受 HTTP 请求结束影响，5 分钟后超时。
- 执行步骤：
  1. 调主链路 `Agent.Ask`（见[主链路执行入口](#主链路执行入口)），问题文本为去空白后的 text，RunID 为刚建的 run。
  2. 若主链路返回错误：记 Error 日志；错误不是「执行权丢失」时，原因码记为 AGENT_ERROR。执行权丢失时不写（run 可能已被 stuck_run 扫描接管，见 03）。
  3. 若协程 panic：recover 后记 Error 日志，原因码记为 AGENT_PANIC。
  4. 原因码非空时调 FinishRun(FAILED, 原因码)：`UPDATE agent_run SET status=?, reason_code=?, row_ver=row_ver+1 WHERE ... AND status='RUNNING' AND row_ver=?`。失败只记 Warn。
- 结果与失败：
  - 正常结束（含拒答、含中断等待审批）时这里不写任何东西，run 状态已由 runner 写好。
  - 注：`service/ask.go` 注释写的是「超时由 Ask 返回错误并置 FAILED」且原因码为 AGENT_ERROR，代码实际是 runner 先以图给出的原因码 GRAPH_ERROR 把 run 置 FAILED 并发 RUN_FAILED；随后这里的 FinishRun(AGENT_ERROR) 因 run 已不是 RUNNING 而失败，只记 Warn，reason_code 保持 GRAPH_ERROR。只有 runner 来不及收尾（例如建锁之前就出错）时才会落 AGENT_ERROR。
  - 进程优雅退出时 `AskService.Wait` 等待所有后台协程结束。

## 主链路

### 主链路节点顺序

图名 advice，由 `internal/agent/graph/agent.go` 的 `Agent.compile` 把 13 个节点按固定顺序串成一条线（START → 节点 → END），没有条件边。分支靠节点内部判断：任一节点给出拒答原因后，后续节点检查「已拒答」直接返回，拒答卡一路带到 persist。

```
START
  → classify        模型分类：一级类 / 意图 / 防治对象 / 槽位；不在范围即拒答
  → enrich          按一级类并发调只读工具，汇成事实表
  → load_knowledge  按加载策略选知识条目，写 kb_load_item，发 KB_LOADED
  → candidates      规则层判定（作业 / 观察）；植保作业类给出登记药剂候选
  → choose          模型在候选内选药（仅植保作业类有候选时）
  → compute         按所选药剂补算用量、安全间隔期等
  → explain         模型组织结论（数字只能写占位符）；模型不可用时降级为规则模板
  → assemble        组装建议卡或拒答卡
  → validate        输出护栏校验，不通过改为 VALIDATION_FAILED 拒答卡
  → persist         落建议卡与引用（拒答卡同样落库），发 ADVICE_READY
  → to_order        作业类建议转作业单草稿并开审批票
  → await_approval  有审批票时中断（写检查点、run 置 INTERRUPTED）
  → finalize        发 RUN_COMPLETED
END
```

各节点的状态都放在同一个内存对象上（问题、Scope、run_id、知识快照、计算器、分类结果、工具结果、事实表、规则结论、候选、数值、建议卡、作业单、票据），节点原地修改它。

### 主链路执行入口

- 入口：[异步执行与失败收尾](#异步执行与失败收尾)第 1 步。代码：`internal/agent/graph/agent.go` 的 `Agent.Ask`；装配在 `internal/app/agent.go` 的 `GraphAgent`。
- 前置条件：装配时已校验 LLM、工具网关、run / 建议卡 / 作业单仓储、锁、时钟、知识库、分类表、作物、区域、约束注册表、故障矩阵均不为空，默认档位存在；否则启动失败。
- 执行步骤：
  1. 若 RunID 为 0（受理接口不会出现），先按 Scope 建 run。
  2. 若配置了长对话压缩，给 ctx 挂上压缩状态载体，供检查点与终态 UPDATE 共用（见[长对话压缩](#长对话压缩)）。
  3. 交给 runner 托管执行（见[runner 执行外壳](#runner-执行外壳)），执行体内依次：
     1. ctx 放入 run 标识，trace 回调据此写事件。
     2. 构造状态：打开知识快照（`KB.Open`，引用默认是工作区版本）；建计算器；若装配了农场区域源，读 `SELECT region FROM farm_profile WHERE tenant_id=? AND farm_id=?`，经区域名映射（江苏 → jiangsu 等）得到区域码，映射为空时报错（知识按区域隔离，不回落默认区域）。任一步失败，run 以 GRAPH_ERROR 失败。
     3. 发 RUN_STARTED 事件（actor 为提问用户，payload 为 field_id 与脱敏后的问题）。
     4. ctx 放入检查点归属（Scope、run_id、中断类型 WAIT_APPROVAL）。
     5. 调用图，带 runner 的步骤回调、trace 回调，以及配置了检查点时的 checkpoint_id（= run_id 十进制）。
     6. 若图以审批中断返回，执行体返回「INTERRUPTED(WAIT_APPROVAL)」；若图返回错误，返回 GRAPH_ERROR；否则返回 COMPLETED，原因码为拒答原因（出建议时为空）。节点 panic 被转为 GRAPH_ERROR 错误。
  4. 由最终状态组装返回值（结局、拒答原因、建议卡、作业单、票据、约束拦截的规则）；中断时附上 runner 激活后的票据。最终状态没有建议卡时返回错误。
- 结果与失败：成功时 run 为 COMPLETED 或 INTERRUPTED；失败时 run 为 FAILED(GRAPH_ERROR) 并发 RUN_FAILED。拒答不是失败，run 照样 COMPLETED，reason_code 记拒答原因。

### runner 执行外壳

- 入口：`Agent.Ask` 第 3 步、`Agent.Resume`。代码：`internal/agent/harness/runner/runner.go` 的 `Runner.Run` / `Runner.Resume` / `Runner.execute`。
- 前置条件：run 已存在。
- 执行步骤：
  1. 取 run 锁：Redis `SET lock:run:{run_id} {token} NX PX 30000`。已被占用时返回错误（「acquire run」），run 不变，由 AskService 记 AGENT_ERROR。
  2. ctx 放入执行权标记与 resume_epoch（首次执行为 0）。
  3. 启动续期协程：每 10 秒续一次锁；续期成功后 `UPDATE agent_run SET updated_at=? WHERE ... AND status='RUNNING'` 作心跳，心跳失败只记 Warn；续期失败则标记执行权丢失并取消 ctx。此后所有业务写入前的「仍持有执行权」检查都会失败。
  4. 运行执行体，节点开始 / 结束 / 失败写 run_step（见[步骤记录与 trace 回调](#步骤记录与-trace-回调)）。
  5. 执行体结束后停止续期协程，然后按顺序判断：
     - 若执行权已丢失：返回「执行权丢失」，不写终态（由接管者处理）。
     - 若执行体无错但 run_step 写入出过错：按执行错误处理。
     - 若执行体返回 INTERRUPTED：不写终态（检查点事务已置 INTERRUPTED），发 RUN_INTERRUPTED 事件；中断类型为 WAIT_APPROVAL 时在仍持锁的情况下调审批闸门 Activate，把票据从 PREPARING 激活为 OPEN。激活失败只记 Warn，由 ticket_activate 扫描补做。激活的细节见 03 的「票据激活」。
     - 若执行体出错：首次执行把终态改为 FAILED（原因码取执行体给的，缺省 EXEC_ERROR）；续跑时不写 FAILED，直接返回错误，run 留在 RUNNING。
  6. 写终态 FinishRun（目标必须是终态、当前必须 RUNNING、row_ver 匹配；载体里有压缩状态时同一 UPDATE 写 compaction_state / compaction_count）。FAILED 时再发 RUN_FAILED 事件。
  7. 释放锁（失败只记 Warn）。
- 结果与失败：FinishRun 失败时返回错误。续跑失败留在 RUNNING 的 run 停止心跳后由 stuck_run 扫描处理（见 03）。

## 节点

### 节点 classify

- 入口：图的第 1 个节点。代码：`internal/agent/graph/nodes.go` 的 `Agent.classify`。
- 前置条件：状态已构造（知识快照、分类表已就绪）。
- 执行步骤：
  1. 组装入参：问题原文、知识快照登记表里的防治对象表、分类表的一级类代码与二级主题代码。
  2. 调模型任务 classify（见[模型调用](#模型调用)），输出一级类、意图、主题、防治对象、槽位（施药方式、施肥时期、肥料、灾种、是否叶面喷施、袋重、营养元素等）、是否在范围内、是否未知主体。
  3. 若 ctx 已取消（含执行权丢失），节点返回错误，run 失败。若模型回复不合规（非 JSON 或空），拒答 VALIDATION_FAILED。若模型不可用，走[模型不可用降级](#模型不可用降级)，此时尚无规则结论，必然拒答 LLM_UNAVAILABLE。
  4. 否则按结果判断：不在范围 → 拒答 OUT_OF_SCOPE；未知主体 → 拒答 KB_MISS；一级类不是植保 / 施肥 / 灌溉 / 灾害之一 → 拒答 OUT_OF_SCOPE。
- 结果与失败：分类结果写入状态；拒答时后续节点直通到 assemble。

### 节点 enrich

- 入口：图的第 2 个节点。代码：`internal/agent/graph/nodes.go` 的 `Agent.enrich` / `Agent.callTool`。
- 前置条件：未拒答。
- 执行步骤：
  1. 按一级类取工具清单：
     - 植保：crop.phenology、field.profile、field.history、field.pest_survey、weather.forecast、weather.history；意图为安全类知识问答时不调工具。
     - 施肥、灌溉：crop.phenology、field.profile、field.history、weather.forecast。
     - 灾害：crop.phenology、weather.forecast、weather.alert、field.history、field.profile。
  2. 入参统一为 `{field_id}`，每个工具一个协程并发调用工具网关（见[工具调用网关](#工具调用网关)），step_id 为 enrich，带当前 resume_epoch 与是否复检。
  3. 任一调用返回错误（只有 ctx 取消或网关存储失败）时节点返回错误，run 失败。
  4. 逐个检查结果：状态 OK 但数据为空或不可解码，或状态既不是 OK 也不是 REJECTED（超时、上游错误、越权等），拒答 DATA_MISSING；其中错误码属于故障矩阵 MCP_TIMEOUT 的，记下故障工具（拒答时写 DEGRADED，见[工具失败与缓存回落](#工具失败与缓存回落)）。REJECTED 视为该数据不存在，不拒答。
  5. 未拒答时，对来源为 cache 的结果记缓存回落降级。
  6. 把各工具数据拍平成事实表（按工具名排序）；另算虫情调查距今天数、预报距今小时数、移栽后天数等派生事实；从事实表取当前生育期。
- 结果与失败：工具调用都写 tool_call 行（网关负责）。DEGRADED 事件写失败时节点返回错误，run 失败。

  10. 选药后的补算（compute 节点调用）：取所选药剂的登记信息；有最大安全间隔期时输出 phi_days；意图为问用量时，按亩登记的输出亩用量区间、亩施药液量，有面积再给整田用量区间；按稀释倍数登记的需要槽位里的稀释倍数与水量，按倍数算配药量。

### 施肥规则

- 入口：[节点 candidates](#节点-candidates)第 1 步，一级类为施肥时。代码：`internal/agent/graph/rules_fertilize.go` 的 `decideFertilize`。

  8. 基肥且问题含「钾」时，另输出基肥氯化钾亩用量区间。

### 节点 to_order

- 入口：图的第 11 个节点。代码：`internal/agent/graph/assemble.go` 的 `Agent.toOrder`，`internal/agent/graph/approval.go` 的 `Agent.openTicket`，`internal/repository/orderdraft.go` 的 `OrderDraftRepo.CreateDraft`。
- 前置条件：建议卡结局为 ADVICE 且下一步为 CREATE_ORDER（观察类、模型降级卡、拒答卡都不转；只因缓存回落标了 degraded 的作业类卡照样转单）；仍持有执行权。
- 执行步骤：
  1. 组装 payload：物料、亩用量（第一个按亩的数值，灌水量除外）、整田用量（第一个整田数值或灌水量）、地块、面积。
  2. 定设备类型：施药与磷酸二氢钾叶面喷施取施药方式（无人机 / 背负式），灌溉为阀门，其余为人工。
  3. 定下发模式：按设备类型读一次开关（DispatchModeFor），未装配或读失败按 DRY_RUN（记 Error）。
  4. 做审批前约束检查（PRE_APPROVAL，见[约束检查](#约束检查)），结果挂在作业单上。
  5. CreateDraft，一个事务内：
     - `INSERT INTO work_order (...) ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id)`，状态 DRAFT，按 uk_advice 幂等；
     - 只在新插入时写 work_order_transition（from 为空串、to 为 DRAFT、actor 为 agent）和 run_event ORDER_TRANSITION（payload 为 order_id 与 DRAFT）。
  6. 开审批票：未装配审批闸门时跳过；否则再查执行权，调 `Gate.Open`（作业单、建议卡、发起人为提问用户）。写入了 constraint_check(PRE_APPROVAL) 与 approval_ticket(PREPARING)，后续见 [03-审批与工单下发](03-审批与工单下发.md)。
  7. 若闸门返回约束拦截：这是业务结论，单留 DRAFT、无票据，记下被拦截的规则 id，记 Info 日志，run 正常收尾；CONSTRAINT_BLOCKED 事件已由闸门写入，后续见 03。
- 结果与失败：作业单与票据写入状态。建单或开票的其他错误节点返回错误，run 失败。
- 注：`assemble.go` 注释写的是「转作业单草稿（DRAFT + DRY_RUN）」，代码实际是 dispatch_mode 按设备类型读开关决定，开关开且该设备类型可开放时为 REAL。

### 节点 await_approval

- 入口：图的第 12 个节点；审批后续跑时 Eino 只重跑本节点。代码：`internal/agent/graph/interrupt.go` 的 `Agent.awaitApproval` / `Agent.restore`。
- 前置条件：无。
- 执行步骤：
  1. 若本次是从中断恢复：取中断状态，取不到即报错「resumed without usable interrupt state」；取到则走第 5 步。
  2. 首次执行时，若没有票据，或未同时装配审批闸门与检查点存储，直通到 finalize（只装配闸门时 run 直接 COMPLETED）。
  3. 查执行权，组装快照：run_id、Scope、field_id、图版本、已完成节点（前 11 个节点）、待审批的 ticket_id 与 order_id、建议卡、作业单、票据、中断时刻；有压缩状态时附上压缩状态与次数。
  4. 以 WAIT_APPROVAL 类型发起有状态中断。Eino 把中断状态交给检查点存储写库（见[检查点存储](#检查点存储)），run 变为 INTERRUPTED；runner 随后发 RUN_INTERRUPTED 并激活票据（见[runner 执行外壳](#runner-执行外壳)第 5 步）。
  5. 恢复时：解码快照；解码失败、图版本不一致或 run_id 为 0 都报错。由快照重建状态（只含建议卡、作业单、票据，不再打开知识快照），恢复压缩状态到载体，发 RUN_RESUMED（ticket_id、order_id、epoch）。
- 结果与失败：恢复失败时节点返回错误，续跑失败（run 留在 RUNNING，见[审批后续跑](#审批后续跑)）。

### 节点 finalize

- 入口：图的第 13 个节点。代码：`internal/agent/graph/interrupt.go` 的 `Agent.finalize`。
- 前置条件：状态里有建议卡，否则报错。
- 执行步骤：
  1. 组装摘要：status COMPLETED、结局、advice_id、是否续跑（resume_epoch > 0）；拒答时加 refuse_reason 与 reason；有作业单、票据时加 order_id、ticket_id。
  2. 记 Info 日志，发 RUN_COMPLETED 事件（actor 为 system，观察型，失败只记 Warn）。
- 结果与失败：不调设备、不做复检。run 的 COMPLETED 由 runner 的 FinishRun 写入。

### 模型不可用降级

- 入口：classify、choose、explain 中模型重试后仍不可用（超时、5xx、连接错误）时调用。代码：`internal/agent/graph/fault.go` 的 `Agent.degrade`；文案与告警取 `policy/fault_matrix.yaml` 与 `configs/texts/zh-CN.yaml`。
- 前置条件：模型回复不合规不走这里（那是 VALIDATION_FAILED 拒答）。
- 执行步骤：
  1. 判断能否降级，以下任一成立则拒答 LLM_UNAVAILABLE（DEGRADED 事件留到 assemble 写）：
     - 没有命中知识条目；
     - 规则层没有决策句、没有判定过阈值或没有引用；
     - 植保作业类且候选集合为空。
  2. 已经降级过则不重复处理。
  3. 置降级标记：建议类型改为观察类；清空候选与所选药剂；撤销 compute 追加的数值与引用。
  4. 发 DEGRADED 事件（fault LLM_UNAVAILABLE、action RULE_FALLBACK、文案键），actor 为 system，step_id 为当前节点。该事件必须落库，写失败时节点返回错误，run 失败。
- 结果与失败：降级卡为观察类，不选药、不转作业单，置信度 0.5，degraded=true。

### 工具失败与缓存回落

- 入口：enrich 第 4、5 步与 assemble。代码：`internal/agent/graph/fault.go` 的 `Agent.noteToolFault` / `Agent.noteCacheFallback` / `Agent.emitRefusalFault`。
- 前置条件：工具结果已返回。
- 执行步骤：
  1. 网关在超时或上游错误时已尝试回落到 max_staleness 内的缓存（见[工具调用网关](#工具调用网关)），回落成功的结果来源为 cache、状态为 OK。
  2. 对 cache 来源的结果：照常使用，置「数据陈旧」标记（建议卡 degraded=true），发 DEGRADED(fault MCP_TIMEOUT、action CACHE_FALLBACK、staleness_sec、工具名)。写失败节点返回错误。
  3. 回落失败的工具错误（超时 / 上游）在 enrich 中拒答 DATA_MISSING 并记下工具名。
  4. assemble 组装拒答卡时写 DEGRADED(action REFUSE)：LLM_UNAVAILABLE 与 KB_MISS 拒答一律写；DATA_MISSING 只在记下了故障工具时写（空数据、非法返回不算故障降级）。写失败节点返回错误。
- 结果与失败：DEGRADED 事件经运行事件写入同事务投影为审计记录。

## 执行外壳组件

### 步骤记录与 trace 回调

- 入口：每次调图时挂上的两组回调。代码：`internal/agent/harness/runner/runner.go` 的 `Runner.handler`，`internal/agent/harness/callbacks/recorder.go`、`llm.go`、`tracer.go`；`internal/repository/run.go` 的 `RunRepo.SaveStep`。
- 前置条件：ctx 里有 run 标识。只处理节点级回调，图级回调跳过。
- 执行步骤：
  1. runner 步骤回调（step_id 与 node 都取节点名）：
     - 开始时写 STARTED，结束时写 COMPLETED，出错时写 FAILED 并带错误码（错误自带码时取之，否则 NODE_ERROR）；
     - SQL 为 `INSERT INTO run_step (...) VALUES (...) AS new ON DUPLICATE KEY UPDATE status, ended_at, error_code, row_ver+1`，续跑时同名节点覆盖同一行；
     - 审批中断引起的「出错」不记 FAILED，该步保持 STARTED；
     - 执行权丢失后不再写；写失败记入外壳，执行体结束后按执行错误处理，run 失败。
  2. trace 回调：节点开始发 STEP_STARTED，结束发 STEP_ENDED；中断结束记为 STEP_ENDED(INTERRUPTED)。
  3. 模型调用观测：每次调用把入参与回复存为 LLM_IO 原文（名为 `llm-{step}-{task}-{摘要前缀}`），再发 LLM_CALL_END（raw_object_id、token 数、耗时、错误码）。原文存储失败只记 Warn，事件照发。
  4. 日志 tracer 输出结构化日志，属性经脱敏。
- 结果与失败：run_step 是续跑与运行详情的依据；事件写入见[运行事件写入](#运行事件写入)。

### 检查点存储

- 入口：Eino 在 await_approval 中断时调 Set，续跑时调 Get。代码：`internal/agent/harness/checkpoint/checkpoint.go`（checkpoint_id 为 run_id 十进制），`internal/repository/checkpoint.go` 的 `CheckpointRepo.Set` / `CheckpointRepo.Get`。
- 前置条件：ctx 里有检查点归属（Scope、run_id），且与 checkpoint_id 一致，否则报 bad checkpoint。Set 还要求归属带中断类型（续跑时 ctx 不带中断类型，再次 Set 会被拒绝）。
- 执行步骤：
  1. Set：
     1. payload 不超过 256KB 时直接入库；超过时先写 MinIO（raw_object.kind=CHECKPOINT，名为 `ckpt-{run_id}-{毫秒}`），库里只存 raw_object_id。未装配原文存储时报错。
     2. 一个事务内：`SELECT status, row_ver FROM agent_run`，不是 RUNNING 即非法迁移；`INSERT INTO run_checkpoint`（seq 取当前最大值加 1，带 payload 或 raw_object_id、size_bytes）。
     3. 同一事务把 run 置 INTERRUPTED：载体里有压缩状态时执行 `UPDATE agent_run SET compaction_state, compaction_count, status, row_ver+1 WHERE ... AND row_ver=?`，再补写 interrupt_type；否则执行 `UPDATE agent_run SET status='INTERRUPTED', interrupt_type=?, row_ver=row_ver+1 WHERE ... AND status='RUNNING' AND row_ver=?`。影响 0 行即并发冲突。
     4. 同一事务 `DELETE FROM run_checkpoint WHERE ... AND seq <= 当前 seq - 3`，每个 run 只留最近 3 份。
  2. Get：`SELECT payload, raw_object_id FROM run_checkpoint ... ORDER BY seq DESC LIMIT 1`；没有返回「无检查点」；有 raw_object_id 时按它查 object_key，从 MinIO 读回。
- 结果与失败：Set 失败时图返回错误，run 以 GRAPH_ERROR 失败。
- 注：`internal/agent/harness/checkpoint/doc.go` 写的是「将在 L6 实现」，代码实际已实现。

### 审批后续跑

- 入口：审批通过后由审批决定服务（DecisionService）异步调用，或由扫描任务补偿调用，均经计数包装 ObservedResumer（触发方见 03）。代码：`internal/agent/graph/agent.go` 的 `Agent.Resume`，`internal/agent/harness/runner/runner.go` 的 `Runner.Resume`，`internal/repository/runresume.go` 的 `RunRepo.MarkResumed`。
- 前置条件：装配了检查点存储与续跑存储，否则返回「不支持续跑」。
- 执行步骤：
  1. ctx 放入只含 Scope 与 run_id 的检查点归属，Get 确认检查点存在；不存在返回「不可续跑」，不整图重跑。
  2. 挂压缩载体（restore 时恢复压缩状态）。
  3. runner 取 run 锁（同[runner 执行外壳](#runner-执行外壳)第 1 步）。
  4. MarkResumed，一个事务内：
     - `SELECT status, interrupt_type, graph_version, resume_epoch, sys_retry, row_ver FROM agent_run`；须为 INTERRUPTED、有中断类型、图版本一致；
     - WAIT_APPROVAL 要求 `SELECT COUNT(*) FROM approval_ticket WHERE ... run_id=? AND ticket_kind='ORDER' AND status='APPROVED'` 大于 0；SYSTEM_ERROR 要求 sys_retry 不超过 3；其他类型不可续；
     - `UPDATE agent_run SET status='RUNNING', interrupt_type=NULL, resume_epoch=resume_epoch+1, row_ver+1 WHERE ... AND status='INTERRUPTED' AND row_ver=?`，返回新 epoch。
     - 任一不满足返回错误，run 保持 INTERRUPTED。
  5. 在外壳内以空输入调图：Eino 按检查点恢复，classify 到 to_order 不重跑，await_approval 走恢复分支，finalize 发 RUN_COMPLETED。
  6. 收尾同 runner 执行外壳，区别是执行出错时不写 FAILED，run 留在 RUNNING、心跳停止，由 stuck_run 扫描处理（见 03）。
- 结果与失败：成功时 run 为 COMPLETED，返回建议卡、作业单、票据。不调设备、不做复检。

### 记忆注入

- 入口：[节点 explain](#节点-explain)第 2 步。代码：`internal/agent/graph/memory.go` 的 `Agent.memoryHints`，`internal/agent/harness/memory/memory.go` 的 `Store.Recent`，`internal/repository/memory.go` 的 `MemoryRepo`。
- 前置条件：配置 `memory.enabled`（默认 true，环境变量 AS_MEMORY_ENABLED 可关）；episodic_limit 5、rune_budget 600。
- 执行步骤：
  1. Scope 缺租户或农场时报错（先于开关判断）。开关关时返回空，不读库。
  2. 按相关性依次收集：
     - 工作记忆：ctx 里绑定本农场的当前会话条目（主链路没有注入，实际为空）；
     - 画像：`SELECT ... FROM field_profile f JOIN farm_profile p ... WHERE f.tenant_id=? AND f.farm_id=? AND f.id=?`，渲染为「农场名（区域），常种作物；地块编号种某作物，播种日期，面积，偏好」一句话；

  3. 累计字符超过 600 时，从最不相关的一端截掉。
  4. 回到 explain：每条去掉数字后加前缀「历史记录：」，空的丢弃，追加到理由里。读取失败记 Warn，按无记忆继续。

### 长对话压缩

- 入口：主链路第一次调模型时（通常是 classify）。代码：`internal/agent/graph/compaction.go` 的 `Agent.llmInput` / `Agent.assembleSession`，`internal/agent/harness/compaction/engine.go` 的 `Engine.Assemble`，`internal/repository/run_l6_session.go` 的 `RunRepo.LoadSession`。
- 前置条件：装配了压缩引擎（ctx 挂了载体）；不是下发前复检；开关 enable_compaction 为开（读失败按关）。参数：trigger_tokens 1200、keep_recent_turns 4、summary_max_tokens 300、max_block_tokens 6000、summary_timeout 10 秒。
- 执行步骤：
  1. 每个 run 只组装一次，结果缓存，之后每次模型调用复用。
  2. 读会话原料（每次读出后对自由文本脱敏）：
     - 用递归 CTE 沿 prev_run_id 由早到晚取会话链，最多 32 个 run；链被截断时，另按同地块同用户汇总更早 run 的问题与作业单；
     - 轮次：链上本 run 之前每个 run 一轮，问题取 RUN_STARTED 事件，回答取建议卡结论；
     - 业务事实：建议卡（含作业窗口）、作业单与最新审批票及驳回原因、未被取代的时效实测、引用的 kb_id；
     - 已有压缩状态取本 run 的 compaction_state（建 run 时从上一轮复制）。
  3. 没有轮次也没有压缩状态（首轮）时不加会话块。
  4. 构造会话块：白名单事实（不压缩、不裁剪）加上一次摘要之后的轮次。摘要边界不在本会话轮次内时按无压缩处理。
  5. 若可压缩部分（摘要加轮次）估算超过 1200 token 且轮次多于 4 轮：把最近 4 轮之前的轮次交摘要器（10 秒超时，摘要须非空、带版本且不超过 300 token）生成新摘要。
  6. 带摘要的会话块：先裁到 6000 token（由早到晚丢轮次，再丢摘要），再从源表重读一次原料做白名单断言；通过后，若本次新压缩了轮次，把被压缩原文写 MinIO（raw_object.kind=COMPACTED_MSGS，名为 `compacted-{run_id}-until-{step_id}`），记入状态的原文引用与历史。
  7. 摘要、重读、断言、转存任一失败都放弃压缩，退回完整上下文（白名单事实加全部轮次，同样裁到 6000 token），不写新状态。
  8. 回到图：放弃、裁剪、链截断各发一条 COMPACTION_FAILED（kind 区分，原因脱敏）；新压缩发 COMPACTION_APPLIED（前后 token 数），压缩次数记 1；压缩状态放进载体，中断事务或终态 UPDATE 写 agent_run.compaction_state / compaction_count。
  9. 会话块以 session 键追加到模型入参末尾；入参不是 JSON 对象或已有该键时记 Warn，用原入参。
- 结果与失败：压缩任何失败都不让 run 失败。每次模型调用后 `AddTokens` 累计 agent_run 的 token 数（为 0 不写，失败记 Warn）。
- 注：`engine.go` 里 plain 的注释写的是「超过硬上限时裁剪原文轮次（Failed 记裁剪）」，代码实际把裁剪说明放在 Trimmed，Failed 只在编码失败时填。
- 注：生产装配的摘要器是确定性 stub（Deterministic），不调模型。

### 规则下沉与影子比对

- 入口：explain 前读开关、explain 后比对、validate 拒收、persist 落库。代码：`internal/agent/graph/rules_offload.go`、`rules_offload_inject.go`。
- 前置条件：三个开关 rule_offload.operation_window / tank_mix / pest_priority，取值 off / shadow / on，默认 off；读失败按 off。
- 执行步骤：
  1. 规则结论（三档都算，只对出卡的建议）：
     - 作业窗口：规则层判定过的施药 / 施肥窗口硬约束（不含数据时效类）汇成窗口结论，时段为现在到现在加作业窗口时长；
     - 混用禁忌：所选药剂及分组表里不得同桶的药剂，单桶上限取 common/safety/mixing 的参数；
     - 虫情优先级：植保非安全类、虫情调查可用、至少两个防治对象有判定时，按实测超阈倍数给出对象排序。
  2. on 档：把规则结论作为约束注入 explain 入参。choose 不注入。
  3. shadow 档：不注入；模型给出结论后（降级模板不算）用与拒收相同的检查比对，每项记一行差异（冲突分句脱敏），persist 时同事务写 rule_shadow_diff 并发 RULE_SHADOW_DIFF。
  4. 三档下 validate 都拒收与规则结论冲突的模型原文。
- 结果与失败：rule_shadow_diff 按 rule_offload.shadow_diff_days（180 天）由 worker 按农场逐项分批删除（每批 5000 行）。

### 知识加载

- 执行步骤：
  1. 校验情境：作物与区域必填，生育期须在标准生育期表内，否则返回错误（不算 KB_MISS）。
  2. 过滤：逐条检查快照里的条目，全部满足才算命中。
     - 作物等于情境作物，或条目作物为 `*`；
     - 区域等于农场区域码，或条目区域为 `*` 且位于 `common/` 下；
     - 条目类别包含情境一级类；情境给了子类 Topic 时，须在条目主题内（主链路只传排序主题 RankTopic，它不参与过滤）；
     - 生育期匹配；防治对象为空或相等；
     - 已废弃的条目排除。
  3. 若命中里没有作物专属或防治对象专属的条目（锚定条目），返回 KB_MISS。
  4. 必加：按策略的 must_include 先选条目，入选原因记 MUST_INCLUDE。必加条数超过 limit−1 时返回 ErrMustIncludeOverLimit。
  5. 排序：其余命中按策略的排序键依次比较，全部相同时按 kb_id 升序。入选原因：`common/` 下记 COMMON，其他记 RANKED。
  6. 若有必加条目但其中没有专属条目，最后一个名额留给排序第一的专属条目。
  7. 截断到策略的 limit 条，返回条目、名次与入选原因。
- 两个策略：
  - v0（`configs/loader/v0.yaml`）：limit 8，排序键 authority、specificity，无必加。
  - v1：limit 10，排序键 authority、topic_match、specificity、stage_match、version；必加规则为植保类加 `common/safety.md` 与 `common/operation_window.md`，施肥类加 `{作物}/fertilization.md`（只取公式）。
- 结果与失败：返回入选条目；KB_MISS 与必加超限由调用方处理（见[节点 load_knowledge](#节点-load_knowledge)）。

### 计算器

- 入口：节点 candidates（候选与判定）和 compute（数值）调用。代码：`internal/agent/calc` 下 `calc.go`、`calculator.go`、`pesticide.go`、`fertilizer.go`、`window.go`、`tankmix.go`、`priority.go`。
- 前置条件：构造时必须能在知识快照里找到以下公式，缺任一条构造失败：
  - dosage-dilution 的 total_dose、dilution_ratio、dose_from_dilution；
  - phi 的 last_spray_date、earliest_harvest；
  - n-budget 的 n_for_stage、product_per_mu、product_total；
  - water-volume 的 water_m3。
- 执行步骤：
  1. 参数只取知识条目 front-matter 与农药登记表，不由模型提供。
  2. 按调用的函数计算：药剂候选（Candidates）、登记信息（Registration）、亩用量（Dosage）、喷液量（SprayVolume）、稀释倍数（Dilution）、由倍数反算用量（DoseFromDilution）、安全间隔期日期（PHIDate）、施肥量（Fertilizer）、灌水量（WaterVolume）、作业窗口（OperationWindow）、桶混（TankMix）、虫情优先级（PestPriority）。
  3. 取整精度：亩用量 0.1、总量 0.1、稀释倍数 1、喷液量 0.1、氮量 0.01、亩施肥量 0.1、施肥总量 0.5、灌水量 1、天数 1。
  4. 每个结果带 Trace：输入值与公式标识 `kb_id@version#formula`，供引用与护栏核对。
  5. 输入超出条目给定范围时返回 ErrOutOfRange，不截到边界。
- 结果与失败：业务错误为 ErrNoCandidates、ErrNotRegistered、ErrOutOfRange、ErrUnitMismatch、ErrPHINotApplicable、ErrMissingParam，由 candidates 归为 KB_MISS 或 DATA_MISSING（见[节点 candidates](#节点-candidates)）。
- 注：桶混分组表在代码中标为待专家审核的草稿。

### 输出护栏

- 入口：节点 validate 第 2 步。代码：`internal/agent/guardrail/validator.go` 的 `OutputValidator.Validate`，否定范围判断在 `internal/agent/guardrail/claim.go`。
- 前置条件：建议卡已组装。
- 执行步骤：
  1. 卡为空 → schema 不通过。
  2. schema：用内嵌的 advice_card 契约校验卡的副本（副本的 advice_id 由 0 改为 1，因为落库前还没有 id）。不通过 → schema。
  3. 若卡不是 ADVICE 结局，只做 schema，结束。
  4. 否则依次检查，遇到第一项不通过就返回：
     - citation：结论、每条理由、每个数值至少有一条引用，引用不指向不存在的字段；知识引用须在快照里且未废弃；实测引用须带 tool_call_id。
     - number：占位符序号在范围内，模型文本里没有裸数字；每个计算结果有 Trace 且是有限数；卡上数值与计算结果逐项一致（字段、取整后数值、单位）。
     - product：卡上候选是规则候选的子集，所选药剂在候选内；植保作业卡必须选药。
     - 规则下沉项：作业窗口、桶混、优先级与规则结论冲突时不通过，检查项名取各下沉项名。
     - 药剂点名：模型文本不得推荐候选以外的药剂。否定句范围内的提及、对过去用药的陈述、对记忆内容的复述不算推荐。
- 结果与失败：通过返回空；不通过返回检查项名（schema、citation、number、product 或下沉项名）与详情。不修复。
- 注：`guardrail` 包注释列的是 4 项检查，代码实际 Validate 跑 6 项（另有规则下沉项与药剂点名）。

### 约束检查

- 入口：节点 to_order 第 4 步（PRE_APPROVAL）与[下发前复检](#下发前复检)（PRE_DISPATCH）。代码：`internal/agent/graph/constraint.go` 的 `Agent.constraintChecks`，`internal/agent/guardrail/constraint/registry.go` 的 `Registry.Required` / `Registry.Evaluate`。
- 前置条件：有作业单（作业类型、设备类型、下发方式、时间窗、payload）与 run 的工具结果、知识快照。
- 执行步骤：
  1. 组装输入：每个工具结果作为一个数据来源（采集时刻取数据里的 collected_at，没有时取当前时间减 data_freshness_sec）、知识快照、面积、所选药剂的登记信息与安全间隔期、本地同地块近期 REAL 作业单（回看最长安全间隔期与重复作业窗口；读不到时 repeat_operation 判失败）。
  2. 按阶段、作业类型、设备类型取必检集合：
     - 植保：已登记、风速、降雨、温度、安全间隔期、重复作业、漂移；无人机另加禁飞区；
     - 施肥：用喷施设备时查风速、降雨、温度、重复作业（无人机另加禁飞区）；人工撒施只查降雨与重复作业；
     - 灌溉：重复作业；
     - PRE_DISPATCH 且为无人机：另加电量与载重。
  3. 若必检集合为空 → 输出一行 no_constraint_plan 失败行，结束。
  4. 按注册顺序逐项判定。必检项未注册 → 失败行。数据缺失、过期或缺 tool_call_id → passed=false。阈值只取知识条目。
  5. 每行含 rule_id、passed、observed（值、单位、来源、采集时刻、tool_call_id）、threshold（值、单位、`kb:<kb_id>@<version>`）。
- 结果与失败：返回校验行，attempt 留 0，由落库方填写（开票取 ticket_seq，复检取 recheck_seq）。本函数不写库；PRE_APPROVAL 行由 Gate.Open 写入 constraint_check，后续见 [03-审批与工单下发](03-审批与工单下发.md)。

### 脱敏

- 入口：四个出口各调一次。代码：`internal/agent/guardrail/pii/pii.go` 的 `Mask` / `ForModelText`，`json.go` 的 `MaskJSON` / `ForModel`，`handler.go` 的日志 Handler 与 `MaskAttrs`。
- 前置条件：无。脱敏规则只在 pii 包实现；repository 层不脱敏，由写入方先处理。
- 执行步骤：
  1. 规范化：全角数字转半角。长度 32、40、64 的十六进制摘要整段跳过。
  2. 识别并掩码（保留前 3 位与后 4 位）：
     - 手机号：1[3-9] 开头的 11 位，可带 86 前缀或按 3-4-4 分隔；中文数字写的手机号也识别；
     - 身份证：18 位（末位可为 X）或 15 位，也识别 6-8-4、6-6-3 分隔；
     - 账号：16-19 位数字，也识别每 4 位分组。
  3. 识别精确坐标：经纬度成对出现（逗号分隔时小数至少 3 位，空白分隔时小数至少 4 位，且有一个整数部分不小于 10）、带「经度 / 纬度」标签的坐标、JSON 里的坐标键。
  4. 按出口处理坐标：
     - Mask / MaskJSON（日志、写 run_event / tool_call / audit_log 前）：截断到 0.01°；
     - ForModelText / ForModel（模型入参）：整体替换为地块级引用 FieldRef；
     - 日志 Handler 与 MaskAttrs（OTel 属性）：同 Mask。
- 结果与失败：返回脱敏后的文本或 JSON，不报错。

### 模型调用

- 入口：classify、choose、explain 与长对话压缩调用。代码：`internal/agent/llm/llm.go` 的 `Client.Do`，`prompt.go` 的 `Prompts.System`，`observe.go`；观测回调在 `internal/agent/harness/callbacks/llm.go` 的 `Recorder.ObserveLLM`。
- 前置条件：provider 为 openai 或 stub（`configs/model.yaml`）。档位 standard：temperature 0.1、max_tokens 1024、单次超时 20 秒、最多重试 1 次、退避 200 毫秒 × 第几次重试。
- 执行步骤：
  1. 档位不存在 → 返回未知档位错误。
  2. system 提示词：`prompts/{version}` 下按「角色 → 边界 → 输出格式 → 拒答」分层拼接，再接 `tasks/{task}.md`。
  3. user 消息为 `{"task","input"}` 的 JSON，默认经 ForModel 脱敏。
  4. 若装配了限流器：读失败或不放行都返回模型不可用。
  5. 逐次尝试：每次独立超时调模型，回复去掉代码围栏后解码为 JSON，解码失败记为回复不合规。任何错误都重试；ctx 取消立即返回 ctx 错误。
  6. 用尽重试：最后一次是回复不合规 → ErrBadReply；否则 → ErrUnavailable。
  7. 调用结束交给观测回调：模型输入与每次尝试的原始回复存为 LLM_IO 原文，再发 LLM_CALL_END（任务、档位、状态、token、耗时、错误码）。不持有执行权时不记录。
- 结果与失败：返回本次（含重试）的 token 用量。调用方把 ErrUnavailable 走[模型不可用降级](#模型不可用降级)，ErrBadReply 拒答 VALIDATION_FAILED。
- 注：`configs/model.yaml` 配了 rate_per_min 60，`llm.go` 也写了限流分支，代码实际图装配（`internal/app/agent.go`）没有传限流器，第 4 步不执行。

### 工具调用网关

- 入口：节点 enrich 取数与复检取设备状态时经 `Agent.callTool` 调用（step_id 固定为 enrich，带 resume_epoch 与复检标记）。代码：`internal/agent/tools/mcp/call.go` 的 `Gateway.Call` / `Gateway.fetch` / `Gateway.fallback`，`dedup.go` 的 `Gateway.claim`，`invoke.go` 的 `Gateway.invoke`，`finish.go` 的 `Gateway.finish`，`cacherule.go` 的 `Bypass`。
- 前置条件：工具已在注册表（`configs/tools.yaml`）登记并通过[工具策略](#工具策略)启动自检。默认单次超时 3 秒。
- 执行步骤：
  1. ctx 已取消 → 返回错误。
  2. 算 call_key：run_id、step_id、工具名、规范化入参、调用序号、epoch（只有时效工具带 epoch，非时效工具记 0）。
  3. 策略前置检查（policy.Before）不通过 → 记 REJECTED。若是 actuate 工具，另记 Error 日志并发告警 model_actuate。
  4. 租户校验：入参带 field_id 或 device_id 时须属于本租户本农场。入参畸形 → REJECTED；越界 → 写 CROSS_FARM_DENIED 审计，记 SCOPE_DENIED。
  5. 去重，抢占 Redis 键 `idem:tool:{call_key}`（PENDING 占位 TTL 为超时 × 尝试次数，约 9 秒）：
     - 抢到占位：再查 tool_call 是否已有同 call_key 的 OK 行，有则把键改写为 DONE 并复用该行；
     - 命中 DONE：回查 OK 行复用；行不存在则删键重抢；
     - 命中 PENDING：轮询等到占位 TTL，仍未完成则按 MySQL 判断，没有就不占位直接调用；
     - Redis 出错：按 MySQL 判断。
  6. 若复用了 OK 行：从 MinIO 原文取回未脱敏结果，新鲜度按 collected_at 重算后返回，结束。取不回原文，或复检时命中的是缓存回落结果，则重新调用。
  7. 读缓存：工具可缓存且本次不绕过时，读 `cache:mcp:{tool}:{tenant}:{farm}:{入参摘要}`，写入时刻在新鲜期内（weather 10 分钟、crop 24 小时；field、device 不缓存）则直接用。复检、pre_dispatch 步骤、epoch>0 的时效工具一律绕过缓存且不回落。
  8. 调用 Server：每次独立超时；read 且幂等的工具遇超时或上游错误再试 2 次。输出须是 JSON 对象且符合输出 schema，否则 MALFORMED。错误归为 TIMEOUT、EMPTY、MALFORMED、UPSTREAM、REJECTED。
  9. 若超时或上游错误且本次可用缓存：取缓存，按 collected_at 算陈旧度，在最大陈旧度内（weather 1 小时、crop 24 小时）则回落，来源记 cache、data_freshness_sec 为陈旧度；否则保留原失败。
  10. 若 Server 返回 SCOPE_DENIED：写 CROSS_FARM_DENIED 审计（target 为 device:{id} 或 tool:{name}）。
  11. 收尾（finish）：
      - 策略后置检查：OK 但缺数据源降为 MALFORMED；失败缺错误码补 UPSTREAM；
      - OK 时原始结果写 MinIO（`tool-{call_key}`），失败只记 Warn，raw_object_id 留空；
      - 写 tool_call 一行（状态、错误码、来源、新鲜度、脱敏摘要、耗时、policy_level、epoch）；
      - OK 时把占位改写为 `DONE:{id}`（24 小时），真实调用的结果写缓存（TTL 为最大陈旧度）；失败时删除占位；
      - 输出 trace 日志并发 TOOL_CALL_END。
- 结果与失败：返回 tool_call_id、状态、来源、新鲜度与数据。工具失败不返回 error，由节点按状态处理；只有 ctx 取消、审计写失败或存储失败返回 error（并删除占位）。

### 工具策略

- 入口：启动时网关构造与每次调用的前后置检查。代码：`internal/agent/harness/policy/toolpolicy.go` 的 `Load` / `ToolPolicy.Check` / `ToolPolicy.Bind`，`internal/agent/harness/policy/policy.go` 的 `Policy.Before` / `Policy.After`；策略文件 `policy/tool_policy.yaml`。
- 前置条件：策略文件 version 为 1。工具等级：weather、crop、field 全部与 device.list、device.status 为 read；device.dry_run、device.dispatch 为 actuate。
- 执行步骤：
  1. 加载：版本不符、未知字段、工具名为空或重名、等级不是 read / write / actuate 都报错。
  2. 启动自检，任一问题即启动失败：
     - 注册表工具未在策略中声明等级或注册表等级为空；
     - 两边等级不一致；
     - 注册表（模型可见工具集）中出现 actuate 工具；
     - 策略里的 read / write 工具不在注册表。
  3. 构造调用期策略表，网关只允许 read 级。
  4. 调用前（Before）：actuate 工具（已注册或只在策略中声明）一律拒绝；未知工具、等级未声明、等级不被允许、入参不是 JSON 对象或不符合入参 schema 都拒绝。空入参视为 `{}`。
  5. 调用后（After）：修正结果必备字段（见网关第 11 步）。
- 结果与失败：Before 拒绝在网关记 REJECTED。actuate 只允许作业单状态机在 APPROVED 后经设备适配器调用，见 03。

### 下发前复检

- 入口：下发 worker 在下发前调 `RecheckService.PreDispatch`，它再调 agent 的复检（处置部分见 03）。代码：`internal/agent/graph/recheck.go` 的 `Agent.Recheck` / `recheckVerdict` / `recheckOrder`，`internal/agent/graph/constraint.go` 的 `Agent.deviceSources`。
- 前置条件：请求带原 run_id、原问题、原建议卡、作业单要素和新 epoch（须大于 0，由调用方分配）。缺 run_id 或 epoch 不大于 0 → 返回入参错误。
- 执行步骤：
  1. 按原问题新建图状态，ctx 带新 epoch 与复检标记。
  2. 依次重跑 classify → enrich → load_knowledge → candidates。所有工具调用不读缓存、不回落；原结果是缓存回落时也重取。不经 runner，不写 run_step、建议卡、作业单，不调设备；图内事件因不持有执行权而跳过。网关照常写 tool_call 行。
  3. 比对结论（recheckVerdict）：
     - 拒答为 LLM_UNAVAILABLE 或 DATA_MISSING → 返回 ErrRecheckInconclusive（无结论），结束；
     - 其他拒答、一级类与原卡不同、不再是作业类、原选药剂不在新候选内 → 结论变化（Changed）；
     - 否则结论未变。
  4. 定校验用的作业单：调用方给了作业单就用它；否则按复检的规则层结论推断作业类型、设备与地块。
  5. 若为无人机：只按作业单 payload.device_id 调一次 device.status 并入数据来源。payload 没有 device_id 时不调，电量与载重两项随后判失败。
  6. 跑 PRE_DISPATCH 约束检查（见[约束检查](#约束检查)），植保作业带原选药剂，其他作业不带。结论变化时也照常检查。
  7. 记 Info 日志（run_id、epoch、是否变化、详情）。
- 结果与失败：返回是否变化、详情与 PRE_DISPATCH 校验行。工具或节点内部错误返回 error。取消原单、新建 run、写 constraint_check(PRE_DISPATCH) 由调用方处理，后续见 [03-审批与工单下发](03-审批与工单下发.md)。

### 运行事件写入

- 入口：图内事件、步骤与模型回调、网关、runner 与业务事务都经此写 run_event。代码：`internal/repository/event.go` 的 `EventRepo.AppendTx`，`internal/repository/eventsink.go` 的 `EventSink.Emit`，`internal/repository/audit.go` 的 `ProjectAudit`，`internal/agent/graph/events.go` 的 `Agent.emitAs` / `Agent.emitStrict`；service 层用 `internal/service/observe.go` 的 `ObservedEvents` / `ObservedEventSink` 包一层，事件提交后交给观测器（回滚的不计）。
- 前置条件：事件有租户与农场，event_type 已登记，否则返回错误。
- 执行步骤：
  1. 图内事件：未装配事件写入或已失去执行权（含复检）时跳过。payload 编码后补齐租户、农场、run_id 与时间，用不随请求取消的 ctx 发送。
     - 观测类（RUN_STARTED、KB_LOADED、ADVICE_READY、RUN_RESUMED、RUN_COMPLETED）走 emitAs：写失败只记 Warn；
     - 必须落库的（DEGRADED、VALIDATION_FAILED 等）走 emitStrict：写失败交给节点，节点返回错误。
  2. 图内事件经 EventSink.Emit 各开一个短事务；业务事务内的事件直接调 AppendTx。
  3. AppendTx 在调用方事务内：
     1. 投影审计：事件类型在投影表里时解析 payload 生成审计记录，payload 为空或解析失败返回错误；
     2. 分配序号：`UPDATE agent_run SET event_seq = LAST_INSERT_ID(event_seq + 1) WHERE tenant_id, farm_id, id`，影响 0 行返回 run 不存在；
     3. `INSERT INTO run_event (..., seq, ...) VALUES (..., LAST_INSERT_ID(), ...)`；
     4. 需投影时同事务写 audit_log；
     5. 登记提交后动作：PUBLISH `sse:run:{run_id}`（消息含 run_id、seq、类型、step_id、tool_call_id、actor、payload、时间），失败只记 Warn。事务不是 repository 开的则不发布并记 Warn。
  4. 投影表：RUN_STARTED→ASK，TOOL_CALL_END→TOOL_CALL，KB_LOADED→KB_LOAD，LLM_CALL_END→LLM_CALL，VALIDATION_FAILED 与 ADVICE_READY→VALIDATE，APPROVAL_OPEN / APPROVAL_PENDING / APPROVAL_DECIDED / CONSTRAINT_BLOCKED→APPROVAL，ORDER_TRANSITION→ORDER_TRANSITION，DISPATCHED→DISPATCH，DEGRADED→DEGRADED。其他类型不投影。审计链细节见 04。
- 结果与失败：返回分配的 seq。payload 文本由写入方先经 Mask 脱敏。

### 运行事件 SSE

- 入口：`GET /api/v1/farms/:farm_id/runs/:run_id/events`，需 OpAdviceRead；FarmAuth 只在这条路由接受 `?access_token=`。代码：`internal/controller/events.go` 的 `EventsHandler`，`internal/service/events.go` 的 `EventService.Stream`。
- 前置条件：run_id 为正整数，否则 400。游标取请求头 Last-Event-ID，没有时取 `?last_event_id=`，都没有从 0 开始；不是非负整数 → 400。
- 执行步骤：
  1. 先 SUBSCRIBE `sse:run:{run_id}`（订阅生效后消息进缓冲）。
  2. 读 run 状态做归属校验（限定租户与农场）。查不到 → 403 并记 RESOURCE_NOT_IN_SCOPE（target run:{id}），此前不写任何帧。
  3. 补读：读 run_event 中 seq 大于游标的事件，逐条推送并前移游标。
  4. 若补读中推出了 RUN_COMPLETED、RUN_FAILED 或 RUN_INTERRUPTED，或 run 已是终态或 INTERRUPTED，发 `event: end` 后返回。
  5. 否则循环：
     - 每 15 秒发一行 `: ping` 保活；
     - 收到订阅消息：不是本 run 或 seq 不大于游标的丢弃；seq 跳号时先补读；否则直接推送；
     - 推出结束类事件后发 end 并返回；
     - 请求取消或服务停机时直接返回（停机不发 end，客户端按 Last-Event-ID 重连）；订阅被关闭返回错误。
  6. 帧格式：`id: {seq}`、`event: {event_type}`、`data: {seq, event_type, step_id, tool_call_id, actor_type, payload, created_at}`，每帧 flush。响应头 text/event-stream、no-cache、X-Accel-Buffering: no。
- 结果与失败：首帧之前的错误按 JSON 错误码返回；之后的错误只能断开连接，错误挂到 gin 错误链。
- 注：流在 RUN_INTERRUPTED 时就结束，审批续跑之后的事件需客户端重新连接才能收到。

### 运行详情

- 入口：`GET /api/v1/farms/:farm_id/runs/:run_id`，需 OpAdviceRead。代码：`internal/controller/rundetail.go` 的 `RunDetailHandler`，`internal/service/rundetail.go` 的 `RunDetailService.Get`，`internal/repository/rundetail.go` 的 `RunDetailRepo.Load`。
- 前置条件：run_id 非 0。
- 执行步骤：
  1. 读 run 摘要（`agent_run` 按 tenant_id、farm_id、id），查不到 → 403 并记 RESOURCE_NOT_IN_SCOPE。
  2. 读建议卡（没有不报错）。
  3. 依次读本 run 的 run_step、run_event、tool_call、approval_ticket、approval_decision、work_order、work_order_transition、audit_log，全部限定租户与农场，任一失败返回错误。
  4. 组装（纯函数）：
     - question：RUN_STARTED 的 payload（已脱敏）；
     - steps：按 run_step 顺序，再追加只在事件或工具调用里出现的 step；每步挂 tool_call（按 tool_call_id 关联 TOOL_CALL_END）、LLM_CALL_END 与其余事件 seq；step_id 为空的事件归到 run 级伪 step；
     - 模型调用的 raw_object_id：取 audit_log 中 LLM_CALL 行按序对应，条数与 LLM_CALL_END 不等时不关联；
     - evidence：KB_LOADED 列表与建议卡引用；
     - approvals：票据及其决策；execution：作业单及其迁移、DISPATCHED 事件；
     - timeline 与 audit 原样返回；payload 解析失败的事件记入 warnings。
- 结果与失败：返回完整链路。除 run 本身外，其余表缺数据不报错。
- 注：`internal/service/ask.go` 里的 `AskService.GetRun` 注释写的是 GET /runs/{run_id} 的结果，代码实际该路由由 RunDetailService 处理，GetRun 没有生产调用方。

### 原文读取

- 入口：`GET /api/v1/farms/:farm_id/runs/:run_id/raw/:raw_id`，需 OpRawRead。代码：`internal/controller/audit.go` 的 `RawHandler`，`internal/service/audit.go` 的 `AuditService.ReadRaw` / `AuditService.deny`。
- 前置条件：run_id、raw_id 为正整数，否则 400。原文来自主链路写入的 raw_object（模型输入输出 LLM_IO、工具原始结果、检查点溢出、被压缩的原文）。
- 执行步骤：
  1. 角色不具备 OpRawRead → 拒绝 ROLE_INSUFFICIENT（Authorize 中间件已先拦一次，见 01）。
  2. 一个事务内：
     1. 按租户、农场读 raw_object 行。不存在 → 拒绝 RAW_NOT_FOUND；
     2. 行的 run_id 与路径不一致 → 拒绝 RUN_MISMATCH；
     3. 已过保留期 → 拒绝 RAW_EXPIRED（归属核对通过后才判，不向别的 run 暴露对象状态）；
     4. 对 MinIO 对象签发 5 分钟预签名 GET URL；
     5. 同事务写 audit_log RAW_READ / OK（payload 含 raw_id、run_id、kind、过期时间），敏感操作留痕在同事务追加，见 04。
  3. 若被拒绝：在业务事务之外单独写 RAW_READ / DENIED（带拒绝码），审计写失败记 Error 并一并返回。
  4. 响应：成功 200 返回 `{raw_id, kind, url, expires_at}`，头 Cache-Control: no-store；过保留期 410「原文已过保留期」；其他拒绝 403，handler 另记一次 RESOURCE_NOT_IN_SCOPE（target raw:{id}）。
- 结果与失败：不存在与跨 run 都按 403 处理，不暴露对象是否存在。审计链与原文清理见 [04-审计与观测](04-审计与观测.md)。
- 注：一次 403 拒绝会写两条审计：service 写的 RAW_READ / DENIED，以及 controller 写的 RESOURCE_NOT_IN_SCOPE 拒绝审计。
