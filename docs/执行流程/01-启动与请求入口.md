# 01 启动与请求入口

## 本章概述

本章描述两个常驻进程（`cmd/server` 与 `cmd/worker`）如何读取配置、连接 MySQL / Redis / MinIO、经 `app.Build` 装配全部服务，以及收到退出信号后按什么顺序停下。
随后描述一个 HTTP 请求进入 server 后经过的通用链路：恢复、请求 id、农场鉴权、权限矩阵判定，以及被拒绝时写入的审计。
最后描述功能开关的读写与跨进程生效、一键关停核验、指标端口、网页外壳，以及 `cmd/migrate` 与 `cmd/devtoken` 两个辅助命令。
各后台循环与各业务接口的内部逻辑见其他章节，本章只说明它们在哪里启动、挂在哪条路由上。

### 进程启动公共部分

- 入口：被 `cmd/server` 与 `cmd/worker` 共同调用；代码：`internal/app/boot/boot.go` 的 `RegisterFlags`、`Open`、`Process.Close`。
- 前置条件：命令行参数已解析。参数缺省值如下：`-config configs/app.yaml`、`-env-file deploy/.env`、`-tools configs/tools.yaml`、`-model configs/model.yaml`、`-repo .`、`-taxonomy eval/taxonomy.yaml`、`-policy policy/tool_policy.yaml`、`-risk policy/risk_matrix.yaml`、`-permissions policy/permission_matrix.yaml`、`-devices configs/devices.yaml`、`-regulation policy/regulation_map.yaml`、`-notify-texts configs/texts/notify.zh-CN.yaml`；`-fault-matrix`、`-texts`、`-lexicon` 取 `app` 包里的缺省路径常量。
- 执行步骤（`Open`，严格按顺序；任一步失败即返回错误，进程退出）：
  1. 读配置 `config.Load`：用 viper 读 yaml，环境变量前缀为 `AS_`，键名中的点换成下划线。若密钥类键直接写在 yaml 里，则报 `ErrSecretInFile`；密钥只从环境变量或 `-env-file` 指定的 dotenv 文件取（文件不存在则只读环境变量）。随后校验 dispatch、approval、audit、metrics、alerts、eval、quality、compaction 等配置段。
  2. 要求以下密钥齐全：`mysql.password`、`redis.password`、`minio.access_key`、`minio.secret_key`、`auth.jwt_secret`。
  3. 校验保留期配置覆盖了全部原文类型（`Retention.RequireKinds`），缺任一类型的保留天数即失败。
  4. 读模型配置并选定对话模型（`config.LoadModel`、`app.ChatModel`）。provider 可被 `AS_MODEL_PROVIDER` 覆盖；若选 openai 却缺 `ONEAPI_*` 环境变量，则直接失败；stub 只有显式选择时才使用。这一步在连库之前完成。
  5. 读问题分类表（taxonomy），打开仓库内知识库的工作区快照，再加载知识加载策略文件（v0 / v1），校验必加规则。
  6. 构造日志器（按 `log.level`）、系统时钟、Redis 键前缀（`as:{env}:`）。
  7. 加载权限矩阵、故障降级矩阵与用户文案表、通知文案表。三者任一不合法即失败。
  8. 连 MySQL（GORM，按配置的最大连接数）。连 Redis 并执行 PING，PING 失败则关闭客户端后报错。
  9. 若 `eval_review.enabled` 为真，则要求 `eval_review.user` / `eval_review.password` 并用独立账号连评测库；否则不连，连接为空。
  10. 构造 MinIO 客户端（只构造，不发请求）。基于它构造原文存储（写 `raw_object` 表与原文 bucket，并按保留天数写 `expire_at`）与原文读取器。
  11. 构造指标观测器与告警出口（`app.NewObserve`），并把告警出口登记给审计仓储（审计封链失败时发 P0 告警）。
  12. 构造工具调用网关（见下文「工具网关装配」）。
  13. 依次加载审批风险矩阵、设备注册表配置、法规对照表（约束拦截）、地块历史回写端（若 `tools.yaml` 中地块服务为 real，则用「未接线」实现，回写时失败并告警；否则用内存实现）、长对话压缩词表。
  14. 调用 `app.Build`，主链路以工厂 `app.GraphAgent` 注入；看板目录固定为 `{repo}/web/amis`；原文预签名、HITL 检查点读取、L7 保留期删除与锚点存储、质量 / 归因 / 评审的 eval bucket 均由同一个 MinIO 客户端提供；设备回执密钥取 `device_receipt.secret`。详见[应用装配](#应用装配)。
  15. 记 Info 日志「advice graph ready」（含 provider、tier、prompt 版本）。
- 工具网关装配（`boot/tools.go` 的 `buildTools`）：读 `tools.yaml`，加载工具策略并与工具注册表比对（不一致即启动失败），构造 4 个 MCP Server，构造网关（Redis 幂等与缓存、`tool_call` 记录、地块归属守卫在越界时写 `CROSS_FARM_DENIED` 审计、PII 脱敏、告警），最后包一层指标观测。
- 结果与失败：成功返回 `Process`（含 App、配置、模型配置与三个连接）。失败时，已打开的 MySQL、Redis、评测库连接由 defer 依次关闭。`Process.Close` 先关 Redis，再关 MySQL，最后关评测库，错误合并返回。

### server 进程启动与退出

- 入口：CLI 命令 `server [boot 参数]`；代码：`cmd/server/main.go` 的 `run`、`serve`。
- 前置条件：MySQL、Redis 可连；已执行 `migrate up`；密钥已配置。
- 执行步骤：
  1. 登记并解析命令行参数，注册 SIGINT / SIGTERM 信号，收到信号时取消根 context。
  2. 调用[进程启动公共部分](#进程启动公共部分)的 `boot.Open`，并 defer 关闭连接。
  3. 构造鉴权服务 `a.NewAuth(auth.jwt_secret)`：它用 `user_role` 仓储做角色查询。若 JWT 密钥短于 32 字节，则返回 `ErrWeakSecret`，进程退出。
  4. 构造指标循环 `a.MetricsLoop(metrics.server_addr, metrics.path)`，见[指标监听](#指标监听)。
  5. 构造 HTTP 服务：监听 `http.addr`（缺省 `:8080`），处理器为 `a.Handler(auth)`（见[路由挂载总表](#路由挂载总表)），读请求头超时 5 秒。
  6. 进入 `serve`：
     1. 启动后台循环：`a.ServerLoops()`（只有 `flags`）加上指标循环，见[后台循环框架与循环清单](#后台循环框架与循环清单)。
     2. 登记 HTTP 关闭钩子 `EventStream.Shutdown`：服务关闭时关掉停止通道，所有正在推送的 SSE 连接随之返回。
     3. 在 goroutine 中开始监听，记日志「http listening」。
     4. 等待两件事之一：若监听出错，则返回「listen addr: 错误」；若根 context 被取消，则进入关闭流程。
     5. 关闭流程：以 10 秒超时调用 HTTP 服务的优雅关闭；若监听 goroutine 返回的不是「服务已关闭」错误，则作为错误返回。
     6. 等待所有异步提问任务结束（`a.Ask.Wait`）。
     7. 等待所有后台循环退出。
     8. 等待所有异步审批续跑结束（`a.HITL.Decisions.Wait`）。
- 结果与失败：任何一步返回错误时，打印「server: 错误」并以退出码 1 退出；正常关闭退出码 0。
- 注：`serve` 的注释写的是等待提问、循环与审批决策时「各自带超时兜底」，代码实际是这三处都是无超时的等待组等待；超时在每个异步任务内部：异步提问以脱离父取消的 context 加 5 分钟超时运行，审批续跑为 2 分钟超时；开关订阅循环没有超时，随根 context 取消退出。
- 注：`cmd/server/main.go` 的注释写的是「所有路由在 /api/v1/farms/:farm_id/ 下并经鉴权中间件」，代码实际还挂了 `/api/v1/admin/...`（走[平台路由鉴权](#平台路由鉴权)）、不经用户鉴权的设备回执 webhook，以及无鉴权的[网页外壳](#网页外壳)。

### worker 进程启动与退出

- 入口：CLI 命令 `worker [boot 参数]`；代码：`cmd/worker/main.go` 的 `run`、`work`。
- 前置条件：与 server 相同。worker 不开 HTTP 业务端口。
- 执行步骤：
  1. 解析参数、注册信号、调用 `boot.Open`，与 server 相同。
  2. 构造指标循环 `a.MetricsLoop(metrics.worker_addr, metrics.path)`。
  3. 调用 `a.WorkerLoops()` 得到后台循环列表。若构造失败（例如 outbox 处理器主题重复、通知文案缺失、某个 P2 任务启用但依赖不全），则启动失败。
  4. 把指标循环追加到列表末尾，记日志「worker started」（带全部循环名），启动所有循环。
  5. 等待根 context 取消，然后等待所有循环退出，再等待所有异步审批续跑结束，记日志「worker stopped」。
- 结果与失败：启动期错误打印后以退出码 1 退出；正常关闭退出码 0。
- 注：`worker.go` 与 `cmd/worker` 的注释只列出 outbox、扫描、分区、开关订阅与工单运维循环，代码实际还启动 `approval_backlog`、各 P2 任务循环与指标循环。

### 后台循环框架与循环清单

- 入口：由 server 的 `serve` 与 worker 的 `work` 调用；代码：`internal/app/worker.go` 的 `StartLoops`、`App.ServerLoops`、`App.WorkerLoops`、`App.p2WorkerLoops`，`internal/app/worker_p2.go` 的 `registerP2Loops`。
- 前置条件：`app.Build` 已成功。
- 执行步骤：
  1. 每个循环是一对「名称 + 运行函数」，运行函数接收根 context，直到 context 取消才返回。
  2. `StartLoops` 为每个循环起一个 goroutine，并返回一个等待函数；等待函数逐个等待各循环的结束信号。
  3. `ServerLoops` 只返回 `flags` 一项；server 另外追加指标循环。
  4. `WorkerLoops` 按以下顺序组装：先构造 outbox 轮询器（合并处理器表，主题重复或处理器为空即报错），然后依次加入 `outbox`、`scanner`、`partitions`、`flags`、`approval_backlog`、工单运维循环（命名为 `orderops#序号`，当前只有 `orderops#0`），最后加入 P2 任务循环。
  5. P2 任务由各文件在包初始化时登记（按文件名顺序），`p2WorkerLoops` 依次调用各登记项的构造函数。若登记名或构造函数为空、登记重复、返回的循环名或运行函数为空、循环名重复，则启动失败。
- 循环清单（只列出位置与作用，内部逻辑见其他章节）：

| 循环名 | 所在进程 | 周期（缺省） | 启用条件 | 作用 |
|---|---|---|---|---|
| `flags` | server、worker | 长连接订阅 | 总是 | 订阅开关变更消息并清进程内开关缓存，见[开关订阅循环与生效方式](#开关订阅循环与生效方式) |
| `metrics` | server、worker | 常驻监听 | 总是 | 在独立端口暴露 Prometheus 指标，见[指标监听](#指标监听) |
| `outbox` | worker | 1 秒 | 总是 | 领取 outbox 消息并按主题分发：`order.dispatch`、`notify.send`、`order.cancel`、`field.history.append`，配置了审计导出时还有 `audit.export`；消息进入 DEAD 时写 `OUTBOX_DEAD` 审计 |
| `scanner` | worker | 30 秒 | 总是 | 审批过期、票据激活、运行收尾、卡死运行、审批即将过期提醒、审计锚点、保留期清理、建议无引用告警等扫描；锚点与保留期两项只在对应 L7 组件装配后执行 |
| `partitions` | worker | 1 小时 | 总是 | 维护 `audit_log` 与 `run_event` 的分区 |
| `approval_backlog` | worker | 30 秒（`alerts.backlog_refresh`） | 总是 | 刷新审批积压指标 |
| `orderops#0` | worker | 30 秒 | 总是 | 扫描回执超时的工单（锁 `lock:scan:receipt_due`） |
| `attribution-weekly` | worker | 1 小时（`attribution.interval`） | `attribution.enabled` | 生成归因周报 |
| `backflow-collect` | worker | 1 小时（同 `attribution.interval`） | `attribution.backflow.enabled` | 收集线上回流样本；要求已装配原文读取，否则启动失败 |
| `kb-load-retention` | worker | 1 小时 | 总是 | 清理过期的知识加载记录，保留天数取 `retention.table_days.kb_load_item` |
| `quality-daily` | worker | 1 小时（`quality.interval`） | `quality.enabled` | 生成可信度日报；需要 eval bucket、知识库与模型配置 |
| `online-judge-review-enqueue` | worker | 1 小时（`eval_review.enqueue_interval`） | `eval_review.enabled` | 把线上 judge 结果入队到评测库的专家评审任务 |
| `rule-shadow-purge` | worker | 24 小时（`rule_offload.purge_every`） | 总是 | 清理规则下沉影子比对数据（锁 `lock:p2job:rule-shadow-purge`） |

- 结果与失败：构造期错误使 worker 启动失败；循环运行期错误由各循环自行记日志并在下一周期重试，不会使进程退出。
- 注：`ServerLoops` 的注释写的是 server「只有开关订阅」，代码实际是 server 还额外运行指标循环（由 `cmd/server` 追加）。
- 注：`WorkerLoops` 的注释只写了 P0 的四项扫描，代码实际的扫描循环还包含审批即将过期提醒、审计锚点、保留期清理与无引用告警。

### 应用装配

- 入口：`boot.Open` 第 14 步调用（评测工具 evalkit 也调用同一个函数，只是依赖实现不同）；代码：`internal/app/app.go` 的 `Build`。
- 前置条件：配置、连接、工具网关、各类矩阵已在 boot 中准备好。
- 执行步骤（只列装配顺序与依赖，不展开各服务内部）：
  1. 检查必填依赖，一次列出全部缺失项：主链路（`Agent` 或 `NewAgent` 二选一）、时钟、日志器、MySQL、Redis、Redis 键前缀、原文存储、工具网关、风险矩阵、约束拦截器、权限矩阵、故障矩阵。缺任一项即返回合并后的错误。
  2. 若未注入设备下发接缝，则使用模拟实现（只做 dry-run）。
  3. 补齐观测：告警配置取缺省并校验，指标观测器、告警出口、拒绝计数器为空时补缺省（拒绝计数器默认就是指标观测器）。
  4. 构造基础仓储与服务，依赖从上到下：Redis 锁、运行仓储、建议仓储、工单仓储、事件仓储（写 `run_event`，提交后经 Redis 发布）、带指标的事件出口、工单服务、审批服务（事务、票据、风险矩阵、约束拦截、本地同地块工单历史、通知 outbox）。
  5. 组装 App 结构：草稿仓储、本地工单仓储、运行锁、图内事件出口、HITL 存储（记忆、审批决策仓储；若注入了 MinIO 读取器则还有检查点存储）、运行详情服务、看板指标服务。
  6. 依次构造：告警列表服务；访问控制（权限矩阵与拒绝审计器，后者写 `audit_log`）；开关服务（开关仓储、事务、审计仓储、Redis 发布 / 订阅、用户角色仓储、观测器）；设备注册表。
  7. 设备注册表：若 `devices.yaml` 开启了本地模拟平台 devicesim，则要求环境名非空，且拒绝 `env=prod` 与非回环地址，然后为每类设备注册带链路追踪的模拟适配器；四类真实设备总是注册为「不可开放」的骨架。每个条目记一条日志。
  8. 调用 `NewAgent(a)` 构造主链路图（`app.GraphAgent`）：加载提示词与模型分档、追踪回调、LLM 客户端、本地工单、压缩引擎；下发模式来源设为「开关 `enable_robot_dispatch` 开启且该设备类型可开放」；同时注入开关读取器、用量统计、知识加载策略、HITL、约束注册表、农场范围守卫。
  9. 若未显式给出运行版本信息，则取主链路自报的版本。
  10. 构造提问服务：地块归属查询、限流器（每农场每分钟 20 次，Redis 键 `rl:farm:{farm_id}:ask`）、运行与建议仓储、主链路、开关读取器；若装配了长对话压缩，则再挂会话续接。
  11. 构造 L7 审计组件：若注入了锚点存储则启用每日锚点；若注入了对象删除器与原文 bucket 则启用保留期清理；若保留期已启用且有预签名器，则启用审计导出。
  12. 构造 HITL 服务：审批决策服务；扫描器（含即将过期提醒、锚点与保留期节拍、无引用告警）；若主链路支持复检，则构造复检服务。
  13. 构造下发：下发配置取缺省并校验；复开服务；下发仓储与 outbox 仓储；把下发依赖注入工单服务；构造 SSE 事件流服务（Redis 订阅加数据库回填）。
  14. 构造原文读取：若有预签名器，则构造带授权审计的原文读取服务；总是构造分区维护器。
  15. 构造工单运维：地块历史回写端为空时用内存实现；回执、中止、对账服务。若回执密钥非空，则标记回执 webhook 可挂载；否则记 Warn 日志「device receipt webhook not mounted: AS_DEVICE_RECEIPT_SECRET is not configured」。
  16. 构造审批 L5：审批配置取缺省；驳回原因导出服务；若有 MinIO 读取器，则构造待审批详情服务。
  17. 构造 L8：采纳 / 差评服务与归因问题处置服务，总是构造。
  18. 构造专家评审：若 `eval_review.enabled` 为假，则传入评测库连接视为错误，否则使用「已关闭」实现（接口返回 503）；若为真但缺评测库连接、对象存储或 bucket，则启动失败，否则构造评审服务。
- 按配置开关挂载的可选组件：

| 组件 | 开关或条件 | 关闭时的表现 |
|---|---|---|
| 设备模拟平台 | `devices.yaml` 的 devicesim 开关 | 只有不可开放的骨架，所有工单只能 DRY_RUN |
| 原文读取与 `GET .../raw/:raw_id` | 有预签名器（boot 总是注入） | 不挂该路由 |
| 每日锚点 / 保留期清理 / 审计导出 | 锚点存储、对象删除器与 bucket、预签名器（boot 总是注入） | 对应扫描项与导出路由不启用 |
| 设备回执 webhook | `device_receipt.secret` 非空 | 不挂回执路由，记 Warn 日志 |
| 长对话压缩会话续接 | 压缩配置已装配 | 行为与 P1 相同 |
| 专家评审 | `eval_review.enabled` | 路由照挂，返回 503 |
| 可信度日报 / 归因周报 / 线上回流 / 评审入队 | `quality.enabled` / `attribution.enabled` / `attribution.backflow.enabled` / `eval_review.enabled` | 不起对应 worker 循环 |

- 结果与失败：任一构造步骤失败即返回带前缀的错误（例如「app: build dispatch: …」），进程启动失败。
- 注：`Deps` 的注释写的是「全部必填（Agent 与 NewAgent 二选一）」，代码实际只强制检查第 1 步列出的 12 项，其余字段均可为空并取缺省或不启用。

### 路由挂载总表

- 前置条件：`app.Build` 已完成，鉴权服务已构造。

  1. 收集农场路由的挂载项，顺序为：审批列表与决策、运行详情与看板指标、运行事件 SSE、原文读取（有原文读取服务时）、工单运维（中止 / 对账 / 待对账）、审批 L5（驳回导出总是挂，待审批详情可选）、审计导出（启用导出时）、采纳 / 差评、告警列表。

  5. 若回执 webhook 可挂载，则在引擎根上注册回执路由。
  6. 若看板目录非空，则挂网页外壳。

### 农场路由通用链路

- 入口：所有 `/api/v1/farms/:farm_id/...` 请求（回执 webhook 除外）；代码：`internal/controller/router.go` 的 `FarmAuth`、`establishScope`，`internal/controller/ask.go` 的 `RequestID`，`internal/controller/access.go` 的 `Authorize`、`authorize`。
- 前置条件：客户端持有由同一 `auth.jwt_secret` 签发的令牌。
- 执行步骤：
  1. Recovery：handler 发生 panic 时由 gin 恢复并返回 500，进程不退出。
  2. RequestID：读请求头 `X-Request-Id`。
     1. 若为空，则生成 16 字节随机数的十六进制串；随机数生成失败返回 500。
     2. 若不满足「1 到 64 位字母、数字、点、下划线、短横线」，则返回 400 `bad X-Request-Id`。
     3. 把请求 id 写入响应头 `X-Request-Id`，并放入请求 context，后续日志与审计都带上它。
  3. FarmAuth 取令牌：优先取 `Authorization: Bearer` 头。只有路由是运行事件 SSE（`GET /api/v1/farms/:farm_id/runs/:run_id/events`）且没有 Bearer 头时，才改取查询参数 `access_token`（浏览器的 EventSource 不能带请求头）；其他路由不读查询参数。
  4. 校验令牌（`AuthService.Identify`）：令牌为空、不是 HS256、缺少或超过过期时间、`user_id` 为 0、缺少 `tenant_id` 声明，均返回 401 `{"error":"unauthenticated"}`。`tenant_id` 可以是 0。
  5. 解析路径 `farm_id`，失败返回 400 `bad farm_id`。请求体中的 farm_id 一律不用。
  6. 解析 Scope（`AuthService.ResolveScope`，每次请求都查库，不缓存），详见[角色与权限矩阵](#角色与权限矩阵)。若成功，再比较令牌的 `tenant_id` 与农场实际所属租户：若不一致且 Scope 中没有 `platform_admin`，则视为租户不符。
  7. 映射结果（`establishScope`，审计目标为 `farm:{farm_id}`）：
     1. 若是「禁止」类错误（无授权或租户不符），则调用拒绝审计器写一条 `SCOPE_DENIED`（租户不符时附带农场实际所属租户），返回 403 `{"error":"SCOPE_DENIED"}`。
     2. 若是其他错误（查库失败、数据异常），则记 Error 日志「resolve scope」，返回 500。
     3. 否则把 Scope（用户、租户、农场、角色列表）放入请求 context，继续。
  8. Authorize：以「请求方法 + 空格 + 路由模板」为键查路由权限表。若表中没有该路由，则记 Error 日志「route has no permission entry」，所需操作视为空集合，必然拒绝。
  9. 权限判定：若 context 中没有 Scope，则返回 401。若 Scope 的任一角色在权限矩阵中持有所需操作之一，则把守卫放入 gin context 并进入 handler；否则写一条 `ROLE_INSUFFICIENT` 拒绝审计（op 字段为所需操作逗号连接），返回 403 `{"error":"ROLE_INSUFFICIENT"}`。
  10. handler 内部若资源不属于当前 Scope（服务层返回 `ErrNotInScope` 或 `ErrForbidden`），则写一条 `RESOURCE_NOT_IN_SCOPE` 拒绝审计（目标如 `run:9`），返回 403 `Forbidden`，不暴露资源是否存在；若归属已确认但关联数据缺失，则记日志返回 500。
- 结果与失败：handler 内其余错误统一映射为 400（输入非法）、403（禁止）、404（不存在）、429（限流）、500（其他，记日志），响应体为 `{"error": "<HTTP 状态文本>"}`；各 handler 也可以返回自己的业务错误码。

### 访问拒绝审计

- 入口：由 FarmAuth、PlatformAuth、Authorize、RequireOps 与 handler 内的资源越界判定调用；代码：`internal/service/auth_denial.go` 的 `DenialAuditor.Deny`，`internal/controller/access.go` 的 `denial`、`recordDenial`。
- 前置条件：无。拒绝原因有三种：`SCOPE_DENIED`（农场不在授权内、租户不符、无平台绑定）、`ROLE_INSUFFICIENT`（权限矩阵未授予操作）、`RESOURCE_NOT_IN_SCOPE`（run、票据、原文、地块等资源不属于路径农场）。
- 执行步骤：
  1. 控制器组装一次拒绝：用户、路径 `farm_id`（平台路由为 0）、原因、被拒操作、目标（如 `farm:2`、`platform`、`run:9`）、路由（方法加模板）、请求 id。
  2. 基于请求 context 派生一个脱离请求取消、上限 2 秒的 context，保证客户端断开也会写审计，库慢时也不会拖住响应。
  3. 记 Warn 日志「access denied」，带指标名 `as_cross_farm_denied_total` 与全部字段。
  4. 若装配了计数器，则按原因给指标 `as_cross_farm_denied_total` 加 1。
  5. 生成审计摘要 JSON：`code`、`op`、`path_farm_id`、`owner_tenant_id`、`route`、`request_id`（空值省略）。
  6. 写一条 `audit_log`：位置为 Scope 的（租户, 农场）；`SCOPE_DENIED` 时 Scope 尚未建立，平台路由的 Scope 本身就是（0, 0），这两种情况都写在（0, 0）。操作者为该用户，动作 `CROSS_FARM_DENIED`，目标同第 1 步，结果 `DENIED`。写入走审计仓储的独立短事务并接入哈希链，不随任何业务事务回滚。
- 结果与失败：编码或写审计失败只记 Error 日志，对外响应不变（仍是 403）。若 handler 内记拒绝时取不到守卫或 Scope（装配错误），则记 Error 日志「access denial not audited」，不写审计。

### 平台路由鉴权

- 入口：`/api/v1/admin/...` 全部路由；代码：`internal/controller/admin.go` 的 `PlatformAuth`，`internal/controller/access.go` 的 `RequireOps`，`internal/service/auth.go` 的 `ResolvePlatformScope`。
- 前置条件：用户在 `user_role` 中有（租户 0, 农场 0）上的平台角色绑定。
- 执行步骤：
  1. RequestID，与农场路由相同。
  2. 只从 `Authorization: Bearer` 头取令牌（不接受查询参数），校验方式与农场路由相同，失败返回 401。
  3. 解析平台 Scope：查 `user_role` 中该用户在（0, 0）上的绑定，只保留平台角色（`platform_admin`、`kb_expert`、`legal`）。若一个都没有，则写 `SCOPE_DENIED` 审计（目标 `platform`），返回 403；查库失败返回 500。成功时 Scope 的租户与农场都是 0。
  4. RequireOps：按该路由组固定的操作做与 Authorize 相同的判定，不通过时写 `ROLE_INSUFFICIENT` 审计并返回 403。
  5. 进入 handler。
- 结果与失败：令牌中的 `tenant_id` 不要求为 0，平台权限只认（0, 0）上的角色绑定。

### 连通性检查 ping

- 入口：`GET /api/v1/farms/:farm_id/ping`；代码：`internal/controller/router.go` 的 `Ping`。
- 前置条件：通过[农场路由通用链路](#农场路由通用链路)，需要 `advice.read`。
- 执行步骤：
  1. 从请求 context 取 Scope。
  2. 若取不到，则返回 401 `unauthenticated`；否则以 JSON 返回 Scope（用户、租户、农场、角色列表）。
- 结果与失败：200 返回 Scope，不读写任何表。用于自检令牌与角色绑定是否生效。

### 角色与权限矩阵

- 入口：启动时加载矩阵；每个请求解析 Scope 并判定操作。代码：`internal/service/auth.go` 的 `AuthService.Identify`、`AuthService.Issue`、`AuthService.ResolveScope`、`AuthService.ResolvePlatformScope`、`AuthService.FarmHasRole`；`internal/service/auth_permission.go` 的 `LoadPermissionMatrix`、`ParsePermissionMatrix`、`PermissionMatrix.Allows`；`internal/controller/access.go` 的 `routeOps`。
- 前置条件：`policy/permission_matrix.yaml` 合法；`user_role` 与 `farm_profile` 已有数据（`migrate seed` 可写入示范数据）。
- 执行步骤（加载矩阵，启动期一次）：
  1. 读 yaml，只允许已知字段，版本必须为 1。
  2. 逐个角色校验：角色必须已登记；操作必须已登记；同一角色内不得重复；专属操作不得授给别的角色（`flag.write` 只能给 `platform_admin`，`review.read` 与 `review.submit` 只能给 `kb_expert`）。任一不合法即启动失败。
  3. yaml 中未列出的角色视为没有任何权限。
- 执行步骤（签发与校验令牌）：
  1. `Issue` 用 HS256 签发，声明包含 `user_id`、`tenant_id`、签发时间与过期时间。
  2. `Identify` 只接受 HS256，必须有过期时间，用注入的时钟判断是否过期；`user_id` 非 0，`tenant_id` 声明必须存在（值可以为 0）。
- 执行步骤（解析农场 Scope，`ResolveScope`）：
  1. 若用户 id 或农场 id 为 0，则禁止。
  2. 查农场归属：`SELECT tenant_id FROM farm_profile WHERE farm_id=? LIMIT 2`。若没有行，则禁止（403）；若多于一行，或归属租户为 0，则视为数据错误（500）。
  3. 查角色绑定：`SELECT tenant_id, farm_id, role FROM user_role WHERE (tenant_id=? AND farm_id=? AND user_id=?) OR (tenant_id=0 AND farm_id=0 AND user_id=?)`。
  4. 农场角色只取绑定在（该租户, 该农场）上的农场类角色；平台角色只取绑定在（0, 0）上的平台类角色；位置与类别不符的绑定一律忽略（例如农场角色挂在（0, 0）上不能放行任何农场）。
  5. 若既没有农场角色，也没有 `platform_admin`，则禁止。也就是说只有 `kb_expert` 或 `legal` 的用户进不了农场路由。
  6. 返回 Scope：租户、农场、用户，角色为农场角色加平台角色，按登记顺序排序。
- 执行步骤（操作判定，`Allows`）：只要 Scope 中任一角色持有该操作即通过；矩阵为空时一律拒绝。
- 角色 → 操作（来自 `policy/permission_matrix.yaml`）：

| 角色 | 类别 | 操作 |

| farmer | 农场 | ask、advice.read、advice.feedback |
| farm_manager | 农场 | ask、advice.read、approval.submit、approval.decide.other、order.cancel、raw.read、order.reconcile、rejection.export、advice.feedback |
| agronomist | 农场 | ask、advice.read、approval.submit、approval.decide.pesticide、approval.decide.other、order.cancel、raw.read、rejection.export、advice.feedback |
| operator | 农场 | ask、advice.read、order.cancel、advice.feedback |
| admin | 农场 | ask、advice.read、order.cancel、advice.feedback |
| auditor | 农场 | advice.read、audit.export、raw.read、rejection.export |
| platform_admin | 平台 | advice.read、order.cancel、audit.export、raw.read、flag.write、order.reconcile、attribution.write |
| kb_expert | 平台 | review.read、review.submit |
| legal | 平台 | 无 |

- 路由 → 所需操作（农场路由均在 `/api/v1/farms/:farm_id` 下，满足其一即可）：

### 开关读取与三层合并

- 入口：被提问服务、主链路图、下发器等在运行中调用；代码：`internal/service/flag.go` 的 `FlagService.Bool`、`FlagService.Mode`、`FlagService.BoolLive`、`FlagService.DispatchMode`、`FlagService.read`，`internal/model/flag.go` 的 `FlagScopeOf`、`ParseFlagValue`。
- 前置条件：开关已在注册表登记。当前登记的开关及缺省值（全部默认关闭）：`enable_advice`（布尔）、`enable_robot_dispatch`（布尔）、`rule_offload.operation_window`、`rule_offload.tank_mix`、`rule_offload.pest_priority`（三者为模式，取值 off / shadow / on）、`enable_loader_v1`（布尔）、`enable_compaction`（布尔）。
- 开关的三层位置由（租户, 农场）决定：（0, 0）为 GLOBAL，（t, 0）为 TENANT，（t, f）为 FARM，（0, f）非法。各层取值格式：GLOBAL 与 TENANT 只能写 `{"force_off": true|false}`；FARM 层的布尔开关写 `{"on": true|false}`，模式开关写 `{"mode": "off|shadow|on"}`。解析为严格模式，多余字段或类型不符都算非法。
- 执行步骤（`read`）：
  1. 若开关未登记，则报 `FLAG_UNKNOWN`；若用布尔方法读模式开关（或反之），则报类型不符；若查询的租户或农场为 0，则报范围非法。以上任一错误都按「关闭」返回。
  2. 若不是直读（`Bool`、`Mode`），则先查进程内缓存：键为（开关名, 租户, 农场），有效期 30 秒；命中即返回。`BoolLive` 跳过缓存。
  3. 读库：`SELECT tenant_id, farm_id, scope_type, value FROM feature_flag WHERE flag_key=? AND ((tenant_id=0 AND farm_id=0) OR (tenant_id=? AND farm_id IN (0,?)))`。若某行的 `scope_type` 与其（租户, 农场）位置不符，则报错。
  4. 合并：若 GLOBAL 层 `force_off` 为真，或 TENANT 层 `force_off` 为真，则结果为关闭；否则取 FARM 层的值；FARM 层没有行时取注册表缺省值（关闭）。任一层存储值非法则报错，按关闭处理。
  5. 回填缓存：读库前记下缓存代数，只有读库期间代数没变（没有收到失效通知）才写回缓存，避免把旧值写回。
  6. `DispatchMode` 用 `BoolLive` 直读 `enable_robot_dispatch`：开启返回 `REAL`，否则 `DRY_RUN`。
- 结果与失败：读取永不阻断调用方，任何错误都按关闭（失败关闭）返回，由调用方决定如何处理错误。

### 写入开关

- 入口：`PUT /api/v1/admin/flags/:flag_key/scopes/:tenant_id/:farm_id`（GLOBAL 用 `0/0`，TENANT 用 `t/0`，FARM 用 `t/f`）；代码：`internal/controller/admin.go` 的 `FlagSetHandler`，`internal/service/flag_set.go` 的 `FlagService.Set`、`validateSet`、`checkRobotDispatchOn`、`lockRobotPrecondition`、`write`。
- 前置条件：通过[平台路由鉴权](#平台路由鉴权)，持有 `flag.write`（只有 `platform_admin`）。
- 执行步骤：
  1. 控制器从 context 取 Scope（取不到返回 401），解析路径中的租户与农场（失败返回 400 `bad tenant_id` / `bad farm_id`），解析请求体 `{value, comment, expect_row_ver}`（失败返回 400 `bad body`），调用 `Set`。
  2. 事务外校验（`validateSet`），按顺序：
     1. 操作者必须是（0, 0）上的 `platform_admin`，否则 `ROLE_INSUFFICIENT`。
     2. 开关必须已登记，否则 `FLAG_UNKNOWN`。
     3. （租户, 农场）必须能映射到某一层，否则 `FLAG_SCOPE_INVALID`。
     4. 取值必须符合该层格式，否则 `FLAG_VALUE_INVALID`。
     5. 备注去掉首尾空白后必须为 1 到 256 个字符，否则 400。
     6. `expect_row_ver` 若给出必须不小于 0。
     7. 若不是 GLOBAL，则确认范围存在：`SELECT 1 FROM farm_profile WHERE tenant_id=? AND (farm_id=? OR ?=0) LIMIT 1`，不存在报 `FLAG_SCOPE_INVALID`。
     8. 若是在 FARM 层把 `enable_robot_dispatch` 打开，则检查前置条件：该农场 `enable_advice` 当前直读为开启，且该农场有 `agronomist` 角色绑定（`SELECT 1 FROM user_role WHERE tenant_id=? AND farm_id=? AND role=? LIMIT 1`），否则 `FLAG_PRECONDITION_FAILED`。
  3. 开启事务：
     1. 若是第 2.8 步的情形，则先 `SELECT ... FOR UPDATE` 锁住该农场 `enable_advice` 的 FARM 行，并再次确认它为开启，否则 `FLAG_PRECONDITION_FAILED`。这样并发关闭 `enable_advice` 的请求会被串行化。
     2. 锁目标行：`SELECT value, row_ver FROM feature_flag WHERE tenant_id=? AND farm_id=? AND flag_key=? FOR UPDATE`，记下旧值。
     3. 若请求未给 `expect_row_ver`：若是 FARM 层且行已存在，则报 `FLAG_CONFLICT`（FARM 层改已有值必须带版本号）；否则执行 `INSERT ... ON DUPLICATE KEY UPDATE`（更新 value、comment、updated_by，`row_ver` 加 1，更新时间）。新行的 `row_ver` 为 0，已有行为原值加 1。
     4. 若给了 `expect_row_ver`：执行 `UPDATE feature_flag SET ..., row_ver=row_ver+1 WHERE ... AND row_ver=?`，影响行数为 0 则报 `FLAG_CONFLICT`（乐观锁）。
     5. 在同一事务写 `audit_log`：位置为该开关的（租户, 农场），操作者为该用户，动作 `FLAG_CHANGE`，目标 `flag:{开关名}`，摘要含开关名、层、租户、农场、旧值（首次设置为 null）、新值、备注、新 `row_ver`，结果 OK。
  4. 若事务因 MySQL 死锁（错误号 1213）失败，则转成写入竞争，对外报 `FLAG_CONFLICT`。
  5. 提交后：清本进程该开关的缓存；以 2 秒超时（脱离请求取消）向 Redis 频道 `as:{env}:flags:changed` 发布 `{"flag_key": ...}`；指标 `as_flag_change_total` 加 1；记 Info 日志。
- 结果与失败：成功返回 200 与写入后的行状态（开关名、租户、农场、层、值、`row_ver`）。错误码映射：`ROLE_INSUFFICIENT` 403，`FLAG_UNKNOWN` 404，`FLAG_VALUE_INVALID` 400，`FLAG_SCOPE_INVALID` 400，`FLAG_CONFLICT` 409，`FLAG_PRECONDITION_FAILED` 409，响应体为错误码；备注非法 400；其他 500。发布失败只记 Warn 日志不回滚，其他进程最迟在 30 秒缓存过期后读到新值，`enable_robot_dispatch` 的关键读取本来就直读数据库。

### 查询开关

- 入口：`GET /api/v1/admin/flags/:flag_key`；代码：`internal/controller/admin.go` 的 `FlagListHandler`，`internal/service/flag_set.go` 的 `FlagService.List`。
- 前置条件：同[写入开关](#写入开关)。
- 执行步骤：
  1. 校验操作者是（0, 0）上的 `platform_admin`，开关已登记。
  2. 读 `SELECT tenant_id, farm_id, scope_type, value, comment, row_ver, updated_at FROM feature_flag WHERE flag_key=? AND scope_type IN (...) ORDER BY tenant_id, farm_id`。
  3. 返回 `{flag_key, settings: [...]}`，没有任何设置时 settings 为空数组。
- 结果与失败：只读，不写审计；错误码映射同写入。

### 开关订阅循环与生效方式

- 入口：循环 `flags`，server 与 worker 各运行一个，长连接订阅；代码：`internal/service/flag_set.go` 的 `FlagService.Run`、`consume`、`onChanged`，`internal/service/flag.go` 的 `invalidate`。
- 前置条件：Redis 可用。
- 执行步骤：
  1. 若未装配订阅端，则记 Warn 日志「flags:changed subscriber not configured, rely on cache TTL」并退出循环，此后只靠 30 秒缓存过期。
  2. 订阅 Redis 频道 `as:{env}:flags:changed`。订阅成功后先清空本进程全部开关缓存（断开期间可能漏掉消息，首次订阅也同样清空）。
  3. 逐条处理消息：解析 `{"flag_key": ...}`，清掉该开关在所有（租户, 农场）上的缓存；若消息无法解析或开关名为空，则记 Warn 日志并清空全部缓存。每次清缓存都会把缓存代数加 1，使正在读库的旧结果不会写回。
  4. 若订阅失败或频道被关闭，则记 Warn 日志「flags:changed subscription lost」，等 5 秒后回到第 2 步重新订阅。
  5. 根 context 取消时关闭订阅并退出。
- 开关值到达运行中进程的路径：
  1. 管理员写入后，写入所在的 server 进程立即清本地缓存，并发布变更消息。
  2. 其他 server 与 worker 进程收到消息后清缓存，下一次读取会直接读库拿到新值；若消息丢失，最迟 30 秒后缓存过期生效。
  3. 直读的地方不受缓存影响，写入提交后立即生效：主链路生成工单时用 `DispatchMode` 决定 REAL 还是 DRY_RUN（同时要求该设备类型在注册表中可开放，读失败按 DRY_RUN）；下发器首次下发与恢复下发 REAL 工单前都直读 `enable_robot_dispatch`（首次下发时还记下读取时间，供关停核验使用）。
  4. 走缓存的读取方：提问入口读 `enable_advice`，关闭或读取失败时返回 403 `ADVICE_DISABLED`；主链路的长对话压缩读 `enable_compaction`，知识加载策略读 `enable_loader_v1`，规则下沉读三个 `rule_offload.*` 模式；这些读取经 `internal/agent/flag_p2.go` 的 `FlagOn`、`FlagModeOf`，未装配读取器或读取出错时都按关闭执行。
- 结果与失败：循环本身不写库。订阅失败只降级为依赖缓存过期，不影响请求处理。

### 一键关停与关停核验

- 入口：关停操作为 `PUT /api/v1/admin/flags/enable_robot_dispatch/scopes/0/0`（全局）或 `.../scopes/{t}/0`（单租户），值为 `{"force_off": true}`；核验为 CLI 命令 `auditctl kill-switch-report --since <RFC3339> [--expect-held N] [--drill] [--config ...]`。代码：`internal/service/flag_set.go` 的 `FlagService.Set`，`cmd/auditctl/gray.go` 的 `cmdKillSwitchReport`、`runKillSwitchReport`，`internal/service/killswitch.go` 的 `KillSwitchReporter.Report`、`locateT0`、`countHeld`、`killSwitchFailures`、`RecordDrill`。
- 前置条件：关停需要 `platform_admin`。GLOBAL / TENANT 行不要求 `expect_row_ver`，直接 upsert。
- 执行步骤（关停如何生效）：
  1. 写入流程同[写入开关](#写入开关)，同事务写 `FLAG_CHANGE` 审计（GLOBAL 时位置为（0, 0）），提交后发布变更消息。
  2. 三层合并中 GLOBAL 或 TENANT 的 `force_off` 为真时，覆盖所有下层农场的设置，`enable_robot_dispatch` 立即读作关闭。
  3. 下发器每次发出 REAL 工单前直读该开关，读到关闭时：首次尝试的工单进入保留状态并写 `DISPATCH_HELD` 审计，重试中的工单按失败重试处理，恢复下发的工单转人工；新生成的工单直接定为 DRY_RUN。下发细节见 03 章。
  4. 解除关停是写入同一位置 `{"force_off": false}`。
- 执行步骤（核验报告）：
  1. 校验参数：`--since` 必须为 RFC3339；`--expect-held` 不小于 0；带 `--drill` 时 `--expect-held` 必须不小于 1。不合法为用法错误。
  2. 读配置（只读环境变量，不读 `deploy/.env`），以只读会话连业务库。若带 `--drill`，则另开一条可写连接，只用于写演练审计。
  3. 定位关停时刻 T0：从 `audit_log` 读（0, 0）位置、动作 `FLAG_CHANGE`、目标 `flag:enable_robot_dispatch`、已封链（`chain_seq` 非空）、时间不早于 `--since` 的记录，最多 200 条。第一条「从开到关」的 GLOBAL 记录（新值 `force_off:true`，旧值为空或 `force_off:false`）的审计时间为 T0；其后第一条 GLOBAL `force_off:false` 记录为解除时刻。两条记录都重算 `row_hash` 校验。若找不到 T0，则报 `ErrKillSwitchNoT0`；若看满 200 条仍未找到解除记录，则报扫描上限错误。
  4. 统计 T0 之后发出的 REAL 下发：`SELECT MAX(sent_at), COUNT(*) FROM dispatch_attempt WHERE mode='REAL' AND sent_at > T0`（有解除时刻时再加 `AND sent_at < 解除时刻`），得到最后一单距 T0 的耗时。
  5. 统计 T0 之后发出、且开关读取时间也在 T0 之后的 REAL 下发数（`sent_at >= T0 AND flag_read_at >= T0`），正常应为 0。
  6. 统计保留数：列出该开关的全部 FARM 行，逐个农场统计 T0 之后的 `DISPATCH_HELD` 审计数并求和。
  7. 判定失败项：耗时超过 60 秒；第 5 步计数不为 0；给了 `--expect-held` 且保留数之和小于它。
  8. 打印报告（各计数与各农场灰度档位）。若带 `--drill`，则在（0, 0）写一条 `KILL_SWITCH_DRILL` 审计，操作者为 system，结果按是否通过记 OK 或 FAILED（不论是否通过都会写）。
  9. 输出 `RESULT PASS` 或 `RESULT FAIL: N assertions failed`。
- 结果与失败：退出码 0 为通过，1 为断言不成立，2 为用法错误，3 为运行失败。灰度预检（`gray-preflight`）只认 7 天内的演练记录。
- 注：`killswitch.go` 的注释写的是统计区间为「[T0, 解除)」，代码实际第 4 步用的是 `sent_at > T0`，不含 T0 时刻本身。

### 指标监听

- 入口：循环 `metrics`，server 监听 `metrics.server_addr`（缺省 `127.0.0.1:9101`），worker 监听 `metrics.worker_addr`（缺省 `127.0.0.1:9102`），路径 `metrics.path`（缺省 `/metrics`）；代码：`internal/app/observe.go` 的 `App.MetricsLoop`、`App.MetricsHandler`。
- 前置条件：端口未被占用。该端口独立于业务 HTTP 端口，不经过任何业务鉴权，缺省只绑定回环地址。
- 执行步骤：
  1. 构造时：新建只处理指标路径一条路由的 HTTP 服务，读请求头超时 5 秒；处理器以 Prometheus 文本格式输出本进程的指标注册表。同时构造指标预置器（按农场列表为各农场预先建好指标序列，周期为 `alerts.backlog_refresh`，新登记的农场在下个周期补上）。
  2. 循环开始：若预置器构造失败，则记 Error 日志「metrics preseed disabled」，不启动预置；否则在 goroutine 中运行预置器。
  3. 在 goroutine 中开始监听，记 Info 日志「metrics listening」。
  4. 若监听出错（例如端口被占用），则记 Error 日志「metrics listen failed」，本循环结束，业务进程继续运行（只是没有指标）。
  5. 根 context 取消时，以 5 秒超时（脱离父取消）优雅关闭指标服务，关闭出错只记 Warn 日志。
  6. 停止预置器并等待它退出。
- 结果与失败：本循环不读写业务表（预置器只读农场列表）。指标端口故障不会让进程退出。

### 数据库迁移与种子命令

- 入口：CLI 命令 `migrate up [--target business|eval] [--dir 目录] [--skip-buckets]` 与 `migrate seed [--file configs/seed/fields.yaml]`，两者都接受 `--config`（缺省 `configs/app.yaml`）与 `--env-file`（缺省 `deploy/.env`）；代码：`cmd/migrate/main.go` 的 `run`、`cmdUp`、`postMigrateL7`、`cmdSeed`，`internal/seed/seed.go` 的 `Load`、`Apply`。
- 前置条件：MySQL 可连，配置了 `mysql.password`；业务库建 bucket 时 MinIO 可连。
- 执行步骤（`up`）：
  1. 读配置并要求 `mysql.password`。按 `--target` 选库与迁移目录：business 为业务库与 `migrations`，eval 为评测库与 `migrations/eval`；`--dir` 可覆盖目录；其他取值报错。
  2. 若库不存在则创建（`CreateDatabase`）。
  3. 用 golang-migrate 执行迁移到最新版本，打印「migrated 库名 to version N」。不使用 GORM 自动建表。
  4. 若目标是 eval，则到此结束。
  5. 业务库迁移后的初始化（`postMigrateL7`，均可重复执行）：先校验保留期配置覆盖全部原文类型；连库；在一个事务内为（0, 0）、`farm_profile` 与 `user_role` 中出现的每个（租户, 农场）以及各租户级位置（t, 0）预建审计链头 `audit_chain_head`（`INSERT IGNORE`，序号 0、哈希为 64 个 0，已存在的跳过）；按保留天数回填 `raw_object.expire_at`；打印建了多少链头、回填了多少行。失败时报「tables migrated but audit chain / retention init failed」。
  6. 若带 `--skip-buckets`，则在 stderr 打印 WARNING（列出被跳过的原文、评测、锚点三个 bucket）后结束。
  7. 否则构造 MinIO 客户端，确保原文 bucket 与评测 bucket 存在；再确保锚点 bucket 存在并开启 COMPLIANCE 模式的对象锁，保留天数为 `audit.anchor_lock_days`（缺省 365）；MinIO 不支持对象锁时明确报错，不降级为普通 bucket。打印「buckets ready」。
- 执行步骤（`seed`）：
  1. 读配置并要求 `mysql.password`，读种子文件，连业务库。
  2. 在一个事务内执行：
     1. 预建平台链头（0, 0）。
     2. 对主农场与种子中的额外农场逐个：upsert `farm_profile`；预建（t, f）与（t, 0）链头；逐个 upsert `field_profile`。
     3. 逐条 upsert `user_role`（已存在时更新授权人）。
     4. 写种子中的开关：只插入 `feature_flag` 中缺失的行，已有的行不改。
  3. 打印「seeded farm (t,f) 名称 with N fields」。
- 结果与失败：退出码 0 成功，1 失败（stderr 打印「migrate: 错误」），2 用法错误。`seed` 可重复执行。
- 注：`cmd/migrate` 文件头注释把 `seed` 写成「示范农场地块 upsert」，代码实际还 upsert 额外农场与 `user_role`、插入缺失的 `feature_flag` 行、预建审计链头。

### 开发令牌命令

- 入口：CLI 命令 `devtoken --user N [--tenant T] [--ttl 时长] [--seed configs/seed/fields.yaml] [--config ...] [--env-file ...]`；代码：`cmd/devtoken/main.go` 的 `run`、`tokenTenant`。
- 前置条件：配置了 `auth.jwt_secret`（环境变量 `AS_AUTH_JWT_SECRET` 或 `deploy/.env`），且与 server 使用的是同一个密钥。
- 执行步骤：
  1. 若 `--user` 未给或为 0，则报错。
  2. 读配置，要求 `auth.jwt_secret`；读种子文件。不连数据库。
  3. 按种子文件中的 `user_roles` 决定令牌的 `tenant_id`：
     1. 若该用户在种子中没有任何绑定，则报错。
     2. 若显式给了 `--tenant`：值为 0 直接使用；非 0 时必须是该用户绑定过的租户，否则报错。
     3. 若未给 `--tenant`：用户绑定在多个租户时报错并要求指定；只在一个租户时取该租户；只有平台绑定时取 0。
  4. 构造只能签发、不能解析 Scope 的鉴权服务（密钥短于 32 字节同样报 `ErrWeakSecret`）。
  5. 有效期取 `--ttl`，未给时取 `auth.token_ttl`。
  6. 签发 HS256 令牌并打印到 stdout。不打印密钥。
- 结果与失败：任何错误打印「devtoken: 错误」并以退出码 1 退出。令牌是否真能访问某农场，取决于数据库中 `user_role` 的实际数据，命令只检查种子文件。
