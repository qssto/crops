# 04 审计与观测

本章描述审计日志怎样写入并串成哈希链，怎样每日锚定、校验、清理和分区，以及审计导出、`cmd/auditctl` 命令行工具、告警、看板指标和 Prometheus 指标的执行流程。
审计链按 (tenant_id, farm_id) 分链，(0,0) 是平台链。所有审计行都在事务提交前由「封链」步骤统一计算哈希并写入，业务代码只负责把记录排进当前事务。
告警有两条来源：代码里直接调用告警出口（写 ALERT.* 审计、计数、打日志），以及 Prometheus 按业务指标计算的规则。
后台任务（扫描、分区、积压刷新）都只在 `cmd/worker` 里运行；审计导出与告警列表、看板指标的 HTTP 接口只在 `cmd/server` 挂载。

### 审计写入与封链

- 入口：没有独立入口，由业务代码在事务内调用。代码：`internal/repository/audit.go` 的 `AuditRepo.AppendTx` / `AuditRepo.Append`、`internal/repository/event.go` 的 `EventRepo.AppendTx`、`internal/repository/aftercommit.go` 的 `inTx` / `withAuditSeal`、`internal/repository/audit_chain.go` 的 `queueAudit` / `sealAudit` / `insertChained`
- 前置条件：每条链在 `audit_chain_head` 里必须已有一行。`cmd/migrate` 用 `InitChainHeads` 以「不存在才插入」的方式预建：平台链 (0,0)、`farm_profile` 与 `user_role` 中出现的每个 (tenant, farm)、每个租户的 (tenant, 0)，初始 chain_seq 为 0，head_hash 为 64 个 0（创世哈希）。
- 执行步骤：
  1. 调用方有两种写法。
     - 「同事务」写法 `AppendTx`：审计与业务同一事务，业务回滚时审计一起回滚。
     - 「独立」写法 `Append`：自己开一个短事务只写审计，用于拒绝、告警这类业务失败也必须留痕的场合。
  2. 两种写法都先用 `NewAuditRecord` 组装记录：payload_digest 为 payload 的 sha256；payload 不超过 8KB 时原样作为 summary，超过则 summary 只记 `{"truncated":true,"bytes":N}`；target 截到 64 个字符。scope 为 (0,0) 是合法的，审计写入不要求农场归属。
  3. `queueAudit` 不立即写库，而是把记录追加到「当前事务连接」对应的待封链批次里。若当前不在事务内，或该事务不是经 `inTx` 打开的（没有批次），返回 `ErrAuditNoSeal`，并同步发出 `audit_write_failed` 告警（见下一节）。
  4. `inTx` 打开数据库事务后执行业务函数。嵌套调用 `inTx` 时只由最外层负责封链；内层函数失败时，内层追加的记录从批次里截掉。
  5. 业务函数成功后，最外层取出批次执行 `sealAudit`：
     - 收集批次里出现的所有链键，按 (tenant_id, farm_id) 升序排序后依次加锁，固定顺序避免死锁。
     - 对每条链执行 `SELECT chain_seq, head_hash FROM audit_chain_head WHERE tenant_id=? AND farm_id=? FOR UPDATE`。查不到行则返回 `ErrAuditChainHeadMissing`。
     - 按追加顺序对每条记录调用 `insertChained`（规则见下文）。
     - 若该记录是敏感操作成功（`model.SensitiveAudit`：result 为 OK，且 action 为 FLAG_CHANGE、ORDER_CANCEL、RAW_READ、AUDIT_EXPORT 之一），紧接着在同一条链上再插一行二次留痕 `SENSITIVE.{action}`：target 为 `audit:{主记录 id}`，summary 为主记录的 action、target、payload_digest，result 为 OK。
     - 最后对每条链执行 `UPDATE audit_chain_head SET chain_seq, head_hash, updated_at`。
  6. 封链成功则提交事务，提交后按注册顺序执行提交后回调（SSE 发布、指标计数等）。封链失败则整个事务回滚，回滚后调用 `fireAuditWriteFailed`。
- 单行入链规则（`insertChained`）：
  - 先规范化：created_at 截到毫秒并转 UTC，summary 转成规范 JSON。
  - chain_seq 取链头 chain_seq + 1，prev_hash 取链头 head_hash。
  - row_hash = sha256(prev_hash 的十六进制文本 拼接 本行规范 JSON) 的十六进制。本行规范 JSON 不含 id，键为 action、actor_id、actor_type、chain_seq、created_at（格式 `2006-01-02T15:04:05.000Z`）、farm_id、payload_digest、raw_object_id、result、run_id、summary、target、tenant_id；整数写成十进制字符串，target 或 summary 为空时写 null。
  - 执行 `INSERT audit_log (..., chain_seq, prev_hash, row_hash)`，再把链头推进到本行。
- 运行事件到审计的投影（`EventRepo.AppendTx`，所有 run_event 的唯一写入口）：
  1. 校验 scope 有农场归属、事件类型合法。
  2. `ProjectAudit` 按投影表算出审计行：RUN_STARTED 投为 ASK（target `field:{id}`），TOOL_CALL_END 投为 TOOL_CALL（`tool:{tool}`），KB_LOADED 投为 KB_LOAD（`kb:{ref}`），LLM_CALL_END 投为 LLM_CALL（`llm:{task}`），VALIDATION_FAILED 与 ADVICE_READY 投为 VALIDATE（`check:{check}` / `advice:{id}`），APPROVAL_OPEN、APPROVAL_PENDING、APPROVAL_DECIDED、CONSTRAINT_BLOCKED 投为 APPROVAL（`ticket:{id}`），ORDER_TRANSITION 投为 ORDER_TRANSITION（`order:{id}`），DISPATCHED 投为 DISPATCH，DEGRADED 投为 DEGRADED（`fault:{fault}`）。STEP_* 与 RUN_INTERRUPTED / RUN_RESUMED / RUN_COMPLETED / RUN_FAILED 不投影。
  3. result 规则：VALIDATION_FAILED 与 CONSTRAINT_BLOCKED 为 FAILED；TOOL_CALL_END 的状态 OK 为 OK、REJECTED 为 DENIED、其余为 FAILED；LLM_CALL_END 带 ERROR 为 FAILED；其余为 OK。payload 为空或解析不了返回 `ErrBadAuditPayload`。
  4. `UPDATE agent_run SET event_seq = LAST_INSERT_ID(event_seq+1)` 取本 run 的事件序号，`INSERT run_event`。
  5. 若该事件需要投影，调用 `AuditRepo.AppendTx` 排入同一事务的封链批次。
  6. 注册提交后回调：向 Redis 频道 `sse:run:{run_id}` 发布事件。若事务不是经 `inTx` 打开的，只记 Warn 日志，不发布。外层的 `service.ObservedEvents` 另外注册提交后回调，把 ORDER_TRANSITION、DEGRADED、LLM_CALL_END 计入 Prometheus 指标。
- 其他直接写审计的调用方：审批决策（`DecisionRepo.InsertDecisionTx`，同事务另写 `SENSITIVE.APPROVAL_DECIDE`）、跨农场拒绝（CROSS_FARM_DENIED）、开关变更（FLAG_CHANGE）、outbox 死信（OUTBOX_DEAD）、原文读取、保留期清理、审计导出、告警出口、回流、专家评审、关停演练等，写法都是上面两种之一。
- 结果与失败：封链失败使业务事务整体回滚，调用方拿到错误；没有重试，由调用方按自身逻辑处理。同一事务内的审计行按追加顺序连续编号，并发事务在链头行锁上排队，所以同一条链的 chain_seq 连续无空洞。

### 封链失败告警

- 入口：封链失败回滚之后，或 `queueAudit` 发现事务没有封链批次时。代码：`internal/repository/audit_chain.go` 的 `fireAuditWriteFailed`；告警出口由 `internal/app/boot/boot.go` 启动时调用 `repository.SetAuditAlertSink` 注册。
- 前置条件：进程已注册告警出口；未注册时只打 Error 日志。
- 执行步骤：
  1. 若失败原因是 context 取消或超时，则不告警（调用方自己放弃了请求）。
  2. 若当前 ctx 带有「正在发告警」标记，则不告警。告警出口写 ALERT.* 审计时也走封链，这个标记防止它失败后再递归告警。
  3. 否则组装告警 `audit_write_failed`，级别 P0，scope 取批次中第一条记录的 (tenant, farm)，run_id 取第一条记录的 run_id，detail 为错误文本。
  4. 带上「正在发告警」标记调用告警出口的 `Fire`（见[告警出口](#告警出口)）。
- 结果与失败：本函数没有返回值，不影响业务错误的返回。没有重试。

### 原文读取

- 入口：`GET /api/v1/farms/:farm_id/runs/:run_id/raw/:raw_id`。代码：`internal/controller` 的 `RawHandler`，`internal/service/audit.go` 的 `AuditService.ReadRaw`，`internal/repository/rawaccess.go` 的 `RawAccessRepo`
- 前置条件：用户已通过鉴权，路由权限为 `raw.read`（权限矩阵中授予 farm_manager、agronomist、auditor、platform_admin）。装配时配置了预签名器（`Deps.Presign`），否则不挂此路由。
- 执行步骤：
  1. 控制器解析 run_id、raw_id，不是正整数则直接返回 400（bad run_id / bad raw_id）。服务层对 0 值再做一次校验。
  2. 再次按权限矩阵判定 `raw.read`，不通过则走拒绝分支，拒绝码 ROLE_INSUFFICIENT。
  3. 开事务 `InTx`，在事务内读 `raw_object` 行：
     - 不存在则拒绝，拒绝码 RAW_NOT_FOUND。
     - 该行所属 run 与路径中的 run_id 不一致则拒绝，拒绝码 RUN_MISMATCH。
     - 先核对归属，再看是否过期；已过期则拒绝，拒绝码 RAW_EXPIRED。
  4. 调用 MinIO 生成预签名下载地址，有效期 5 分钟（`RawReadTTL`）。
  5. 同一事务内写审计 RAW_READ / OK，summary 为 raw_id、run_id、kind、expires_at。封链时自动追加 `SENSITIVE.RAW_READ`。
  6. 提交事务，返回下载地址。
- 拒绝分支：用 `context.WithoutCancel` 经独立短事务写审计 RAW_READ / DENIED，summary 带拒绝码，这条审计不随请求取消而丢失。
- 结果与失败：成功返回 200，响应头 `Cache-Control: no-store`。已过期返回 410（此前已写 RAW_READ / DENIED，拒绝码 RAW_EXPIRED）。其余拒绝统一按 403 处理，控制器 `abortScoped` 另记一条 CROSS_FARM_DENIED 拒绝审计（拒绝码 RESOURCE_NOT_IN_SCOPE，target `raw:{raw_id}`）；RAW_READ / DENIED 审计本身写失败时，错误合并后仍返回 403。

### 扫描循环中的审计任务

- 入口：`cmd/worker` 的后台任务 `scanner`，每 30 秒一轮（`DefaultScanInterval`）。代码：`internal/service/scan.go` 的 `Scanner.Run` / `Scanner.RunOnce` / `Scanner.runTask`
- 前置条件：`audit_anchor` 任务要求配置了锚点 bucket（`L7.Anchors`）；`retention` 任务要求配置了对象删除器与 raw bucket（`L7.Objects`、`L7.RawBucket`）；`advice_no_citation` 任务要求配置了引用查询与告警出口。缺依赖的任务不注册。
- 执行步骤：
  1. 启动后等第一个 30 秒周期到达，之后每个周期执行一轮。
  2. 每轮按注册顺序串行执行各任务：approval_expire、ticket_activate、run_finalize、stuck_run、approval_expiring（以上见 03 章），然后是本章的 audit_anchor、retention、advice_no_citation。
  3. 每个任务先抢 Redis 锁 `lock:scan:{task}`，租期 60 秒。锁已被其他副本持有则本轮跳过该任务。
  4. 抢到锁后以跨农场凭证 `server_scan` 执行任务，结束后释放锁（释放用不随 ctx 取消的上下文）。
- 结果与失败：单个任务失败只合并进本轮错误、打 Warn 日志，不影响其余任务；下一轮重新执行。
- 注：注释写的是「server 内扫描任务」，代码实际是扫描循环只在 `cmd/worker` 的 `WorkerLoops` 里启动，`cmd/server` 的 `ServerLoops` 只有开关订阅。

### 每日锚点

- 入口：扫描任务 `audit_anchor`，随扫描循环每 30 秒被调用一次，实际每天只做一次。代码：`internal/service/audit_anchor.go` 的 `AnchorService.Tick` / `ensureAnchor` / `ensureVerified` / `verifyIncrement`，`internal/repository` 的 `MinIOAnchorStore`
- 前置条件：锚点 bucket `agri-steward-audit-anchor` 由 `cmd/migrate` 创建，开启 COMPLIANCE 模式对象锁，保留 365 天（`anchor_lock_days`）。
- 执行步骤：
  1. 若当前北京时间早于当日 00:10，或本进程今天已完成（进程内记录的日期等于今天），直接返回。
  2. `ensureAnchor` 处理今天的锚点 `anchor/{yyyymmdd}.json`：
     - 读对象时列出全部版本，取最早的有效版本。版本数大于 1（被重写或删除过）则发 `audit_chain_broken` P0。
     - 若对象已存在：校验文件里 chains 数组规范化后的 sha256 与 sha256 字段一致、date 字段与文件名日期一致。不一致则打 Error 日志、发 `audit_chain_broken` P0、本进程今天不再处理，返回 `ErrAnchorDigest`。
     - 若对象不存在：读全部链头 `SELECT ... FROM audit_chain_head ORDER BY tenant_id, farm_id`，生成 {date, anchored_at, chains[每条链的 tenant_id、farm_id、chain_seq、head_hash], sha256} 并写入 bucket。已存在时不重写。
  3. `ensureVerified` 校验「前一日锚点到今日锚点」之间的增量，校验标记为 `verify/{yyyymmdd}.json`：
     - 先读标记是否已存在。
     - 读前一日锚点。其摘要不符则记一个问题并把前一日视为空（从链头开始校验）；不存在则打 Warn 日志并从链头开始校验。
     - 对前一日和今日两份锚点分别调用 `CheckAnchor`，逐链比对当前库：链头缺失记 HEAD_MISSING；当前链头 seq 小于锚定 seq 或锚定那一行已不存在记 TRUNCATED；锚定那一行内容重算哈希与库内 row_hash 不同、或 row_hash 与锚定 head_hash 不同记 RECOMPUTED。
     - 对今日锚点中的每条链，从「前一日锚定 seq + 1」到「今日锚定 seq」调用[审计链校验](#审计链校验)。当天无增量的链跳过。
     - 每个问题都写进标记的 problems；只有标记尚不存在时才逐个发 `audit_chain_broken` P0（避免重复告警）。
     - 若标记已存在：检查标记对象的版本数，大于 1 发 P0；再把已存标记与本次重算结果比对（verified_at 除外），任何字段不同发一条 P0。
     - 若标记不存在：写入标记 {date, prev_date, verified_at, chains, rows, problems}。链有问题时也照常写入标记。
  4. 记录本进程今天已完成。
- 结果与失败：读写 MinIO 或查库出错时返回错误，本轮不记完成，下一轮（30 秒后）重试。进程重启后会重新执行一次步骤 2、3，此时锚点与标记都已存在，只做比对，不重复写入。

### 审计链校验

- 入口：没有独立入口，被[每日锚点](#每日锚点)、[审计导出 生成文件](#审计导出-生成文件)和 [auditctl verify](#auditctl-verify) 调用。代码：`internal/service/audit_verify.go` 的 `VerifyChain` / `checkRow`，`internal/repository/audit_chain.go` 的 `AuditChainRepo.Head` / `Rows`
- 前置条件：调用方给出链键 (tenant, farm) 和区间 [from, to]；from 为 0 表示 1，to 为 0 或超过链头表示到链头。
- 执行步骤：
  1. 读该链的 `audit_chain_head`，得到链头 chain_seq 与 head_hash。
  2. 若 from 大于 1，先读第 from−1 行，用它的 row_hash 作为期望的 prev_hash；该行不存在则报 GAP。from 为 1 时期望 prev_hash 为创世哈希。
  3. 每次 1000 行分页读取：`SELECT ... FROM audit_log WHERE tenant_id=? AND farm_id=? AND chain_seq BETWEEN ? AND ? ORDER BY chain_seq`。
  4. 逐行检查，顺序为：chain_seq 不等于期望值报 GAP；prev_hash 不等于上一行 row_hash 报 LINK_BROKEN；按入链规则重算哈希不等于 row_hash，或 summary 无法规范化，报 ROW_MODIFIED。若调用方传了逐行回调，每行通过检查后交给回调。
  5. 一页读完但行数不足（中间缺行）报 GAP。
  6. 若校验到了链头，且最后一行的 row_hash 不等于 head_hash，报 LINK_BROKEN。
- 结果与失败：只报告第一个断点（类型、chain_seq、audit_log.id），之后不再继续。返回校验区间与行数。读库出错时返回错误，不算断点。

### 原文保留期清理

- 入口：扫描任务 `retention`，随扫描循环每 30 秒调用一次。代码：`internal/service/audit_retention.go` 的 `RetentionService.Tick` / `purgeBatch`，`internal/repository/retention.go` 的 `RetentionRepo`
- 前置条件：配置了对象删除器和 raw bucket（`agri-steward-raw`）。各类原文的保留天数取 `retention.raw_object_days`：LLM_IO 180、TOOL_RAW 180、SNAPSHOT 1095、CHECKPOINT 30、EXPORT 30、DEVICE_CMD 1095、RECEIPT_RAW 1095、COMPACTED_MSGS 180。这些天数在写入原文时已折算成 `raw_object.expire_at`。
- 执行步骤：
  1. 按北京时间取当天日期。日期变了就把游标清零、把「今日已扫完」标记清掉。若今天已扫完，直接返回。
  2. 每轮最多 5 批，每批 200 行。每批先查到期行：`SELECT id, tenant_id, farm_id, kind, object_key, expire_at FROM raw_object WHERE deleted_at IS NULL AND expire_at < now AND (expire_at, id) > 游标 ORDER BY expire_at, id LIMIT 200`。查不到行则标记今天已扫完。
  3. `purgeBatch` 处理一批：
     - 查引用（`Referenced`，一条 UNION 查询）：被 PREPARING / OPEN 状态票据、或作业单未终态（或作业单不存在）的票据以 `approval_ticket.snapshot_raw_id` 引用的；被 `dispatch_attempt.command_raw_id` 引用的；被作业单未终态（或不存在）的 `device_receipt.raw_object_id` 引用的；被 run 不是 COMPLETED / FAILED / CANCELED（或不存在）的 `run_checkpoint.raw_object_id` 引用的。这些行本次跳过。
     - 对剩下的行逐个删除 MinIO 对象。删除失败的行计入失败数，本行不打墓碑。对象本来就不存在也算删除成功。
     - 开一个事务：对删除成功的行 `UPDATE raw_object SET deleted_at=? WHERE ... AND deleted_at IS NULL`（0 行表示已被别人处理，不计数）；再按 (tenant, farm, kind) 分组，每组写一条审计 RETENTION_PURGE，actor 为 system，target `raw_kind:{kind}`，summary {kind, count, max_expire_at}，result OK。
  4. 把游标推进到本批最后一行。本批不满 200 行则标记今天已扫完。
- 结果与失败：引用查询或打墓碑事务失败时游标不前进，本轮结束，下一轮重扫这一批（对象已删的行再删一次算成功，然后打墓碑）。对象删除失败和被引用跳过的行，游标已越过它们，要等第二天游标清零后重试。`raw_object` 行只打墓碑不删除。`audit_log`、`run_event` 不由本任务删除，`retention.table_days` 只登记它们的保留期（audit_log 1095 天、run_event 365 天、kb_load_item 180 天）。
- 注：注释写的是「worker 任务 retention 每日一轮」，代码实际是每 30 秒都会被调用、没有时刻门槛，从每天 0 点（北京时间）起分批扫，扫完后当天不再扫。

### 分区维护

- 入口：`cmd/worker` 的后台任务 `partitions`，启动时立即检查一次，之后每小时一次（`DefaultPartitionCheck`）。代码：`internal/service/partition.go` 的 `PartitionMaintainer.Run` / `Tick` / `RunOnce` / `ensure` / `MissingMonths`，`internal/repository/partition.go` 的 `PartitionRepo`
- 前置条件：`audit_log` 与 `run_event` 按月 RANGE 分区，最后一个分区为 `pmax`（VALUES LESS THAN MAXVALUE）。迁移 0001 预建了 p202610 到 p202709 和 pmax。
- 执行步骤：
  1. `Tick`：按北京时间，若今天早于当月 25 日，或本进程本月已成功维护过，则跳过。
  2. `RunOnce`：抢 Redis 锁 `lock:scan:partition`，租期 10 分钟。锁被其他副本持有则本次不执行，也不记本月完成，下个小时再试。
  3. 依次处理 `audit_log`、`run_event` 两张表（`ensure`）：
     - 执行 `SELECT COUNT(*) FROM 表 PARTITION (pmax)`。若 pmax 里有数据，只打一条 Error 日志。
     - 从 `information_schema.PARTITIONS` 读出现有分区名。
     - `MissingMonths` 计算缺的月份：从现有最大 pYYYYMM 的下一个月开始（中间缺的月份也补上），到当前月份加 2 个月为止。都已存在则结束。
     - 执行 `ALTER TABLE 表 REORGANIZE PARTITION pmax INTO (PARTITION pYYYYMM VALUES LESS THAN ('下月1日'), ..., PARTITION pmax VALUES LESS THAN (MAXVALUE))`，然后打 Info 日志。
  4. 两张表都成功才记本月已完成。锁在结束时释放。
- 结果与失败：一张表失败不影响另一张；有失败时本月不记完成，下个小时重试（已建的分区不会重复建）。错误只打 Warn 日志，不告警。
- 旧分区：代码中没有删除或清空分区的逻辑，本任务只从 pmax 拆出新分区，旧月份分区一直保留。

- 执行步骤：
  1. 控制器解析请求体 {from, to, request_id}，解析失败返回 400「bad body」。

  5. 调用[审计导出 查询与下载](#审计导出-查询与下载)的同一逻辑读取当前状态并返回。
- 结果与失败：成功返回 202 与导出状态 {export_id, state, from, to, rows, ...}。导出始终异步执行，没有同步路径。同一 request_id 重复提交是幂等的，返回同一个 export_id。本步骤不写审计；审计在生成完成或失败时写。

### 审计导出 生成文件

- 入口：`cmd/worker` 的 outbox 轮询器领取 topic `audit.export` 的消息（领取、续租与退避见 03 章 outbox 部分）。代码：`internal/service/audit_export.go` 的 `AuditExportService.Handle` / `verifySpan` / `writeLine` / `buildZip` / `scanExport` / `quarantine` / `finish` / `fail`
- 前置条件：同上，worker 装配了导出服务才注册该 topic 的处理器。
- 执行步骤：
  1. 解析 payload。若 state 已是 DONE 或 FAILED（消息重放），直接返回成功。
  2. 以消息的 (tenant, farm) 作为链键，查导出窗口内的 chain_seq 范围：`audit_log` 中 created_at 落在 [from, to) 的最小、最大 chain_seq。
  3. 确定校验区间（`verifySpan`）：窗口内有行时，校验区间为 [最小 seq−1（不小于 1）, 最大 seq+1]，前后各多校验一行，使删除首尾行或改动边界行时间都能被发现；窗口内无行时，取窗口开始前最后一行的 seq 为 b，校验 [b（不小于 1）, b+1] 的衔接。
  4. 调用[审计链校验](#审计链校验)，逐行回调里只保留 created_at 落在 [from, to) 的行，写成一行 JSON：target 用 `pii.Mask` 按文本脱敏，summary 用 `pii.MaskJSON` 按 JSON 结构脱敏，row_hash 和 prev_hash 保留库内原值。
  5. 若发现断点：打 Error 日志，发告警 `audit_chain_broken` P0，然后在一个事务里把 payload 改为 FAILED（错误码 CHAIN_BROKEN）并写审计 AUDIT_EXPORT / FAILED（summary 带错误码），返回成功（不重试）。
  6. 打包 zip：`audit_log.jsonl` 加 `manifest.json` {export_id, tenant_id, farm_id, from, to, chain_from, chain_to, rows, chain_verified: true, masked_fields: [target, summary], generated_at}。
  7. 写入 MinIO：kind 为 EXPORT，文件名 `audit-export-{export_id}.zip`，日期取消息入队时间（跨日重放仍写同一个 key），对象 key 为 `raw/{tenant}/{farm}/{yyyy}/{mm}/{dd}/0/EXPORT/audit-export-{export_id}.zip`，bucket 为 `agri-steward-raw`。同时 upsert 一行 `raw_object`，保留 30 天。
  8. 单独开事务，把 raw_object_id 写回 outbox payload（state 仍为 PENDING）。
  9. 用 `internal/piiclean` 解压 zip、逐行再扫一遍敏感信息（手机号、身份证号、账号、精确坐标）。这是独立于脱敏器的复核。
  10. 若扫到敏感信息（隔离）：
      - 先删除 MinIO 对象，失败则返回错误等待重试。
      - 一个事务内：`raw_object` 打墓碑，payload 改为 FAILED（错误码 PII_LEAK），写审计 AUDIT_EXPORT / FAILED。
      - 打 Error 日志，发告警 `audit_export_pii_leak` P0，返回成功。
  11. 否则一个事务内：payload 改为 DONE，写审计 AUDIT_EXPORT / OK（target `export:{id}`，summary {export_id, from, to, rows, chain_from, chain_to}，带 raw_object_id）。封链时自动追加 `SENSITIVE.AUDIT_EXPORT`。
- 结果与失败：断链和敏感信息命中都是终态，不重试。读库、写 MinIO、更新 payload 等临时错误返回错误，由 outbox 按 1 秒、5 秒、30 秒、2 分钟、10 分钟的间隔退避重试；失败累计达到 5 次（`OutboxMaxAttempts`）后消息置 DEAD，并写 OUTBOX_DEAD 审计。重放时会重新生成并覆盖同一个对象。

### auditctl verify

- 入口：命令 `auditctl verify --farm <id> [--tenant <id>] [--from-seq N] [--to-seq M] [--config configs/app.yaml]`。代码：`cmd/auditctl/main.go` 的 `run`，`cmd/auditctl/verify.go` 的 `cmdVerify` / `runVerify` / `resolveChain`
- 前置条件：读配置文件，MySQL 密码只从环境变量取（不读 `deploy/.env`）。用只读会话连接业务库（DSN 设置事务只读），连接池 2。
- 执行步骤：
  1. 解析参数：`--farm` 必填（0 表示平台链）；`--tenant` 不能小于 0；给了 `--to-seq` 时 `--from-seq` 不能大于它。若给了 `--from-manifest`，直接返回「未启用」（导出包离线校验尚未实现）。
  2. 确定链键：给了 `--tenant` 就用 (tenant, farm)；farm 为 0 时用平台链 (0,0)；否则查 `SELECT tenant_id FROM farm_profile WHERE farm_id=? LIMIT 2`，没有结果要求传 `--tenant`，只有一个就用它，有两个则报歧义并要求传 `--tenant`。
  3. 读链头。若 `--from-seq` 大于链头 seq，按用法错误退出。
  4. 调用[审计链校验](#审计链校验)。
  5. 有断点时输出 `BROKEN chain (t,f) range [from,to]: 断点说明`；否则输出 `OK chain (t,f) range [from,to] rows=N`。
- 结果与失败：退出码 0 为通过，1 为发现断点，2 为参数错误或功能未启用，3 为运行失败（连库、读配置等）。
- 注：`--tenant` 的帮助文本与 `verifyOpts` 注释写的是「缺省按 user_role 解析」，代码实际查的是 `farm_profile`（`UserRoleRepo.FarmTenants` 读 farm_profile）。

### auditctl anchor-check

- 入口：命令 `auditctl anchor-check --date yyyymmdd [--anchor-file path]`。代码：`cmd/auditctl/verify.go` 的 `cmdAnchorCheck` / `fetchAnchor` / `runAnchorCheck`
- 前置条件：同上。未给 `--anchor-file` 时需要 MinIO 密钥（环境变量），从锚点 bucket 读取。
- 执行步骤：
  1. `--date` 必须是 8 位数字，否则用法错误。
  2. 读锚点：给了 `--anchor-file` 就读本地文件，版本数按 1 计；否则从锚点 bucket 读 `anchor/{date}.json` 的最早版本和版本数。
  3. 版本数大于 1 时先输出一行 BROKEN 提示（对象被重写过），仍按最早版本继续检查。
  4. 校验文件整体 sha256，不符则输出 BROKEN 并退出码 1。文件内 date 与 `--date` 不同也按 BROKEN 处理。
  5. 调用 `CheckAnchor` 逐链比对当前库（HEAD_MISSING / TRUNCATED / RECOMPUTED，规则见[每日锚点](#每日锚点)），每个不一致输出一行 BROKEN。
  6. 有不一致或版本数大于 1 时退出码 1；否则输出 `OK anchor {date} chains=N sha256=...`。
- 结果与失败：退出码规则同 verify。本命令补的是 verify 发现不了的情况：链尾被整体截掉后，剩下的行仍能自洽，只有和锚点比才能发现。

### auditctl gray-preflight

  2. 按 [auditctl verify](#auditctl-verify) 的同一规则从 `farm_profile` 解析租户。
  3. `GrayPreflight.Run` 拒绝租户或农场为 0 的范围，然后按固定顺序逐项检查。某一项读数据出错只把该项判 FAIL，不中断后面的项：
     1. d5_closed：严格解码 `policy/external_decisions.yaml`（出现未知字段即失败），id 不能重复。D5 的状态必须是 CLOSED，closed_at、approved_by、record_ref 都不能为空。closed_at 必须是 `2006-01-02` 格式，且不晚于北京时间今天。

     4. kill_switch_drill：在平台链 (0,0) 上读 7 天内（`KillSwitchDrillWindow`）最近一条已入链的 KILL_SWITCH_DRILL 审计。这一行要通过行哈希重算（`VerifyRowHash`），summary 要能解析。result 为 OK 且 passed 为 true，elapsed_ms 不超过 60000（`KillSwitchMaxElapsed`），expect_held 大于 0 且 held_total 不小于 expect_held，T0 在窗口内。然后用 `FlagChangeByID` 读它引用的 FLAG_CHANGE：必须是平台链上已入链的行，行哈希通过，属于全局开关「开转关」（新值 force_off 为 true），且 created_at 等于 T0。
     5. redteam_pass5：读 `eval/suites/redteam` 下全部 .yaml / .yml 样本，每个都要有 id 且 suite 为 redteam，id 不能重复。目录为空，或任何样本声明了隔离，该项 FAIL。再查评测库最近一次红队实验：`SELECT ... FROM experiment WHERE FIND_IN_SET('redteam', suite)>0 ORDER BY id DESC LIMIT 1`，状态必须为 DONE，finished_at 不早于「现在减 max-age」。接着读它的试次 `SELECT sample_id, trial_index, status, scores FROM trial WHERE experiment_id=? AND suite=?`：任一 scores 解析出错则整个实验作废；至少要有一个红线维度被打分；试次里的样本不在仓库样本中判失败；每个样本至少 5 次试次，且全部试次的每个红线维度都必须通过，INFRA_ERROR 计为不通过。输出说明里带实验的 git_sha。
     6. agronomist_bound：`SELECT 1 FROM user_role WHERE tenant_id=? AND farm_id=? AND role='agronomist' LIMIT 1`，必须有结果。

  4. 每项输出一行 `PASS 项名: 说明` 或 `FAIL 项名: 说明`，最后输出 `RESULT PASS` 或 `RESULT FAIL`。

### auditctl kill-switch-report

- 入口：命令 `auditctl kill-switch-report --since <RFC3339> [--expect-held N] [--drill]`。代码：`cmd/auditctl/gray.go` 的 `cmdKillSwitchReport` / `runKillSwitchReport`，`internal/service/killswitch.go` 的 `KillSwitchReporter.Report` / `locateT0` / `countHeld` / `RecordDrill`
- 前置条件：报告查询走业务库只读会话。`--expect-held` 不能小于 0；带 `--drill` 时 `--expect-held` 必须至少为 1（没有预置单的空演练耗时恒为 0，不能算通过）。
- 执行步骤：
  1. 解析 `--since`，不是 RFC3339 按用法错误退出。若带 `--drill`，另开一个可写连接，只用于最后写演练审计。
  2. 定位 T0（`locateT0`）：读平台链上 target 为 `flag:enable_robot_dispatch`、created_at 不早于 since、已入链的 FLAG_CHANGE 审计，按 created_at、id 升序，最多 200 行。
     - 第一条「GLOBAL 开转关」（result OK，旧值为空或 force_off 为 false，新值 force_off 为 true）作为 T0；关转关的重复写不算。
     - T0 之后第一条「GLOBAL 新值 force_off 为 false」作为解除时刻。
     - 这两行都要重算行哈希，不一致直接报错。找不到 T0 报错；读满 200 行仍没有解除也报错，要求缩小 `--since`。
  3. 统计区间为 [T0, 解除时刻)，未解除则到现在：
     - `RealSentAfter`：REAL 模式 `dispatch_attempt` 中 T0 之后发出的次数和最大 sent_at。
     - `RealReadAfter`：其中 flag_read_at 不早于 T0 的次数（读到开关已关却仍发出）。
     - `countHeld`：取 enable_robot_dispatch 的全部 FARM 级记录作为灰度农场，逐个统计区间内的 DISPATCH_HELD 审计并求和。
  4. 耗时 = 最大 sent_at − T0（毫秒），没有发出记录时为 0。断言三条：耗时不超过 60 秒；flag_read_at 不早于 T0 的发出次数为 0；DISPATCH_HELD 之和不小于 `--expect-held`。
  5. 输出 T0、解除时刻、各计数、每个灰度农场的开关值与 held 数，以及每条不成立的断言。
  6. 若带 `--drill`，经独立短事务（`AuditRepo.Append`）在平台链 (0,0) 写 KILL_SWITCH_DRILL 审计：actor system，target `flag:enable_robot_dispatch`，summary {t0, flag_change_audit_id, released_at, elapsed_ms, max_sent_at, real_sent_after, flag_read_after, held_total, expect_held, gray_farms, failures, passed}（只记灰度农场个数，不记逐农场明细）。断言全部成立时 result 为 OK，否则为 FAILED，断言失败也照写。
- 结果与失败：断言全部成立输出 `RESULT PASS`，退出码 0；有不成立项输出 `RESULT FAIL`，退出码 1。这条演练审计是 [auditctl gray-preflight](#auditctl-gray-preflight) 第 4 项 kill_switch_drill 的数据来源。

### 告警出口

- 入口：代码中所有 `Alerts.Fire` 调用。代码：`internal/service/alert_sink.go` 的 `AuditAlertSink.Fire` / `appendAlert`，装配在 `internal/app/observe.go` 的 `NewObserve` / `buildObserve`，`internal/app/audit_l7.go` 的 `buildAuditL7`
- 前置条件：
  - `cmd/server` 与 `cmd/worker` 启动时（`boot`）在构造 MCP gateway 之前调用 `NewObserve`，生成指标观测器和告警出口，gateway 与 `app.Build` 共用这一个出口。
  - 未传入时 `buildObserve` 补缺省：alerts 配置取 `config.DefaultAlerts` 并校验，指标观测器新建一个，告警出口用同一套实现新建，拒绝计数器也指向这个观测器。
  - 审计导出、锚点使用的出口按 `L7.Alerts`、`Deps.Alerts`、`LogAlertSink`（只打日志）的顺序取第一个非空的。
  - 审计写超时取 `alerts.audit_write_timeout`，缺省和上限都是 500 毫秒，超出范围装配失败。
- 执行步骤：
  1. 设置 panic 兜底：出口内部 panic 只记 Error 日志，不传给调用方。
  2. 计数 `as_alert_total{alert, level, farm_id}`。
  3. 打一条 Error 日志，带告警名、级别、tenant、farm、run_id、order_id、detail。
  4. 组装 summary {alert, level, run_id, order_id, detail}，detail 截到 256 个字符（由调用方保证不含个人信息）。
  5. 用脱离调用方取消、带 500 毫秒上限的上下文，经独立短事务（`AuditRepo.Append`）写审计：scope 为告警 scope，action `ALERT.{告警名}`，actor system，target 有作业单时为 `order:{id}`，否则有 run 时为 `run:{id}`，都没有则为空；run_id 列有值才填；result 为 P0 写 FAILED、P1 写 DENIED。
  6. 若写成功则结束。否则打 Error 日志，然后：
     - 若 scope 已是平台链 (0,0)，或已到截止时间，则结束。
     - 否则在同一截止时间内改写平台链 (0,0) 再试一次：summary 加 origin {tenant_id, farm_id}，run_id 列置空。成功打 Warn 日志，失败打 Error 日志。
- 结果与失败：`Fire` 没有返回值，任何失败都不影响调用方。回退到平台链的行不会出现在该农场的[告警列表](#告警列表)里，要按 origin 在平台审计中查。
- 防递归：ALERT 审计也走封链。若这次写入失败，封链会再发一条 `audit_write_failed`；若当前上下文已带「正在发告警」标记（即本次 `Fire` 本身就来自 `audit_write_failed`），或失败原因是超时、取消，则不再发。所以最多多发一层，不会无限递归。
- 注：注释写的是「本分支无 L7-A 的 ErrAuditChainHeadMissing」，代码中 `repository.ErrAuditChainHeadMissing` 已存在，封链遇到链头缺失时返回它。出口确实不判断错误类型，截止前的任何失败都会回退平台链。

     - as_fault_kb_miss：1 小时内 KB_MISS 大于 5 次，agronomist。

### 告警列表

- 入口：`GET /api/v1/farms/:farm_id/alerts?name=&from=&to=&limit=&cursor=`。代码：`internal/controller/alert.go` 的 `AlertListHandler`，`internal/service/alert_list.go` 的 `AlertService.List` / `alertItem`，`internal/repository` 的 `AlertRepo.ListAlerts`
- 前置条件：路由权限 `advice.read`（与看板指标相同，`internal/controller/access.go`）。只在 `cmd/server` 挂载。
- 执行步骤：
  1. 控制器从上下文取 scope，取不到返回 401。from、to 按 RFC3339 解析，limit 必须是正整数，不符合返回 400。
  2. 服务层校验：name 非空时必须是已登记的告警名；cursor 格式为「{unix 毫秒}_{id}」，毫秒和 id 都必须为正。
  3. 补缺省：to 缺省为当前时间，from 缺省为 to 减 24 小时。from 必须早于 to，跨度不超过 744 小时（31 天）。limit 缺省 50，上限 200。
  4. 确定要查的 action：name 为空取全部告警名。每个告警名对应 `ALERT.{name}`；cross_farm_denied 另加业务审计 CROSS_FARM_DENIED，flag_changed 另加 FLAG_CHANGE。
  5. 查 `audit_log`：`WHERE tenant_id=? AND farm_id=? AND action IN (...) AND created_at>=from AND created_at<to`，有游标时只取排在游标之后的行，`ORDER BY created_at DESC, id DESC`，取 limit+1 行。
  6. 多出一行说明还有下一页，截掉后用本页最后一行的 (created_at, id) 生成 next_cursor。
  7. 逐行组装 {id, created_at, alert, level, action, target, result, run_id, order_id, detail, run_link}：
     - ALERT 行解析 summary，取 level、order_id、detail；run_id 列为空时用 summary 里的 run_id。
     - 业务审计行只给 action、target、result，summary 不外露，alert 字段按 action 映射回告警名。
     - run_id 不为 0 时 run_link 为 `/api/v1/farms/{farm_id}/runs/{run_id}`。
- 结果与失败：成功返回 200 {from, to, items, next_cursor}。参数、告警名、跨度、游标不合法返回 400，读库失败返回 500。只查本农场的链，回退到平台链 (0,0) 的告警行查不到。

### 看板指标

- 入口：`GET /api/v1/farms/:farm_id/metrics?from=YYYY-MM-DD&to=YYYY-MM-DD`。代码：`internal/controller/rundetail.go` 的 `MetricsHandler`，`internal/service/metrics.go` 的 `MetricsService.Daily` / `computeMetrics`，`internal/service/metrics_l7b.go` 的 `addOpsFacts`，`internal/repository/metrics.go`、`metrics_l7b.go` 的 `MetricsRepo.Facts`
- 前置条件：路由权限 `advice.read`。只读业务库。
- 执行步骤：
  1. 控制器按 UTC 解析 from、to，格式不对返回 400（bad from / bad to）。
  2. 缺省都取当天（UTC），都截到当天零点。to 早于 from，或天数（含首尾）超过 31，返回 400。
  3. `Facts` 在时间窗 [from, to+1 天) 内对本农场依次执行以下查询：
     - `agent_run`：窗口内创建的 run 的 id、status、created_at。
     - `run_event` 联查 `agent_run`：这些 run 的 VALIDATION_FAILED、RUN_RESUMED、RUN_COMPLETED、LLM_CALL_END 事件。
     - `tool_call`：status、latency_ms、created_at。
     - `advice_card`：outcome、created_at。
     - `approval_ticket`：ORDER 类、状态为 APPROVED 或 REJECTED、decided_at 在窗口内的票；opened_at 为该票 APPROVAL_PENDING 事件的最早时间。
     - `work_order`：窗口内创建的单，dispatched 表示 `work_order_transition` 中存在转 DISPATCHED 的记录。
     - `dispatch_attempt`：REAL 模式、sent_at 在窗口内的尝试，accepted 为 device_job_id 不为空。
     - `work_order_transition` 联查 `work_order`：转 DONE、PARTIALLY_DONE、FAILED、EXPIRED，或 reason 为 RECHECK_FAILED 的迁移。
     - 当前 OPEN 的 ORDER 票数（查询时刻的快照，不受时间窗限制）。
  4. 按 UTC 日归桶：run 类指标按 run 创建日，票按决策日，下发尝试按 sent_at，其余按行的创建时间。每天各算一份，再算一份全区间合计。
  5. 各指标口径（分母为 0 时比率为 null）：
     - sessions：当天创建的 run 数。completion_rate：其中 COMPLETED 的比例。validation_failure_rate：有 VALIDATION_FAILED 事件的 run 占 sessions 的比例。
     - resume_success_rate：有 RUN_RESUMED 的 run 中，存在序号大于首个 RUN_RESUMED 的 RUN_COMPLETED 的比例。
     - tool_success_rate：OK 的工具调用比例。tool_p95_latency_ms：耗时按最近秩取 95 分位（排序后取第 ceil(0.95·n) 个）。
     - refusal_rate：建议卡中 REFUSED 的比例。
     - tokens：LLM_CALL_END 中 prompt、completion 与合计，per_session 为合计除以 sessions，bad_payload 为解析不了的事件数。
     - approval_wait：decided 为决策票数，missing_open 为找不到 APPROVAL_PENDING 的票数，avg_sec、p95_sec 为决策时刻减 opened_at 的平均值与 95 分位。
     - jobs：只统计 REAL 单。orders 为单数，dispatch_rate 为曾转 DISPATCHED 的比例，done_rate 为当前状态 DONE 或 PARTIALLY_DONE 的比例，dry_run_excluded 为被排除的 DRY_RUN 单数。
     - dispatch_success_rate：REAL 下发尝试中 accepted 的比例。
     - job_success_rate：REAL 单转 DONE 或 PARTIALLY_DONE 的次数，除以转 DONE、PARTIALLY_DONE、FAILED 的次数。
     - recheck_returned：reason 为 RECHECK_FAILED 的迁移次数；expired：转 EXPIRED 的次数。这两项都包含 DRY_RUN 单。
- 结果与失败：成功返回 200 {from, to, days[], total, approval_backlog}，days 覆盖区间内每一天，没有数据的日期各项为 0 或 null。读库失败返回 500。

### Prometheus 指标端口与序列预置

- 入口：后台任务 `metrics`。`cmd/server` 监听 `metrics.server_addr`（缺省 127.0.0.1:9101），`cmd/worker` 监听 `metrics.worker_addr`（缺省 127.0.0.1:9102），路径都是 `metrics.path`（缺省 `/metrics`）。代码：`internal/app/observe.go` 的 `MetricsLoop`，`internal/service/backlog.go` 的 `MetricsPreseeder`，`internal/service/metrics_observer.go` 的 `MetricsObserver` / `Preseed`，`internal/service/metric_registry.go` 的注册表
- 前置条件：每个进程各有一个指标注册表，由 `NewObserve` 创建，进程间不共享。这个监听使用独立的 HTTP 服务，只挂 `/metrics`，没有业务路由，也不经业务鉴权。
- 执行步骤：
  1. 构造注册表时登记全部指标，并预置不带 farm_id 的有限取值序列（值为 0）：拒绝码 SCOPE_DENIED、ROLE_INSUFFICIENT、RESOURCE_NOT_IN_SCOPE；开关 enable_advice、enable_robot_dispatch；续跑结果 ok、error；MCP server weather、crop、field、device 与各工具状态的组合。另外预置 farm_id=0 的农场类序列。
  2. 任务启动后另起协程运行预置器：立即执行一次，之后每隔 `alerts.backlog_refresh`（缺省 30 秒）执行一次。每次查 `SELECT DISTINCT farm_id FROM farm_profile`，对每个农场（另加 0）补齐 0 值序列：各告警名 × 级别 P0/P1；四个降级码；下发模式 DRY_RUN/REAL × 结果 ok/rejected/manual/error/blocked；token 类型 prompt/completion；迁移 (EXPIRED, APPROVAL_EXPIRED) 与 (PENDING_APPROVAL, RECHECK_FAILED)。已存在的序列不动。读农场失败只打 Warn 日志。
  3. 启动 HTTP 监听。监听失败打 Error 日志后任务返回，不影响业务进程。
  4. 处理请求：只接受 GET 和 HEAD，其他方法返回 405。按 Prometheus 文本格式（`text/plain; version=0.0.4`）输出，指标族按登记顺序，序列按 label 值排序。写响应失败打 Warn 日志。
  5. 进程退出时停止预置器，优雅关闭监听，最多等 5 秒。
- 指标清单（label 值不在枚举内时记为 other）：
  - `as_alert_total{alert, level, farm_id}` 计数：每次 `Fire` 计一次，见[告警出口](#告警出口)。
  - `as_dispatch_total{farm_id, mode, result}` 计数：下发器每次下发的结果，下发前拦截记为 blocked。
  - `as_order_transition_total{farm_id, to, reason}` 计数：作业单迁移事件在事务提交后计数，reason 为空时记 none；事务回滚的不计。
  - `as_approval_backlog{farm_id}` 仪表：见[审批积压刷新](#审批积压刷新)。
  - `as_approval_wait_seconds{farm_id, decision}` 直方图：审批决策时记录「决策时刻减票据创建时刻」，分桶上界为 60、300、900、1800、3600、7200、14400、28800、86400 秒。
  - `as_cross_farm_denied_total{code}` 计数：每次越权拒绝。
  - `as_flag_change_total{flag}` 计数：每次开关变更。
  - `as_run_resume_total{result}` 计数：审批后续跑，结果 ok 或 error。
  - `as_llm_tokens_total{farm_id, kind}` 计数：LLM_CALL_END 事件中的 prompt、completion token 数。
  - `as_mcp_calls_total{server, status}` 计数：每次 MCP 工具调用，传输层错误记为 ERROR。
  - `as_degraded_total{farm_id, fault}` 计数：每次 DEGRADED 事件。
- 结果与失败：经 `ObservedEvents` 写入的事件在事务提交后才计数；经 `ObservedEventSink` 写入的事件在写入成功后计数。指标只在进程内存里，进程重启后从 0 开始。

### 审批积压刷新

- 入口：后台任务 `approval_backlog`，只在 `cmd/worker` 运行。代码：`internal/app/observe.go` 的 `backlogLoop`，`internal/service/backlog.go` 的 `BacklogRefresher.Run` / `RefreshOnce`，`internal/repository` 的 `AlertRepo.OpenOrderTickets`
- 前置条件：刷新周期取 `alerts.backlog_refresh`，缺省 30 秒。
- 执行步骤：
  1. 启动后立即刷新一次，之后每个周期刷新一次。
  2. 以跨农场凭证查 `SELECT tenant_id, farm_id, COUNT(*) FROM approval_ticket WHERE ticket_kind='ORDER' AND status='OPEN' GROUP BY tenant_id, farm_id`。
  3. 按 farm_id 累加各行计数，用结果整体替换 `as_approval_backlog`；本轮没有 OPEN 票的农场不再出现在仪表中。
- 结果与失败：查询失败保留上一轮的值，打 Warn 日志，下一周期再试。本任务不取 `lock:scan`，每个 worker 副本各自刷新自己进程内的值，告警规则用 `max by (farm_id)` 合并多个副本。
