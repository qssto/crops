# 03 审批与工单下发

本章接在主链路之后：主链路已经把作业单写成 DRAFT、开出 PREPARING 审批票并让 run 停在 INTERRUPTED(WAIT_APPROVAL)。从这里开始，票据被激活为 OPEN，审批人通过 HTTP 接口通过或驳回；通过后同一事务写入 outbox(order.dispatch)，cmd/worker 里的 outbox 轮询器把它交给下发器。下发器做准入、开关、选设备、下发前复检，再走 DRY_RUN 模拟或 REAL 真实设备通道。真实下发之后由设备回执 webhook、回执超时扫描、人工对账和中止补偿把作业单推到终态。cmd/worker 中的扫描器负责票据过期、补激活、补续跑和卡住 run 的收尾。

## 状态迁移表

### 审批票（approval_ticket.status）

| 状态 | 触发 | 去向 |
|---|---|---|
| （无） | 主链路 ApprovalService.Open 建第一张票（ticket_seq=1） | PREPARING |
| PREPARING | ApprovalService.Activate（runner 中断后立即调用，或 ticket_activate 扫描补调） | OPEN |
| PREPARING | ticket_activate 扫描发现 run 已终态，voidTicket 作废 | EXPIRED |
| PREPARING / OPEN | 用户中止未下发的作业单（closeTicketsTx） | SUPERSEDED |
| OPEN | 首审通过（需要双人确认的票），只记 first_approver_id | OPEN（不变） |
| OPEN | 单人通过，或第二人确认通过 | APPROVED |
| OPEN | 审批驳回 | REJECTED |
| OPEN | 决策时发现已过期，或 approval_expire 扫描 | EXPIRED |
| APPROVED | 下发前复检约束不通过，ReopenService.Reopen 换票 | SUPERSEDED（同时插入 ticket_seq+1 的新票，直接为 OPEN） |

### 作业单（work_order.status）

合法迁移只认 `internal/model/workorder.go` 的 WorkOrderTransitions 表；不在表中作为来源的状态即终态（DONE、PARTIALLY_DONE、REJECTED、EXPIRED、FAILED、CANCELED）。下表列出本章代码实际触发的迁移，括号内是写入 work_order_transition 的 reason_code。

| 状态 | 触发 | 去向 |
|---|---|---|
| DRAFT | 主链路开票成功（Open） | PENDING_APPROVAL |
| DRAFT | 用户中止（CANCELED_BY_USER）；run 重试耗尽 failRun（RETRY_EXHAUSTED） | CANCELED |
| PENDING_APPROVAL | 审批通过（单人或第二人确认） | APPROVED |
| PENDING_APPROVAL | 审批驳回（APPROVAL_REJECTED） | REJECTED |
| PENDING_APPROVAL | 票据过期收尾，或 PREPARING 票被作废（APPROVAL_EXPIRED） | EXPIRED |
| PENDING_APPROVAL | 用户中止（CANCELED_BY_USER） | CANCELED |
| APPROVED | DRY_RUN 写下发意图（recordIntent）；REAL 首次写 SENT 尝试（recordSentIntent） | DISPATCHED |
| APPROVED | 下发前复检约束不通过，退回重审（RECHECK_FAILED） | PENDING_APPROVAL |
| APPROVED | 超过 dispatch_deadline_at（APPROVAL_EXPIRED）；选不到设备且等待超限（DEVICE_UNAVAILABLE） | EXPIRED |
| APPROVED | 用户中止（CANCELED_BY_USER）；复检结论变化（CONDITION_CHANGED） | CANCELED |
| DISPATCHED | DRY_RUN 写入模拟结果（跳过 EXECUTING） | DONE |
| DISPATCHED / EXECUTING | 回执 EXECUTING（RECEIPT） | EXECUTING |
| DISPATCHED / EXECUTING | 回执 DONE / PARTIALLY_DONE / CANCELED（RECEIPT）；人工对账（RECONCILED） | DONE / PARTIALLY_DONE / CANCELED |
| DISPATCHED / EXECUTING | 回执 FAILED+IN_EXECUTION（无面积 → FAILED，有面积 → PARTIALLY_DONE）；NOT_EXECUTED 且已到 MaxAttempts（RETRY_EXHAUSTED） | FAILED / PARTIALLY_DONE |
| DISPATCHED | 平台明确拒绝（DISPATCH_REJECTED）；重试在开关 / 复检处被拦（RETRY_BLOCKED）；重试选不到设备且等待超限（DEVICE_UNAVAILABLE） | FAILED |
| DISPATCHED / EXECUTING | 用户中止且最后一次尝试已确认未执行（CANCELED_BY_USER） | CANCELED |

## 公共机制：lock:order 与作业单迁移入口

### 作业单锁 WithOrderLock

- 入口：`internal/service/orderlock.go` 的 `WithOrderLock`；审批决策与扫描器用同文件族的 `acquireOrderLock`（只取锁、不续租）。
- 前置条件：调用方给出 order_id。
- 执行步骤：
  1. 以 TTL 10s 取 Redis 键 `lock:order:{order_id}`。若已被他人持有，则返回包装 ErrOrderBusy 的错误。
  2. 取锁成功后起一个续租协程，每 ttl/3（约 3.3s）用 Lua 校验 token 续租。若续租失败，则以 ErrOrderLockLost 取消传给 fn 的 ctx，fn 里的 DB 与设备 IO 随之中断。
  3. 执行 fn，结束后停止续租并释放锁。释放失败只记 Warn。
- 结果与失败：锁曾丢失时返回 ErrOrderLockLost 与 fn 错误的合并。outbox 轮询器把 ErrOrderBusy 当作「推后 5s、不计 attempts」处理；扫描器把它当作可跳过错误。

### 作业单迁移 Transition

- 入口：`internal/service/workorder.go` 的 `WorkOrderService.Transition` 与 `WorkOrderService.TransitionFrom`。
- 前置条件：必须在调用方事务内调用，本身不取 Redis 锁。
- 执行步骤：
  1. GetState 读当前状态与 row_ver。若用的是 TransitionFrom 且当前状态不等于要求的来源状态，则返回 ErrIllegalTransition。
  2. 用 CanTransition 查迁移表，不在表中返回 ErrIllegalTransition。
  3. UpdateStatus 带 row_ver 乐观锁更新 work_order，影响 0 行返回 ErrConcurrentUpdate。
  4. InsertTransition 写 work_order_transition（来源、去向、actor、reason_code）。
  5. AppendTx 追加 run_event(ORDER_TRANSITION)，payload 只含 order_id、from、to、reason_code。
- 结果与失败：任一步失败整个事务回滚。

## 审批

开票（`internal/service/approval.go` 的 `ApprovalService.Open`）属于主链路：它在 DRAFT 单上写 PREPARING 票、快照对象 `ticket-{order_id}-{ticket_seq}-{digest 前 16 位}` 和 constraint_check(PRE_APPROVAL)，并把单迁到 PENDING_APPROVAL。约束不通过时写 CONSTRAINT_BLOCKED，不建票（payload 由 `approval_blocked.go` 组装，上限 8KB，超出从尾部截断）。本章从票据激活开始。

### 票据激活

- 入口：`internal/service/approval.go` 的 `ApprovalService.Activate`。调用方有两个：`internal/agent/harness/runner/runner.go` 的 `Runner.interrupted`（run 以 WAIT_APPROVAL 中断后立即调用，失败只记 Warn），以及扫描任务 [ticket_activate](#ticket_activate)。
- 前置条件：run_id 非 0；run 已落检查点并置 INTERRUPTED(WAIT_APPROVAL)。
- 执行步骤：
  1. TicketByRun 读该 run 的票。若无票，或票既不是 PREPARING 也不是 OPEN，则返回 ErrNotActivatable；若已是 OPEN，则原样返回（幂等）。
  2. 按票的风险等级取 risk_matrix 的审批时效 TTL，expires_at = now + TTL。
  3. 开一个事务：
     - ActivateTx：UPDATE approval_ticket JOIN agent_run，条件是票为 PREPARING 且 run 为 INTERRUPTED(WAIT_APPROVAL)，置 OPEN 并写 expires_at；
     - 经 NotifyOutboxRepo.InsertTx 以 INSERT IGNORE 写 outbox(topic notify.send，kind PENDING_APPROVAL，dedup_key 由 NotifyDedupKey 生成)；
     - 追加 run_event(APPROVAL_PENDING)，payload 为 ticket_id、order_id、expires_at。
  4. 若 UPDATE 命中 0 行，则回滚后重读：票已被并发激活为 OPEN 就返回库中的票，否则返回 ErrNotActivatable。
- 结果与失败：成功返回 OPEN 票。runner 把它放进 Outcome.Ticket，主链路据此给提问人返回待审批信息。

### 待审批列表

- 入口：`internal/controller/decision.go` 的 `PendingHandler`，路由 `GET /approvals`，权限 advice.read；服务为 `internal/service/decision.go` 的 `DecisionService.Pending`。
- 前置条件：`?status` 只接受空或 OPEN，其他值返回 400。
- 执行步骤：
  1. ListPending 查本农场 ticket_kind=ORDER 且 status=OPEN 的票，按 created_at 排序，最多 50 条。PREPARING 票不可见。
  2. OrdersWithChecks 用两条 IN 查询批量取 work_order 与 constraint_check。
  3. 为每张票填 awaiting_confirm（需要双人确认且已有首审人时为 true）和作业单摘要（含 approval_expires_at）。
- 结果与失败：200，返回 `{"tickets":[...]}`。

### 审批详情

- 入口：`internal/controller/approval_l5.go` 的 `ApprovalDetailHandler`，路由 `GET /approvals/:ticket_id`，权限 advice.read；服务为 `internal/service/approval_detail.go` 的 `DecisionService.Detail`。只有配置了 HITL.Objects（对象存储）时 app 才挂这条路由。
- 前置条件：ticket_id 为非 0 整数，否则 400。
- 执行步骤：
  1. TicketTx 按 Scope 读票。查不到映射为 ErrNotInScope。
  2. OrdersWithChecks 读作业单与约束校验行，作业单缺失返回 500。
  3. RawReader.Get 从 MinIO 读快照对象，重算 sha256 并与票上的 snapshot_digest 比对。若不一致，则返回 SNAPSHOT_CORRUPT（500）。
  4. splitChecks 把校验行分成全部 PRE_APPROVAL 行，以及 attempt 最大的那一批 PRE_DISPATCH 行。
- 结果与失败：200，返回 ticket、awaiting_confirm、work_order、snapshot、risk_reasons、highlights、diff、pre_approval_checks、pre_dispatch_checks。ErrNotInScope 经 abortScoped 返回 403 并写拒绝审计（target `ticket:{id}`）。

### 审批决策

- 入口：`internal/controller/decision.go` 的 `DecideHandler`，路由 `POST /approvals/:ticket_id/decide`；服务为 `internal/service/decision.go` 的 `DecisionService.Decide`。路由层只要求用户持有 approval.decide.pesticide 或 approval.decide.other 之一，具体是哪一类由服务层按作业类型判定。
- 前置条件：
  - 请求头 X-Request-Id 必填，长度 1-64，缺失返回 400；ticket_id 必须是非 0 整数。
  - 请求体字段为 decision、snapshot_digest、comment、reason_code、reason_text。decision 只接受 APPROVE 或 REJECT；snapshot_digest 必须是 64 位十六进制；comment 不超过 512 字符。
  - 注：任务说明与背景文档提到「修改」决策，代码实际只有 APPROVE 与 REJECT 两种入参，不存在 MODIFY；库里还会出现 CONFIRM，那是双人确认票第二人通过时写入的存储值。
- 执行步骤：
  1. validateDecide 校验入参，不合规返回 ErrBadInput（400）。
  2. 走 [决策幂等与重放](#决策幂等与重放) 取得执行权，拿到后调 decideOnce。
  3. decideOnce 先按 request_id 查 approval_decision（uk_request）。若已有记录，则按重放规则返回原结果；否则进入 decide。
  4. decide 用 TicketTx 按 Scope 读票，查不到映射为 ErrNotInScope。
  5. 取 `lock:order:{order_id}`（TTL 10s，不续租），已被持有返回 ORDER_BUSY。持锁后重读一次票。
  6. 执行 [决策校验](#决策校验)。任一项不通过都会经 deny 写一条独立短事务审计 audit_log(APPROVAL, DENIED, target `ticket:{id}`，summary 带错误码)，然后返回错误。
  7. 若 decision 是 REJECT，则先校验驳回原因（reason_code 为 OTHER 时 reason_text 必填，否则 REJECT_REASON_INVALID），再执行 [驳回](#驳回)。
  8. 若 decision 是 APPROVE 且票需要双人确认（confirm_required 为真或风险等级 HIGH）而尚无首审人，则执行 [首审记录](#首审记录)。
  9. 其余 APPROVE 执行 [通过](#通过)；需要双人确认时存储值为 CONFIRM。
  10. 若事务里遇到 ErrConcurrentUpdate，则 explainConflict 重读票，把冲突解释为 TICKET_CLOSED、TICKET_EXPIRED 或 SNAPSHOT_STALE 返回。
- 结果与失败：成功返回 200，body 为 decision_id、ticket_id、status、awaiting_confirm。错误码映射：TICKET_CLOSED、TICKET_EXPIRED、SNAPSHOT_STALE、REQUEST_IN_FLIGHT、REQUEST_ID_CONFLICT、ORDER_BUSY 为 409；ROLE_INSUFFICIENT、SAME_APPROVER 为 403；REJECT_REASON_INVALID 与参数错误为 400。角色不足时 controller 另写一条 CROSS_FARM_DENIED 审计，op 为实际判定的审批类别；票不在本农场时经 abortScoped 返回 403 并审计。

#### 决策幂等与重放

- 入口：`DecisionService.Decide` 与 `DecisionService.replay`。
- 执行步骤：
  1. 生成随机 token，SetNX `idem:approve:{request_id}` = `PENDING:{token}`，TTL 10s。
  2. 若 SetNX 失败且现值以 PENDING 开头，则返回 REQUEST_IN_FLIGHT；若现值是 DONE，则走 replay。
  3. 若 SetNX 成功，则执行 decideOnce。失败时按 token 条件删除键（DeleteIf），让客户端可以重试；成功时把键改写为 `DONE:{decision_id}`，TTL 24h，改写失败只记 Warn。
  4. replay 按 request_id 读 approval_decision。查不到返回 REQUEST_IN_FLIGHT；租户、农场、票、操作人或决策（CONFIRM 视同 APPROVE）任一与本次请求不同，返回 REQUEST_ID_CONFLICT；否则返回原决策结果。
- 结果与失败：同一 request_id 重复提交得到同一结果，不会产生第二条决策。

#### 决策校验

- 入口：`DecisionService.check` 与 `DecisionService.decideOp`，在 lock:order 内执行，顺序固定：
  1. 票不是 OPEN → TICKET_CLOSED。
  2. expires_at 为空或已过 → 在本请求内执行 [票据过期收尾](#票据过期收尾)，然后返回 TICKET_EXPIRED。收尾失败只记错，由 approval_expire 扫描兜底。
  3. 请求的 snapshot_digest 与票上的不同 → SNAPSHOT_STALE。
  4. decideOp 读作业单 work_type：model.IsPesticide 为真取 approval.decide.pesticide，否则取 approval.decide.other。本农场票命中但作业单缺失按数据完整性错误返回 500。
  5. 用户须持有一个角色，该角色同时在票的 required_role 里且被权限矩阵授予上一步的操作；用户也不能是发起人。不满足 → RoleDeniedError（ROLE_INSUFFICIENT）。
  6. APPROVE 且用户就是已记录的首审人 → SAME_APPROVER。
- 结果与失败：通过时返回用于落库的角色。

#### 通过

- 入口：`DecisionService.approve`，在 lock:order 内执行。
- 执行步骤（单事务）：
  1. INSERT approval_decision（decision 为 APPROVE 或 CONFIRM，带 operator_role、snapshot_digest、comment）。同事务追加敏感审计 SENSITIVE.APPROVAL_DECIDE，target `decision:{id}`，summary 只含 ticket_id、decision、operator_role、snapshot_digest、request_id，不含 comment。
  2. 置票 APPROVED。若是 CONFIRM，则 ConfirmTicketTx 的 UPDATE 额外要求 first_approver_id 非空且不等于本人；否则 DecideTicketTx。两条 UPDATE 都要求票仍为 OPEN、expires_at > now、snapshot_digest 一致、row_ver 匹配，0 行即 ErrConcurrentUpdate。
  3. Transition 把作业单 PENDING_APPROVAL → APPROVED（actor 为用户，无 reason_code）。
  4. SetDispatchDeadlineTx 写 dispatch_deadline_at = now + DispatchWindow（默认 2h），条件是作业单为 APPROVED。
  5. INSERT outbox：topic order.dispatch，aggregate_id 为 order_id，dedup_key `order.dispatch:{order_id}:{ticket_id}:1`，payload 为 order_id、ticket_id、run_id，status PENDING，next_run_at = now。
  6. 追加 run_event(APPROVAL_DECIDED)，payload 为 ticket_id、order_id、decision、decision_id、operator_id。
- 提交后：
  1. Observer 记一次审批等待时长（开票 created_at 到现在）。
  2. 若票是复检退回后另开的票（ticket_seq > 1），则不唤醒 run，直接返回。
  3. 否则 resumeAsync 起一个协程，超时 2min，调 Resumer.Resume 让 run 从检查点续跑到结束。失败只记 Warn，由 [run_finalize](#run_finalize) 补偿。
- 结果与失败：返回 status APPROVED。作业单之后由 [outbox 轮询器](#outbox-轮询器) 投递给 [作业单下发总流程](#作业单下发总流程)。

#### 首审记录

- 入口：`DecisionService.recordFirst`，用于需要双人确认的票（confirm_required 为真或风险 HIGH）的第一次 APPROVE。
- 执行步骤（单事务）：
  1. INSERT approval_decision(APPROVE)，同样附带 SENSITIVE.APPROVAL_DECIDE 审计。
  2. SetFirstApproverTx：UPDATE approval_ticket 写 first_approver_id，条件是票为 OPEN、first_approver_id 为空、未过期且 row_ver 匹配。
- 结果与失败：票仍为 OPEN，作业单不动，不写 outbox，不写 run_event，不唤醒 run。返回 status OPEN、awaiting_confirm=true。第二位审批人（不能是首审人，也不能是发起人）再次 APPROVE 时进入 [通过](#通过)，存储值为 CONFIRM。

#### 驳回

- 入口：`DecisionService.reject`，在 lock:order 内执行。
- 前置条件：model.ValidateRejectReason 校验 reason_code 合法；不合法经 deny 审计后返回 REJECT_REASON_INVALID，票和作业单不动。
- 执行步骤（单事务）：
  1. INSERT approval_decision(REJECT) 与 SENSITIVE.APPROVAL_DECIDE 审计。
  2. DecideTicketTx 置票 REJECTED。
  3. InsertRejectionTx：先查该作业单引用的知识条目得到 kb_ids，再用 INSERT ... SELECT 从 work_order 取 order_id、advice_id、run_id 写 rejection_reason（reason_code、reason_text、operator_id、operator_role、kb_ids）。
  4. Transition 把作业单 PENDING_APPROVAL → REJECTED(APPROVAL_REJECTED)。
  5. 收尾 run：UPDATE agent_run 为 COMPLETED(APPROVAL_REJECTED)，条件是 run 为 INTERRUPTED(WAIT_APPROVAL)。若是首张票，则 0 行视为不一致，整个事务回滚；若是 ticket_seq > 1 的新票，则 0 行不报错，命中时记一条 Warn。
  6. INSERT IGNORE episodic_memory(kind REJECTED，ref_id 为作业单)，summary 为「作业单 X 审批驳回：{comment}」，截断到 512 字符，field_id 取自 agent_run。
  7. 追加 run_event(APPROVAL_DECIDED)。
- 结果与失败：返回 status REJECTED；Observer 记审批等待时长。不唤醒 run。

#### 票据过期收尾

- 入口：`DecisionService.expireLocked`。调用方有两个：[决策校验](#决策校验) 发现票已过期（actor 为用户），以及 `DecisionService.ExpireTicket`（[approval_expire](#approval_expire) 扫描调用，先取 lock:order，actor 为 system）。
- 执行步骤（单事务）：
  1. ExpireTicketTx：UPDATE approval_ticket 置 EXPIRED，条件是票为 OPEN 且 row_ver 匹配。0 行说明票已被决策或改写，直接返回 false，什么也不写。
  2. Transition 把作业单 PENDING_APPROVAL → EXPIRED(APPROVAL_EXPIRED)。
  3. 按 [驳回](#驳回) 第 5 步的同一规则把 run 收尾为 COMPLETED(APPROVAL_EXPIRED)。
  4. 追加 run_event(APPROVAL_DECIDED)，payload 的 decision 为 EXPIRED。
- 结果与失败：返回是否真正过期。不写 approval_decision，也不写 outbox 通知。

## HITL 扫描器

- 入口：`internal/service/scan.go` 的 `Scanner.Run`，由 `internal/app/worker.go` 的 `App.WorkerLoops` 以 scanner 循环登记，在 cmd/worker 进程内运行；装配在 `internal/app/hitl.go`。
- 注：scan.go 文件头注释写的是「server 内扫描任务」，代码实际只在 cmd/worker 里启动（scanSystem 变量的注释也写了「P1-L4 随扫描迁到 cmd/worker」）。
- 前置条件：Scanner 用跨农场凭证 SystemScope("server_scan")，跨农场查询只在 repository 内进行。
- 执行步骤：
  1. Run 启动时，若 approval_expiring 缺 Expiring 或 Notify 依赖，则记一条 Warn 并不注册该任务。
  2. 每 30s（Interval 为 0 时取 DefaultScanInterval）执行一轮 RunOnce，按固定顺序跑各任务：approval_expire、ticket_activate、run_finalize、stuck_run，再按依赖是否齐全追加 approval_expiring、audit_anchor、retention、advice_no_citation。
  3. 每个任务先取 `lock:scan:{task}`（TTL 60s）。若已被其他实例持有，则跳过该任务；取到则执行，结束后释放，释放失败记 Warn。
  4. 单个任务失败不影响其余任务，错误合并后记一条 Warn（scan round）。
  5. 逐条处理时，ErrOrderBusy、ErrConcurrentUpdate、ErrIllegalTransition 视为可跳过，留给下一轮或说明已被他人收尾。
- 结果与失败：ctx 取消后退出，退出前等待所有异步 Resume 结束。approval_expiring 每轮查 expires_at 在 [now, now+1h] 的 OPEN 票（最多 100 张），逐张以 INSERT IGNORE 写 notify.send(EXPIRING_SOON)，dedup_key `notify:EXPIRING_SOON:{order_id}:{ticket_id}`，每张票只提醒一次；其余追加任务不属于本章。

### approval_expire

- 入口：`Scanner.approvalExpire`。
- 执行步骤：
  1. ListExpired 查 `ticket_kind='ORDER' AND status='OPEN' AND expires_at < now`，最多 100 张。
  2. 逐张调 DecisionService.ExpireTicket：取 lock:order 后执行 [票据过期收尾](#票据过期收尾)。票已被决策时 UPDATE 0 行，静默跳过。
  3. ListDispatchOverdue 查 `work_order.status='APPROVED' AND dispatch_deadline_at < now`，最多 100 张。
  4. 逐张 expireOrder：取 lock:order，在事务内 TransitionFrom APPROVED → EXPIRED(APPROVAL_EXPIRED)，actor 为 system。若作业单已下发，则 TransitionFrom 返回非法迁移，按可跳过处理。
- 结果与失败：过期票对应的作业单变为 EXPIRED，run 收尾为 COMPLETED(APPROVAL_EXPIRED)；超过下发时限仍未下发的 APPROVED 单变为 EXPIRED。这一步不写票据，也不写 outbox。

### ticket_activate

- 入口：`Scanner.ticketActivate`。
- 执行步骤：
  1. ListPreparing 关联 agent_run，查 `status='PREPARING' AND created_at < now-30s` 的票，最多 100 张，带回 run 的 status 与 interrupt_type。
  2. 若 run 为 INTERRUPTED(WAIT_APPROVAL)，则调 [票据激活](#票据激活)（Gate 为空时跳过），ErrNotActivatable 不计错误。
  3. 若 run 已终态，则 voidTicket：取 lock:order，在单事务内 VoidPreparingTx（UPDATE 票 PREPARING → EXPIRED，row_ver 守卫，0 行跳过），再 Transition 作业单 → EXPIRED(APPROVAL_EXPIRED)，actor 为 system。
  4. 若 run 仍是 RUNNING 或 INTERRUPTED(SYSTEM_ERROR)，则不处理，交给 [stuck_run](#stuck_run)。
- 结果与失败：正常路径由 runner 中断后立即激活，这个任务只补漏。

### run_finalize

- 入口：`Scanner.runFinalize`。
- 执行步骤：
  1. ListApprovedInterrupted 查 run 为 INTERRUPTED(WAIT_APPROVAL)、对应票为 APPROVED 且 decided_at 早于 now-60s 的 run，最多 100 个。这种情况说明决策后的异步 Resume 失败了。
  2. 逐个 resumeAsync：协程内超时 2min 调 Resumer.Resume，Resume 自己持有 `lock:run:{id}`，重复触发由锁与 row_ver 挡住。
  3. 若 Resume 返回 ErrNotResumable（无检查点或图版本已变），则 failRun：单事务内 FailInterruptedTx 把 run 从 INTERRUPTED(WAIT_APPROVAL) 置为 FAILED(RETRY_EXHAUSTED)（row_ver 守卫），再把该 run 下仍为 DRAFT 的作业单 Transition 为 CANCELED(RETRY_EXHAUSTED)。其他错误只记 Warn，下一轮重试。
- 结果与失败：作业单已是 APPROVED，不在 DRAFT 之列，所以 failRun 不影响下发。

### stuck_run

- 入口：`Scanner.stuckRun`。
- 执行步骤：
  1. ListStuck 查 `status='RUNNING' AND updated_at < now-90s` 的 run，最多 100 个。
  2. 逐个探测 `lock:run:{id}` 是否存在。若锁仍在，则说明 run 仍在执行，跳过；探测失败计入错误。
  3. 锁不存在时 MarkSystemError：UPDATE run 为 INTERRUPTED(SYSTEM_ERROR)，sys_retry+1，条件是仍为 RUNNING、updated_at 仍早于阈值、row_ver 匹配。
  4. ListSystemError 查所有 INTERRUPTED(SYSTEM_ERROR) 的 run。若 sys_retry > 3，则 failRun（同 [run_finalize](#run_finalize) 第 3 步，来源中断类型为 SYSTEM_ERROR）；否则 resumeAsync 重入，不可续时同样 failRun。
- 结果与失败：卡住的 run 最多自动重入 3 次，之后置 FAILED(RETRY_EXHAUSTED)，其 DRAFT 作业单置 CANCELED。

## outbox 轮询器

- 入口：`internal/service/outbox.go` 的 `OutboxPoller.Run`，由 `internal/app/worker.go` 的 `App.NewOutboxPoller` 构造，只在 cmd/worker 里运行（评测排空也复用它）。处理器表由 MergeOutboxHandlers 合并，同一 topic 注册两次或处理器为空都会报错：
  - order.dispatch → [作业单下发总流程](#作业单下发总流程)；
  - notify.send → [notify.send 处理器](#notifysend-处理器)；
  - order.cancel → [order.cancel 处理器](#ordercancel-处理器)；
  - field.history.append → [field.history.append 处理器](#fieldhistoryappend-处理器)；
  - audit.export → 审计导出（不属于本章）。
- 前置条件：outbox 行由业务事务以 status PENDING 写入，dedup_key 唯一。
- 执行步骤：
  1. 每 1s 执行一轮 RunOnce。
  2. Claim 开一个事务：`SELECT id FROM outbox WHERE status='PENDING' AND next_run_at<=now ORDER BY next_run_at LIMIT 50 FOR UPDATE SKIP LOCKED`，把这些行的 next_run_at 改为 now+60s（租约）并 row_ver+1，再读回整行。多副本靠 SKIP LOCKED 与 row_ver 分开领取。
  3. 逐条串行处理。ctx 取消后不再开始新的消息。
  4. handle 为每条消息起续租协程，每 20s 用 row_ver 守卫把 next_run_at 再推后 60s。若续租命中 0 行，则说明租约已被别人拿走，以 ErrOutboxLeaseLost 取消处理器并丢弃本次结果。
  5. 按 topic 找处理器，超时 2min。未知 topic 返回 ErrUnknownTopic；处理器 panic 被转成错误。
  6. settle 按处理结果落库，均带 row_ver 守卫：
     - 成功 → MarkDone，status DONE；
     - ErrOutboxDeviceOffline → next_run_at 推后 1 分钟，last_error 写 DEVICE_OFFLINE，attempts 不变；
     - ErrOrderBusy 或 ErrOutboxDeferred → next_run_at 推后 5s，attempts 不变；
     - 其他错误 → MarkRetry：attempts+1，last_error 截断到 512 字符；第 n 次失败后依次退避 1s、5s、30s、2min、10min，attempts+1 达到 5 时 status 置 DEAD。
  7. 变为 DEAD 时 auditDead 写审计 OUTBOX_DEAD（target `outbox:{id}`，结果 FAILED，summary 含 outbox_id、topic、aggregate_id、dedup_key、attempts、last_error），并记一条 ERROR 日志。
- 结果与失败：同一条消息至多被一个实例处理；处理器必须自己保证重入幂等。
- 注：`internal/repository` 里 MarkDoneTx 的注释写的是「下发结果 / 过期 / 挂起收尾同事务置 DONE」，代码实际没有任何调用方，outbox 行只由轮询器在处理器返回后置 DONE。

## 作业单下发总流程

- 入口：`internal/service/workorder_dispatch.go` 的 `WorkOrderService.Dispatch`，作为 outbox topic order.dispatch 的处理器。依赖由 `WorkOrderService.SetDispatch` 装配，缺 Adapter、Store、Tx、Locks、Flags、Audit、Logger、Devices、Attempts、Idem、Picker、Epochs、Notify、离线文案 key 或 Tickets 任一项，或 max_attempts < 1、receipt_timeout / device_wait_max 不为正，都返回 ErrDispatchNotConfigured。配置默认值见 `internal/config/dispatch.go`：max_attempts=2，receipt_timeout=30m，device_wait_max=2h。
- 前置条件：消息来自 [通过](#通过)（attempt 缺省为 1），或来自 [回执处理](#回执处理) 中 NOT_EXECUTED 回执写入的重试消息（attempt = n+1）。
- 执行步骤：
  1. [消息解析与准入](#消息解析与准入)。REAL 单在准入前先按 idem_key 查已有尝试，必要时进入 [REAL 续跑](#real-续跑)。
  2. 记录 flagReadAt = now，再进入 [下发开关](#下发开关)。
  3. Epochs.RecheckEpoch 为该 run 分配新的复检 epoch（resume_epoch+1 并持久化）。选设备和复检都用这个 epoch，每次推后重投都会重新分配。
  4. [设备绑定](#设备绑定)。若等待超限已放弃下发，则返回 nil。
  5. [下发前复检闸门](#下发前复检闸门)。被拦下则本条消息处理完毕。
  6. 若是 DRY_RUN 单，则进入 [DRY_RUN 下发](#dry_run-下发)；若是 REAL 单，则进入 [REAL 下发](#real-下发)。
- 结果与失败：返回 nil 时轮询器置 outbox DONE；ErrOutboxDeviceOffline 推后 1 分钟，ErrOrderBusy / ErrOutboxDeferred 推后 5s，都不计 attempts；ErrDispatchState、ErrBadOutboxPayload 等其他错误按退避重试，第 5 次失败变 DEAD。下发器不写 episodic_memory，也不回写 field.history。

### 消息解析与准入

- 入口：`WorkOrderService.parseDispatch`、`WorkOrderService.resumeAttempt`、`WorkOrderService.admit`。
- 执行步骤：
  1. parseDispatch 解析 payload {order_id, ticket_id, run_id, attempt}。order_id 必须非 0 且等于 outbox.aggregate_id；attempt 缺省 1，必须在 [1, MaxAttempts]；dedup_key 非空时必须等于 `order.dispatch:{order_id}:{ticket_id}:{attempt}`。任一不符返回 ErrBadOutboxPayload。
  2. OrderForDispatch 读作业单。payload 的 run_id 非 0 且与单上不同 → ErrBadOutboxPayload。
  3. 若是 REAL 单，则 dedup_key 与 ticket_id 必填，再用 dedup_key 作为 idem_key 调 resumeAttempt 查 dispatch_attempt：
     - 查不到 → 继续；
     - 已有 device_job_id 或状态不是 SENT → 视为重复投递，返回 nil；
     - SENT 且无 device_job_id → 取 lock:order，锁内重读该尝试后执行 [REAL 续跑](#real-续跑)。
  4. admit 按状态分流。作业单已终态 → 记 Info（duplicate delivery），返回 nil。
  5. 若 attempt > 1：
     - 单不是 REAL 或不是 DISPATCHED → 记 Warn 并丢弃；
     - 已过 dispatch_deadline_at → [重试被拦](#重试被拦)；
     - 否则调 admitTicket（见 [设备调用前拦截](#设备调用前拦截)）。
  6. 若 attempt = 1：
     - DRY_RUN 单处于 DISPATCHED 且没有 dispatch_result（上次崩溃在模拟途中）→ 记 Warn，直接从模拟一步续跑 lockedDispatch(intent=false)；
     - 单处于 PENDING_APPROVAL（已复检退回重审，会另开票另写消息）→ 记 Warn 并丢弃；
     - 单不是 APPROVED → ErrDispatchState；
     - 已过 dispatch_deadline_at → 取 lock:order，事务内 TransitionFrom APPROVED → EXPIRED(APPROVAL_EXPIRED)；
     - 否则调 admitTicket。
- 结果与失败：准入阶段不碰设备。

### 下发开关

- 入口：`WorkOrderService.Dispatch` 的模式分支与 `internal/service/dispatch_gate.go` 的 `WorkOrderService.holdReal`。
- 执行步骤：
  1. DRY_RUN 单不看开关。dispatch_mode 既不是 DRY_RUN 也不是 REAL → ErrDispatchState。
  2. REAL 单用 BoolLive 直读 MySQL 中的 enable_robot_dispatch（不走缓存），读失败返回错误。
  3. 若开关关闭且 attempt > 1，则执行 [重试被拦](#重试被拦)。
  4. 若开关关闭且 attempt = 1，则 holdReal：单事务写 audit_log(DISPATCH_HELD，actor system，结果 DENIED，target `order:{id}`，summary 为 order_id、ticket_id、dispatch_mode、flag_key)，记 Warn，返回 nil。作业单保持 APPROVED，开关恢复后也不补发，到 dispatch_deadline_at 由 [approval_expire](#approval_expire) 转 EXPIRED。
  5. 若开关打开但下发前复检服务未配置（Recheck 为空），则记 ERROR 日志 alert=REAL_DISPATCH_UNAVAILABLE，返回 ErrDispatchState。
- 结果与失败：只有开关打开且复检可用时 REAL 单才继续。

### 设备绑定

- 入口：`internal/service/dispatch_device.go` 的 `WorkOrderService.bindDevice`，选设备由 `ToolDevicePicker.PickDevice` 完成。
- 执行步骤：
  1. PickDevice 按 device_type 查设备类别：uav / drone → drone，knapsack / vehicle → sprayer，valve / fertigation → pump；不在表内（如 manual）→ ErrDeviceNotBindable。
  2. 经 mcp-device 工具（step_id 为 pre_dispatch，带本次 epoch）调 device.list{field_id, kind}，列出本地块该类设备。payload 里已绑定的 device_id 若在列表中则排第一。
  3. 逐台调 device.status，返回第一台 online 且 state 为 idle 的设备。某台工具非 OK 时先看其余设备；全部不可用时，若曾有工具失败则返回该失败（ErrDeviceToolFailed），否则返回 ErrDeviceUnavailable。
  4. 若 DRY_RUN 单的类型不可绑定，则记 Info 后不绑定，照常模拟。
  5. 若选不到设备（ErrDeviceUnavailable，或 REAL 单的 ErrDeviceNotBindable），则判断等待是否超限：单上有 dispatch_deadline_at 时以它为准；没有时以 outbox.created_at 起算超过 DeviceWaitMax 为准。
     - 未超限 → deferUnavailable：单事务写 audit_log(DEVICE_UNAVAILABLE，system，DENIED，target `order:{id}`)；INSERT IGNORE outbox notify.send(kind DEVICE_OFFLINE，dedup_key `notify:DEVICE_OFFLINE:{order_id}:{ticket_id}`)；若通知是首次插入，再追加 run_event(DEGRADED，fault DEVICE_OFFLINE，action HOLD_AND_NOTIFY)。记 Warn 后返回包装 ErrOutboxDeviceOffline 的错误，outbox 推后 1 分钟。
     - 超限 → giveUpUnavailable：取 lock:order，事务内重读。已终态则不动；attempt = 1 且为 APPROVED → EXPIRED；attempt > 1 且为 DISPATCHED → FAILED；reason_code 都是 DEVICE_UNAVAILABLE；同事务写 DEVICE_UNAVAILABLE 审计（结果 FAILED，gave_up=true，带 wait_since 与 to）。记 ERROR 日志后返回 nil，outbox 置 DONE。
  6. 若是其他工具失败，则按一般错误退避重试，不写离线审计也不发通知；非超时、非上游错误（如归属校验拒绝）另记 Warn。
  7. 选中的设备与 payload 里已绑定的相同时不写库。否则取 lock:order，事务内重读单；状态变了返回 ErrDispatchState，没变则 BindDeviceTx 把 device_id 写进 work_order.payload（row_ver 守卫）。记 Info 后重读并返回绑定后的单。
- 结果与失败：REAL 单此后必定带 device_id。

### 下发前复检闸门

- 入口：`internal/service/dispatch_gate.go` 的 `WorkOrderService.recheckGate`，复检本身是 `internal/service/recheck.go` 的 `RecheckService.PreDispatch`。在锁外执行。
- 执行步骤：
  1. 若 Recheck 未配置，则记 Warn 跳过。只有 DRY_RUN 单会走到这里，REAL 单已在 [下发开关](#下发开关) 失败关闭。
  2. RecheckSource 从 agent_run 取 user_id、field_id，从该 run 的第一条 run_event 取原问题；Cards.GetByRun 取原建议卡。
  3. PreDispatch 调 Rechecker.Recheck（带本次 epoch 与作业单），得到 Changed、Detail、Checks；Blocked 为未通过约束的 rule_id 列表。
     - Blocked 非空 → 记 Warn，直接返回，不取消原单；
     - 未变化，或这是重试（attempt > 1）→ 直接返回；
     - 首次下发且结论变化 → 取 lock:order，事务内 TransitionFrom APPROVED → CANCELED(CONDITION_CHANGED)；再调 Starter.Ask 以原问题开一个新 run（Supersedes 为旧 run）。若本农场 enable_advice 已关（ErrAdviceDisabled），则不建新 run，NewRunID=0，不算失败。取消与建新 run 不在同一事务里。
  4. InsertPreDispatchChecks 以 INSERT IGNORE 写 constraint_check(PRE_DISPATCH，attempt = epoch)。写失败时，只有「首次、结论变化、无 Blocked」（原单已取消）这一种情况只记 ERROR 日志，其余返回错误让 outbox 重试。
  5. 按结论处置，Blocked 优先于 Changed：
     - Blocked 且是重试 → [重试被拦](#重试被拦)；
     - Blocked 且是首次 → [复检退回重审](#复检退回重审)；
     - Changed 且是重试 → [重试被拦](#重试被拦)；
     - Changed 且是首次 → supersede：NewRunID 非 0 时 SupersedeRun 在旧 run 上写 superseded_by_run_id（只在该列为空时写，0 行记 Warn），然后记 Info。
- 结果与失败：任一处置都表示本条消息处理完毕，不再下发；都通过才进入模拟或真实下发。

### DRY_RUN 下发

- 入口：`WorkOrderService.lockedDispatch`、`recordIntent`、`recordResult`，全程持 lock:order（WithOrderLock，续租）。
- 执行步骤：
  1. 锁内重读作业单。intent=true 时执行 recordIntent：已终态 → 结束；不是 APPROVED → ErrDispatchState；已过下发时限 → 事务内 APPROVED → EXPIRED(APPROVAL_EXPIRED)；否则 admitTicket，再单事务 TransitionFrom APPROVED → DISPATCHED（actor system）并追加 run_event(DISPATCHED，phase INTENT，dry_run=true，device_touched=false)。
  2. intent=false（崩溃续跑）时要求单仍为 DISPATCHED 且没有结果，否则 ErrDispatchState。
  3. [设备调用前拦截](#设备调用前拦截)（DryRun 模式）。
  4. Adapter.DryRun 生成模拟指令，不接触任何设备。
  5. recordResult 单事务：重读 row_ver，SetDispatchResultTx 写 work_order.dispatch_result（dry_run=true、device_touched=false、adapter 名、commands、params{work_type, device_type, payload, time_window}、simulated_at），Transition DISPATCHED → DONE（跳过 EXECUTING），追加 run_event(DISPATCHED，phase RESULT)。EventRepo 在同事务把 DISPATCHED 事件投影为 DISPATCH 审计。
- 结果与失败：Observer 记 DRY_RUN 下发成功，记 Info（dry-run done）。DRY_RUN 单不走回执、不写 field.history。

### REAL 下发

- 入口：`WorkOrderService.dispatchReal`，全程持 lock:order（WithOrderLock，续租；续租失败会取消 ctx，设备 IO 随之中断）。
- 执行步骤：
  1. 锁内按 idem_key 再查一次 dispatch_attempt。若已存在（并发 worker 已写过），则转 [REAL 续跑](#real-续跑)。
  2. 重读作业单并 realReady：已终态 → 结束；attempt > 1 而单不是 DISPATCHED → 记 Warn 丢弃；attempt = 1 而单不是 APPROVED → ErrDispatchState；attempt = 1 且已过下发时限 → 转 EXPIRED；最后 admitTicket。
  3. payload 里没有 device_id → ErrDispatchState。Devices.Get(device_type) 取适配器；不是 Traced 装饰过的实现（不同时具备 Archive 与 DispatchArchived）→ ErrDispatchState。
  4. Archive 把设备指令写入 MinIO（见 [设备注册表与模拟平台](#设备注册表与模拟平台)），得到 command_raw_id。
  5. recordSentIntent 单事务：InsertSentTx 写 dispatch_attempt（status SENT，device_type、device_id、idem_key、mode REAL、command_raw_id、flag_read_at、sent_at、receipt_due_at = now + receipt_timeout）；attempt = 1 时 TransitionFrom APPROVED → DISPATCHED；追加 run_event(DISPATCHED，phase INTENT，带 attempt、device_type、device_id)。同一 idem_key 已写过返回 ErrDuplicateAttempt，outbox 重试后走续跑。
  6. markIdem：SetNX `idem:dispatch:{order_id}:{ticket_id}:{attempt}` = idem_key，TTL 7d。首次下发时键已存在，说明另有处理者，返回 ErrDispatchState，不调设备。
  7. [设备调用前拦截](#设备调用前拦截)。
  8. DispatchArchived 带 idem_key 和 command_raw_id 调设备平台，ctx 带作业单归属供 trace 使用。
  9. recordSent 按返回处置：
     - 无 job 的 FAILED 回执、且不是 NOT_EXECUTED → 尝试置 FAILED(原 failure_kind)，进入待对账；Observer 记 MANUAL；记 ERROR 日志 alert=DISPATCH_MANUAL。作业单保持 DISPATCHED，不重发。
     - 平台明确拒绝（ErrRejected，或无 job 的 FAILED+NOT_EXECUTED）→ 单事务：尝试置 FAILED(NOT_EXECUTED)，TransitionFrom DISPATCHED → FAILED(DISPATCH_REJECTED)，追加 DISPATCHED(RESULT)；Observer 记 REJECTED，记 Warn。
     - 其他调用错误（超时、不可用等）→ Observer 记 ERROR，返回错误；尝试保持 SENT，outbox 重试时走续跑。
     - 返回成功但没有 device_job_id → 返回 ErrBadReceipt，同样保持 SENT。
     - 已受理 → 单事务 SetJobTx 回填 device_job_id、回执状态、receipt_due_at = now + receipt_timeout（row_ver 守卫），追加 DISPATCHED(RESULT，device_touched=true)；Observer 记 OK，记 Info。
- 结果与失败：已受理后的推进全部交给 [设备回执 webhook](#设备回执-webhook) 与 [回执超时扫描](#回执超时扫描)。

### REAL 续跑

- 入口：`WorkOrderService.resumeLocked`，调用方已持 lock:order。处理「已写 SENT 尝试但没拿到 device_job_id」的情况（上次在调设备前后崩溃或设备调用报错）。
- 执行步骤：
  1. 尝试已有 job 或不再是 SENT → 结束。作业单不是 DISPATCHED → 记 Warn 后结束。
  2. Devices.Get 取适配器，读 Capabilities。
  3. 若支持 ExternalQuery，则 QueryStatus(idem_key)：
     - 查到 → 记 Warn，按 [REAL 下发](#real-下发) 第 9 步 recordSent 回填；
     - 报 ErrJobNotFound 以外的错误 → 返回错误，outbox 退避；
     - 查无此单且不支持 IdemKey → toManual（平台可能已受理而外部单号索引尚不可见，重发会造成二次作业）。
  4. 若两种能力都不支持，则 toManual。
  5. 适配器不支持 DispatchArchived → ErrDispatchState。
  6. 重发前再直读 enable_robot_dispatch。关闭 → toManual，不调设备。
  7. [设备调用前拦截](#设备调用前拦截)；markIdem（重发时键已存在属正常）。
  8. refreshSent 单事务 RefreshSentTx：flag_read_at 改为本次读开关时刻，sent_at 改为 now，receipt_due_at 改为 now + receipt_timeout（row_ver 守卫）。
  9. 记 Warn 后带原 idem_key 与原 command_raw_id 重发 DispatchArchived，再 recordSent。
- toManual：单事务把尝试置 FAILED(UNKNOWN)（进入待对账列表），写 audit_log(DISPATCH_MANUAL，system，FAILED，target `order:{id}`，summary 为 order_id、attempt、device_type、idem_key、reason)；记 ERROR 日志 alert=DISPATCH_MANUAL。作业单保持 DISPATCHED，不重发。
- 结果与失败：只有平台按 idem_key 去重时才会重发。

### 设备调用前拦截

- 入口：`internal/service/dispatch_guard.go` 的 `WorkOrderService.guardDeviceCall` 与 `WorkOrderService.admitTicket`，二者共用 ticketBlockReason。
- 执行步骤：
  1. ticketBlockReason 读 order.dispatch 消息里的审批票：ticket_id 为 0、票不存在、票不属于本单、票不是 APPROVED，任一成立即给出拦截原因；读库失败返回错误。
  2. admitTicket 在任何写入之前调用（admit、realReady、recordIntent）。有拦截原因时 fireBlocked，再记 ERROR 日志，返回 done=true，消息被丢弃并置 DONE，单和尝试都不动。复检退回后旧票已 SUPERSEDED 的过时消息就在这里被丢掉。
  3. guardDeviceCall 在每次可能动设备的调用之前、锁内执行（DryRun、REAL 首发、续跑重发）：重读作业单，要求为 DISPATCHED；DryRun 时还要求尚无 dispatch_result；再查票。
  4. 有拦截原因时 fireBlocked，返回包装 ErrPreApprovalDevice 的错误，outbox 退避重试；读库失败原样返回，不告警。
  5. fireBlocked：Observer 记 BLOCKED，并经 AlertSink 发 P0 告警 pre_approval_device（带 order_id、run_id、detail）。
- 结果与失败：审批未通过时不会调用设备适配器。

### 重试被拦

- 入口：`internal/service/dispatch_retry.go` 的 `WorkOrderService.failRetry`。触发点是 attempt > 1 时：超过下发时限、开关关闭、复检约束不通过、复检结论变化。
- 执行步骤：
  1. 取 lock:order（WithOrderLock）。
  2. 单事务 TransitionFrom DISPATCHED → FAILED(RETRY_BLOCKED)，actor system。
  3. 记 Warn，带拦截原因。
- 结果与失败：返回 nil，outbox 置 DONE，不调设备。

### 复检退回重审

- 入口：`WorkOrderService.reopenBlocked`，落库由 `internal/service/approval_reopen.go` 的 `ReopenService.Prepare` 与 `ReopenService.Reopen` 完成。触发点是首次下发时复检约束不通过。
- 执行步骤：
  1. 锁外 Prepare：rule_ids 不能为空。读旧票，要求属于本单且为 APPROVED，否则 ErrBadApproval。新票 ticket_seq+1，沿用旧票的风险等级、required_role、confirm_required、initiator_id，状态直接为 OPEN；把新快照写入 MinIO（不重新判定风险原因）。
  2. 取 lock:order，重读作业单；不是 APPROVED → ErrDispatchState。
  3. Reopen 单事务：
     - LockOrderTx 锁 work_order 行；
     - SupersedeTicketTx 把旧票 APPROVED → SUPERSEDED（row_ver 守卫，0 行即整事务回滚）；
     - TransitionFrom APPROVED → PENDING_APPROVAL(RECHECK_FAILED)；
     - InsertReopenedTicketTx 插入新票，expires_at = now + 风险 TTL；
     - 用约束复核结果写 constraint_check(PRE_APPROVAL，attempt = 新 ticket_seq)，未通过的项照样落库给审批人看；
     - INSERT IGNORE outbox notify.send(kind RECHECK_RETURNED，dedup_key `notify:RECHECK_RETURNED:{order_id}:{旧 ticket_id}`)；
     - 追加 run_event(APPROVAL_OPEN，actor system，payload 含新票 id、ticket_seq、reopened_from、reason、rule_ids)。
  4. 通知已存在时记 Warn；最后记 Info 与 Warn。
- 结果与失败：不唤醒 run，也不关 run。新票批准后写 `order.dispatch:{order_id}:{新 ticket_id}:1`，重新走下发。
- 注：approval_reopen.go 中 recheckReturned 的注释写的是「真实通道在 L5，worker 占位处理」，代码实际已由 [notify.send 处理器](#notifysend-处理器) 真实处理（app/approval_l5.go 注释也写了「替换 L4-A 占位」）。

## 设备注册表与模拟平台

- 入口：`internal/app/devices.go` 的 `App.buildDevices`（启动装配）；`internal/adapter/registry.go` 的 `Registry`；`internal/adapter/traced.go` 的 `Traced`；`internal/adapter/devicesim/client.go` 的客户端；`internal/service/devicetrace.go` 的 `DeviceTraceLog`；模拟平台进程 `cmd/devicesim`。
- 前置条件：配置 devices.devicesim.enabled 为真时才登记可开放设备；此时 env 必填，CheckDeploy 要求 env 不是 prod 且 base_url 是回环地址，否则启动失败。
- 执行步骤：
  1. 用 base_url、timeout 和配置的能力（cancel、idem_key、external_query）构造 devicesim 客户端。
  2. 对配置的每个 device_type，用 NewTraced 包一层 Traced（带 DeviceTraceLog、RawStore、时钟），再 Registry.Register。Register 调 CheckCapabilities：必须支持 Cancel，且 IdemKey 与 ExternalQuery 至少支持一项，否则登记失败、启动失败。
  3. RegisterSkeletons 把其余真实设备类型以「协议未提供，本阶段不开放」登记为不可开放。Registry.Get 对这些类型返回 ErrDeviceNotOpen。
  4. 启动日志逐行打印每个类型是否可开放及其能力。
  5. 主链路 to_order 通过 deviceDispatchMode 决定 dispatch_mode：开关给出 REAL 且该类型可开放时才写 REAL，否则写 DRY_RUN。
- Traced 的行为：
  - Archive：MinIO 对象键为 `raw/{tenant}/{farm}/{作业窗口起始日}/{run_id}/DEVICE_CMD/cmd-{sha256(idem_key) 前 32 位}.json`，日期取 time_window.from（缺省取当前时间），所以同一 idem_key 重试时键不变。内容优先用适配器的 EncodeCommand，否则是通用指令 JSON（idem_key、order_id、run_id、field_id、device_type、work_type、payload、time_window）。
  - DispatchArchived：command_raw_id 为 0 时返回 ErrRejected，不调设备；否则调下层 Dispatch。
  - QueryStatus / Cancel：从 ctx 的 WithTraceOrder 取作业单归属，缺失时记 Warn。
  - 每次调用结束都调 RecordDeviceCall。tool_call_id 为 `dev-{sha256(类型/方法/作业单/纳秒时间) 前 24 位}`。
- DeviceTraceLog.RecordDeviceCall 写一条 slog（msg=trace，span=device），字段有 tool_call_id、name、device_type、tenant、farm、order、run、idem_key、device_job_id、status、code、latency_ms，有指令原文时带 command_raw_id；调用出错时用 Warn 级别。
- devicesim 客户端：Dispatch 为 `POST /v1/jobs`（平台按 idem_key 幂等）；QueryStatus 有 job 时 `GET /v1/jobs/{id}`，只有 idem_key 时 `GET /v1/jobs?external_no=`（需要 ExternalQuery）；Cancel 为 `POST /v1/jobs/{id}/cancel`。错误映射：超时 → ErrTimeout；连不上或 5xx → ErrUnavailable；404 → ErrJobNotFound；其他 4xx → ErrRejected。
- cmd/devicesim：默认 `--addr 127.0.0.1:8090 --devices configs/mock/device.yaml`，作业状态只在内存里。可用 `PUT /sim/v1/scripts/{order_id}` 为某张单预置回执脚本。
- 注：buildDevices 的注释写的是「本层下发器仍只走 DryRun」，代码实际已有 REAL 通道（见 [REAL 下发](#real-下发)），可开放类型会拿到 REAL 单。

## 设备回执 webhook

- 入口：`internal/controller/receipt.go` 的回执控制器，路由 `POST /api/v1/farms/:farm_id/orders/:order_id/receipts`；业务在 `internal/service/receipt_webhook.go` 的 `OrderOpsService.Webhook`。
- 前置条件：
  - 只有配置了 ReceiptSecret 才挂载该路由，否则启动时记 Warn、路由不存在。
  - 只经过 RequestID 中间件，不走农场鉴权，改用 HMAC 签名鉴权。
  - 请求体上限 64KiB，超过返回 413。请求头需要 X-Timestamp 与 X-Signature。
- 执行步骤：
  1. 验签（VerifyReceiptSignature）：签名为 hex(HMAC-SHA256(secret, 时间戳 + "." + 原始请求体))，`sha256=` 前缀可有可无且不区分大小写；时间戳为 Unix 秒，须在当前时间 ±5 分钟内；用 hmac.Equal 比较。secret 为空同样判失败。若失败则记 Warn 并返回 ErrReceiptAuth。
  2. 解析 JSON：receipt_id、device_type、device_job_id、status、failure_kind、done_area_mu、device_ts、code。路径里的 farm_id、order_id 必须非 0，device_type、device_ts 必填，receipt_id 不超过 96 字符，再过回执自身校验；任一不符返回 ErrBadInput。
  3. 计算回执 ID（ReceiptIDOf）：若平台给了 receipt_id 则直接用，否则为 `{来源}-` 加 sha256(来源|job|status|kind|面积(两位小数)|device_ts 毫秒) 的前 40 位。
  4. 若没有 device_job_id，则按「无法匹配」处理（原因 no device_job_id），见下方 unmatched。
  5. 以回执专用的系统凭证按 (device_type, device_job_id) 查归属尝试（Lookup.ByJob）：
     - 查不到且 device_ts 早于当前时间 10 分钟以上 → 按 unmatched 处理；
     - 查不到但在 10 分钟内 → 返回 ErrReceiptUnknownJob（可能是下发事务尚未提交，让平台重投）；
     - 查到但归属的 farm 或 order 与路径不一致 → 写拒绝审计（DenyResource，target `order:{id}`，带路由与 request_id），返回 ErrForbidden。
  6. 否则以来源 WEBHOOK、Raw 为原始请求体调 [回执处理](#回执处理)。
- unmatched 分支：
  1. 查该农场所属租户（FarmTenants）。查询出错记 Warn；恰好 1 个租户时归档原文到 MinIO（RECEIPT_RAW）；多个租户时记 Warn、不归档。
  2. 写审计 RECEIPT_UNMATCHED：作用域为 (0,0)，actor 为 device，结果 FAILED，target `order:{路径 order_id}`，带 raw_object_id；summary 含 path_farm_id、path_order_id、device_type、device_job_id、status、receipt_id、reason、request_id。
  3. 若审计写入失败，则返回错误（让平台重投），否则记 ERROR 日志（alert RECEIPT_UNMATCHED）并返回 UNMATCHED。
- 结果与失败：
  - 响应体为 {status, receipt_id, effect, order_status}，status 取 PROCESSED、REPLAYED（重放）或 UNMATCHED。
  - HTTP 映射：UNMATCHED → 202；正常 → 200；ErrReceiptAuth → 401；ErrBadInput → 400；ErrForbidden → 403；ErrReceiptUnknownJob、ORDER_BUSY、ErrConcurrentUpdate → 503 并带 `Retry-After: 5`；其他 → 500。

## 回执处理

- 入口：`internal/service/receipt_process.go` 的 `OrderOpsService.Process`，状态判定与推进在 `internal/service/receipt_apply.go`。调用方有三个：[设备回执 webhook](#设备回执-webhook)（来源 WEBHOOK）、[回执超时扫描](#回执超时扫描)（来源 POLL）、[order.cancel 处理器](#ordercancel-处理器)（来源 MANUAL）。
- 前置条件：tenant、farm、order、attempt 均非 0；receipt_id 长度 1–96；来源合法；回执自身校验通过。否则 ErrBadInput。
- 执行步骤：
  1. 读 Redis `idem:receipt`（值格式 `v1:{tenant}:{farm}:{outcome}`）。若命中且归属一致，则直接按重放返回；读失败记 Warn，退回由 uk_receipt 唯一键兜底。
  2. 若有原文，则归档到 MinIO（RECEIPT_RAW，对象名 `receipt-{order_id}-{sha(receipt_id) 前 16 位}.json`）。
  3. 取 lock:order 并开事务（applyReceiptTx）：
     1. 读尝试（AttemptTx）。若回执带的 job 与尝试的 job 都非空且不一致，则返回 ErrBadInput。
     2. 读作业单（OrderForDispatch），再做回执分类（classifyReceipt，见下）。
     3. INSERT IGNORE device_receipt（receipt_id、order_id、attempt、device_job_id（缺省取尝试的 job，再缺省为 "-"）、norm_status、effect、done_area_mu、device_ts（缺省为当前时间）、source、raw_object_id）。0 行即重放，不再推进。
     4. 分类为 CONFLICT → 记告警 RECEIPT_CONFLICT；分类为 APPLIED → 执行推进（applyAdvance，见下）；LATE / STALE 只留存回执。
  4. 提交后若有告警，则记 ERROR 日志「receipt: needs attention」。再 SetNX `idem:receipt`，TTL 7 天，失败记 Warn。
- 结果与失败：返回分类（outcome）、是否重放、处理后的作业单状态（重放时为空）。告警在提交后才打，事务回滚不会误报。锁被占返回 ORDER_BUSY，row_ver 冲突返回 ErrConcurrentUpdate，由调用方重试。

### 回执分类

- 入口：`internal/service/receipt_apply.go` 的 `classifyReceipt`。
- 执行步骤（按顺序，命中即返回）：
  1. 若作业单已是终态，则为 LATE；但回执能映射出目标状态且与当前状态不同时为 CONFLICT。
  2. 若尝试已是终态且不在待对账状态，则为 STALE；但回执也是终态且状态或 failure_kind 与尝试不同时为 CONFLICT。
  3. 若回执为 FAILED+UNKNOWN，则尝试仍在途时为 APPLIED，否则为 STALE。
  4. 若回执状态的推进等级（AttemptRank）不高于尝试当前等级，则为 STALE。
  5. 否则为 APPLIED。

### 回执推进

- 入口：`internal/service/receipt_apply.go` 的 `applyAdvance`、`transitionTx`、`writeDoneTx`。
- 执行步骤：
  1. UpdateReceiptTx 把回执状态写入 dispatch_attempt。若回执不是终态，则回执截止时间 receipt_due_at 顺延为当前时间 + 30 分钟（ReceiptWindow）。
  2. 按映射表（model.MapReceipt）取处置。映射表为：SENT、ACCEPTED → NONE；EXECUTING → 迁 EXECUTING；DONE → 迁 DONE；PARTIALLY_DONE → 迁 PARTIALLY_DONE；CANCELED 无面积 → 迁 CANCELED，有面积 → 迁 PARTIALLY_DONE；FAILED+IN_EXECUTION → 迁 FAILED；FAILED+NOT_EXECUTED → RETRY_OR_FAIL；FAILED+UNKNOWN 与 NO_RECEIPT → RECONCILE。
     - NONE：不迁移，结束。
     - RECONCILE：不迁移，记告警 RECEIPT_NEEDS_RECONCILE，进入 [待对账列表与人工对账](#待对账列表与人工对账)。
     - RETRY_OR_FAIL：若 attempt 小于最大尝试次数，则 InsertRetryDispatchOutboxTx 写下一次 order.dispatch（payload {order_id, ticket_id, run_id, attempt+1}）；否则记告警 DISPATCH_RETRY_EXHAUSTED，并迁 FAILED(RETRY_EXHAUSTED)，actor device。
     - TRANSITION：目标为映射表的 To。若为 FAILED+IN_EXECUTION，则加告警 RECEIPT_FAILED_IN_EXECUTION，且有作业面积时改迁 PARTIALLY_DONE。面积缺省取尝试上的面积。原因 RECEIPT，actor device。
  3. transitionTx：目标与当前状态相同则跳过；否则 Orders.Transition，再 writeDoneTx。若是 REAL 单迁到 DONE 或 PARTIALLY_DONE 却没有面积，且没有其他告警，则记告警 DONE_AREA_MISSING。
  4. writeDoneTx（只对 REAL 单的 DONE、PARTIALLY_DONE 生效）：
     1. 有面积则 SetDoneAreaTx 写作业单完成面积。
     2. InsertWorkDoneMemoryTx 写 episodic_memory(WORK_DONE)，摘要为「作业单 X（work_type）状态，完成 N.NN 亩」。
     3. InsertFieldHistoryOutboxTx 写 outbox field.history.append（dedup_key `field.history.append:{order_id}:{ticket_id}:1`，payload {order_id, ticket_id, field_id, work_type, status, done_area_mu, done_at}），由 [field.history.append 处理器](#fieldhistoryappend-处理器) 消费。
- 结果与失败：全部在 [回执处理](#回执处理) 第 3 步的同一事务内，任一步失败整体回滚。DefaultDispatchMaxAttempts 为 2，即设备未动作时最多重发一次。

## 回执超时扫描

- 入口：`internal/service/reconcile.go` 的 `OrderOpsService.RunReceiptDue` 与 `OrderOpsService.ScanReceiptDueOnce`；由 `internal/app/orderops.go` 的 OrderOpsLoops 返回，在 cmd/worker 里起协程运行。
- 前置条件：尝试状态为 SENT、ACCEPTED 或 EXECUTING，且 receipt_due_at 已过（下发时与每次非终态回执都会把它设为当前时间 + 30 分钟）。
- 执行步骤：
  1. 每 ScanInterval（缺省 30s）执行一轮，单轮出错只记 Warn。
  2. 取 `lock:scan:receipt_due`（60s）；已被其他实例持有则本轮跳过。
  3. DueAttempts：`SELECT id, tenant_id, farm_id, order_id FROM dispatch_attempt WHERE status IN ('SENT','ACCEPTED','EXECUTING') AND receipt_due_at < now LIMIT 100`（跨农场，用系统凭证）。
  4. 对每条尝试执行 pollAttempt：
     1. 事务内重读尝试与作业单；若尝试已不在途，则跳过。
     2. 调设备 QueryStatus(idem_key, device_job_id)；结果不带 job 时补上尝试的 job。
     3. 若查询成功且结果合法，则以来源 POLL 调 [回执处理](#回执处理)。若分类为 APPLIED 或查到的是终态，则本条结束；否则视为「没有进展」。
     4. 若查询失败、结果非法或没有进展，则执行 markNoReceipt。
  5. markNoReceipt：取 lock:order，事务内重读尝试；若仍在途，则 `UPDATE dispatch_attempt SET status='NO_RECEIPT', failure_kind='UNKNOWN', row_ver=row_ver+1 … WHERE … AND row_ver=? AND status IN ('SENT','ACCEPTED','EXECUTING')`。确实改了才记 ERROR 日志（alert RECEIPT_TIMEOUT_NO_RECEIPT，带原因）。
  6. 单条出错时，ORDER_BUSY、ErrConcurrentUpdate、ErrIllegalTransition 跳过等下一轮，其余错误汇总返回。
- 结果与失败：扫描不改作业单状态（保持 DISPATCHED / EXECUTING），不转 FAILED，也不重发；尝试进入 [待对账列表与人工对账](#待对账列表与人工对账)。
- 注：OrderOpsLoops 的注释写的是「回执超时扫描等」，worker.go 也写「L4-B 回执超时扫描等」，代码实际只返回 RunReceiptDue 这一个循环。

## 中止作业单

- 入口：`internal/controller/orderops.go` 的 `CancelHandler`，路由 `POST /api/v1/farms/:farm_id/orders/:order_id/cancel`；业务在 `internal/service/workorder_cancel.go` 的 `OrderOpsService.Cancel`。
- 前置条件：已通过农场鉴权，并拥有 order.cancel 权限；order_id 非法返回 400。
- 执行步骤：
  1. 取 lock:order，开事务读作业单；不在本农场返回 ErrNotInScope。
  2. 若状态是 DRAFT、PENDING_APPROVAL 或 APPROVED，则迁 CANCELED(CANCELED_BY_USER)，actor user，再关闭票据（closeTicketsTx）：
     1. LiveTicketsTx 以 FOR UPDATE 读本单 OPEN / PREPARING 的票；
     2. SupersedeLiveTicketTx 把它们置 SUPERSEDED，0 行则整事务回滚；
     3. CloseWaitingRunTx 把等审批的 run 置 COMPLETED(CANCELED_BY_USER)，0 行不报错。
  3. 若状态是 DISPATCHED 或 EXECUTING，则读最后一次尝试（LatestAttemptTx）：
     - 尝试既不在途也不待对账（已确认未执行、等重试）→ 直接迁 CANCELED，后续重试下发见到 CANCELED 即停；
     - 否则若尝试没有 device_job_id → 返回 ErrCancelState，需人工处理；
     - 否则写 outbox order.cancel（dedup_key `order.cancel:{order_id}:{ticket_id}:1`，payload {order_id, ticket_id, attempt_id, device_job_id}），标记 pending，作业单状态暂不变。
  4. 其他状态返回 ErrCancelState。
  5. 同事务写审计 ORDER_CANCEL，payload 为 {order_id, from, attempt_id, pending}。
- 结果与失败：
  - 已中止返回 200；已提交设备中止（pending）返回 202，最终状态由 [order.cancel 处理器](#ordercancel-处理器) 回写。
  - ErrCancelState → 409 CANCEL_NOT_ALLOWED；ORDER_BUSY、ErrConcurrentUpdate、ErrIllegalTransition → 409；不在本农场 → 403 并写拒绝审计。

## order.cancel 处理器

- 入口：`internal/service/workorder_cancel.go` 的 `OrderOpsService.HandleCancel`，由 [outbox 轮询器](#outbox-轮询器) 按 topic order.cancel 调用。
- 前置条件：payload 能解析，且 tenant、farm、order、attempt、device_job_id 都非空，否则返回 ErrBadInput（按普通错误退避，最终 DEAD）。
- 执行步骤：
  1. 事务内读尝试与作业单。
  2. 若作业单已是终态，或尝试既不在途也不待对账，则返回 nil（已有回执收尾，不再调设备）。
  3. 调设备 Cancel(device_job_id)，结果不带 job 时补上，再做回执校验。若失败，则记 ERROR 日志（alert ORDER_CANCEL_DEVICE_FAILED，带 outbox 尝试次数）并返回错误，由 outbox 退避重试。
  4. 把设备返回当作一条回执，以来源 MANUAL 调 [回执处理](#回执处理)，按映射表把作业单推进到 CANCELED 或 PARTIALLY_DONE 等。
- 结果与失败：回执处理出错原样返回，outbox 重试；同一回执重复处理按重放返回。

## 待对账列表与人工对账

- 入口：`internal/controller/orderops.go` 的 `PendingReconcileHandler`（`GET /api/v1/farms/:farm_id/reconcile/pending`）与 `ReconcileHandler`（`POST /api/v1/farms/:farm_id/orders/:order_id/reconcile`）；业务在 `internal/service/reconcile.go` 的 `OrderOpsService.PendingReconcile` 与 `OrderOpsService.Reconcile`。
- 前置条件：已通过农场鉴权。列表要求 advice.read 权限，对账要求 order.reconcile 权限。
- 待对账列表：
  1. `SELECT … FROM dispatch_attempt WHERE tenant_id=? AND farm_id=? AND (status='NO_RECEIPT' OR (status='FAILED' AND failure_kind='UNKNOWN')) ORDER BY sent_at, id LIMIT 100`。
  2. 返回 {"attempts": [...]}，没有记录时为空数组。
- 人工对账执行步骤：
  1. 请求体 {conclusion, failure_kind?, done_area_mu?, comment?}，解析失败 400；tenant、farm、order 任一为 0 返回 ErrBadInput。
  2. 校验结论（target）：
     - 结论为 FAILED+UNKNOWN 不允许（必须是 NOT_EXECUTED 或 IN_EXECUTION）；
     - 结论须通过 CheckAttemptState；PARTIALLY_DONE 必须带大于 0 的面积；
     - comment 不超过 200 字符；
     - 结论须能映射出作业单终态（在途状态不行），否则 ErrBadInput。
  3. 取 lock:order，开事务读作业单；不在本农场返回 ErrNotInScope。
  4. 读最后一次尝试。若作业单已是终态，或尝试不在待对账状态（NO_RECEIPT 或 FAILED+UNKNOWN），则返回 ErrReconcileState。
  5. UpdateReceiptTx 把结论写入尝试（row_ver 守卫）。面积缺省取尝试上的面积。
  6. 调 transitionTx 迁到目标状态，actor user，原因 RECONCILED；REAL 单进入 DONE / PARTIALLY_DONE 时同事务执行 writeDoneTx（见 [回执推进](#回执推进)）。
  7. 同事务写审计 RECONCILE（target `order:{id}`，结果 OK），payload 含 order_id、attempt_id、from、conclusion、failure_kind、done_area_mu、order_status、comment。
- 结果与失败：
  - 返回 {order_id, attempt_id, order_status}，200。
  - ErrReconcileState → 409 RECONCILE_NOT_PENDING；ORDER_BUSY、ErrConcurrentUpdate、ErrIllegalTransition → 409；不在本农场 → 403 并写拒绝审计。

## field.history.append 处理器

- 入口：`internal/service/fieldhistory.go` 的 `OrderOpsService.HandleFieldHistory`，由 [outbox 轮询器](#outbox-轮询器) 按 topic field.history.append 调用。消息由 [回执推进](#回执推进) 的 writeDoneTx 写入。
- 前置条件：payload 能解析，且 order_id、tenant、farm 非 0，否则返回错误（消息非法也不静默丢弃，最终 DEAD 转人工）。
- 写端选择：
  - `internal/app/boot/tools.go` 的 fieldHistoryWriter 按 tools.field.mode 选择：mode 为 real 时用 UnwiredFieldHistory，其余用 MemFieldHistory；
  - `internal/app/orderops.go` 的 buildOrderOps 在未传入写端时也用 MemFieldHistory。
- 执行步骤：
  1. 组装记录 {tenant、farm、field_id、order_id、ticket_id、work_type、status、done_area_mu、done_at}，调 History.AppendWorkDone。
  2. MemFieldHistory 把记录存在进程内存里，按 (tenant, farm, order) 幂等，重复投递不产生重复记录。
  3. UnwiredFieldHistory 一律返回 FIELD_HISTORY_UNWIRED。
  4. 写失败时记 ERROR 日志（alert FIELD_HISTORY_WRITE_FAILED，带 outbox 尝试次数）并返回错误，outbox 退避重试，最终 DEAD。
- 结果与失败：该写端只给 outbox 处理器用，不注册为 MCP 工具，模型不可见。
- 注：注释把 field.history 回写描述为写到 mcp-field，代码实际在 real 模式下没有写接口（UnwiredFieldHistory 必然失败、消息最终 DEAD），mock 模式只写进程内存，进程重启即丢失。

## notify.send 处理器

- 入口：`internal/service/notify.go` 的 `NotifyHandler.Handle`，由 `internal/app/approval_l5.go` 装配，经 [outbox 轮询器](#outbox-轮询器) 按 topic notify.send 调用。消息来源有待审批（PENDING_APPROVAL）、即将过期（EXPIRING_SOON）、[复检退回重审](#复检退回重审)（RECHECK_RETURNED）、设备离线（DEVICE_OFFLINE）。
- 前置条件：构造时 Recipients、Channel、Texts、Audit、Clock、Logger 全部必填，缺一返回 ErrDispatchNotConfigured。
- 执行步骤：
  1. 解析 payload，失败返回 ErrBadOutboxPayload。ticket_id 为 0 时取 new_ticket_id。
  2. Texts.Render 按 kind 取文案；未知 kind 返回 ErrBadOutboxPayload。order_id 必填，除 DEVICE_OFFLINE 外 ticket_id 也必填。
  3. 解析接收人（recipients）：
     1. TicketParties 读票的 initiator_id 与 required_role；ticket_id 为 0 时取该单 ticket_seq 最大的 ORDER 票。查不到票不报错，视为无当事人。
     2. 角色取 required_role；DEVICE_OFFLINE 改为 farm_manager。FarmUsersByRoles 查本农场这些角色的用户。
     3. 若 kind 是 PENDING_APPROVAL 或 EXPIRING_SOON，则排除发起人；否则额外加入发起人。结果去重、升序。
  4. 若没有接收人，则写审计 NOTIFY_SEND（结果 FAILED，payload 含 kind、order_id、ticket_id、text_key、reason NO_RECIPIENT），记 Warn，返回 nil（消息置 DONE）。审计写失败则返回错误。
  5. 否则调 Channel.Send。缺省通道 AuditChannel 写审计 NOTIFY_SEND（结果 OK，target `order:{id}`，actor system，payload 含 kind、order_id、ticket_id、user_ids、text_key、dedup_key，不含正文），再记 Info 日志。
- 结果与失败：通道失败返回错误，outbox 退避重试；接收人查询失败同样返回错误。
- 注：NotifyChannel 的注释写的是外部通道（短信 / 企业微信 / App 推送）实现接口即可接入，代码实际只装配了 AuditChannel，通知只落审计和日志，不会真正送达用户。

## 驳回原因导出

- 入口：`internal/controller/rejection.go` 的 `RejectionExportHandler`，路由 `GET /api/v1/farms/:farm_id/rejections?from=&to=`；业务在 `internal/service/rejection_export.go` 的 `RejectionExportService`。
- 前置条件：已通过农场鉴权，并拥有 rejection.export 权限。最大跨度取配置 approval.rejection_export_max_span，缺省 31 天，构造时须大于 0。
- 执行步骤：
  1. from、to 必填，均为 RFC3339；要求 to 不早于 from，且 to − from 不超过最大跨度。任一不符返回 ErrBadInput（400）。
  2. ListRejections：`SELECT r.*, t.order_id FROM rejection_reason r JOIN approval_ticket t ON t.tenant_id=r.tenant_id AND t.farm_id=r.farm_id AND t.id=r.ticket_id WHERE r.tenant_id=? AND r.farm_id=? AND r.created_at BETWEEN ? AND ? ORDER BY r.created_at`。
  3. 先写 UTF-8 BOM，再写表头与数据行。列为 id、ticket_id、order_id、advice_id、run_id、reason_code、reason_text、operator_id、operator_role、created_at。
  4. 每个单元格过 csvSafe：以 `=`、`+`、`-`、`@`、全角 `＝＋－＠`、制表符或回车开头时，前面加一个单引号，防止表格软件把它当公式执行。
- 结果与失败：返回 text/csv，`Content-Disposition: attachment; filename="rejections-{farm_id}.csv"`。驳回原因本身由 [驳回](#驳回) 写入。

## 与灰度检查的关系

- 入口：`cmd/auditctl/gray.go` 的 `cmdGrayPreflight`（子命令 gray-preflight）；检查实现在 `internal/service/gray_preflight.go` 的 `GrayPreflight.Run` 与 `internal/service/gray_checks.go`。
- 前置条件：需要目标农场 (tenant, farm)，任一为 0 返回 ErrBadInput。任一项 FAIL 时不得打开 enable_robot_dispatch；取数失败按该项 FAIL 处理，不中断其余检查。
- 与下发相关的检查项：
  1. kill_switch_drill（checkDrill）：读 7 天内最近一次 KILL_SWITCH_DRILL 审计，要求已封链且 row_hash 重算一致、结果 OK 且断言全部成立、耗时不超过 60s、expect_held 大于 0 且 held_total 不少于 expect_held、T0 在 7 天窗口内；再回查它引用的 FLAG_CHANGE，要求已封链、row_hash 一致、是 GLOBAL 的开→关（force_off=true），且审计时间等于 T0。
  2. agronomist_bound（checkAgronomist）：FarmHasRole 查目标农场是否绑定 agronomist，与打开 enable_robot_dispatch 前的预检同一查询（见 [下发开关](#下发开关)）。
- 其余检查项（d5_closed、legal_signoff、alert_rules、redteam_pass5、enable_advice_on）不涉及下发链路。enable_advice_on 用开关三层原始行直读合并（mergeFlag），不走缓存。
- 结果与失败：逐项打印 PASS / FAIL 与原因，任一 FAIL 时命令返回错误。检查只读，不改作业单，也不触发下发；下发器第 ② 步读开关用的是 FlagService.BoolLive（直读 MySQL，不走 30s 缓存）。
