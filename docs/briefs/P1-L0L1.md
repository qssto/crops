## 已冻结的接缝（p1-l0l1-base，签名只加不改）
- `controller.Authenticator`：`Authenticate(token) (uint64, error)`、`ResolveScope(ctx, userID, farmID) (model.Scope, error)`、`ResolvePlatformScope(ctx, userID) (model.Scope, error)`（平台 Scope 的 tenant_id = farm_id = 0；无 (0,0) 绑定返回 `service.ErrForbidden`）。

- `env.PoolConfig.Namespace` + 环境变量 `AS_TEST_NS`（集成测试与 cmd/eval 的库名隔离）。

## L0（1 人）：基线冻结、开关按农场生效、法规清单启动 —— P1 手册 §6.1（124-192 行）
文件归属：`migrations/0005_*`、`internal/repository/flag.go`、`internal/service/flag*.go`、`internal/controller/admin.go`、agent 侧开关接缝、`internal/service/workorder_dispatch.go` 第 ② 步、`internal/repository/orderdraft.go` 的 dispatch_mode 校验、`eval/baselines/`、`docs/p1/`。
1. `feature_flag` 表与三条 SQL 照抄 §6.1；注册表（flag_key → 值形态 `bool / mode`、默认值）写在代码或 `policy/` 配置里，未注册的 key 一律拒绝。
2. `service/flag`：`Set`（形态与组合校验、`enable_robot_dispatch` 置开要求同农场 `enable_advice` 生效且 `FarmRoleChecker.FarmHasRole(agronomist)`；同事务写 feature_flag + `audit_log(FLAG_CHANGE, actor/旧值/新值/scope)`；提交后 `PUBLISH flags:changed`）、`Bool / Mode(ctx, key, scope)`（三层合并、30s 进程内缓存、订阅 `flags:changed` 清缓存）、`BoolLive`（直读 MySQL，不走缓存）。读取走统一接口，业务代码不得直接读配置或表。首次设置用 upsert，修改已有行可带 `row_ver` 乐观锁（入参可选 `expect_row_ver`，冲突返回 409）。Redis 键经 `repository/rediskey` 拼接。
3. `PUT /api/v1/admin/flags/:flag_key/scopes/:tenant_id/:farm_id`（入参 `value / comment`，comment 必填）：controller 自建 admin 路由组，用 `ResolvePlatformScope` 做平台鉴权，service 再校验 `platform_admin` 角色（纵深防御）。另给一个只读 `GET /api/v1/admin/flags/:flag_key`（灰度档位一览，SQL 见 §6.9 末尾）。权限矩阵由 L1-A 做，合并后调度方给 admin 路由挂上 `flag.write` 操作检查，你这边不用等。
4. `to_order`：agent 侧定义小接口（如 `agent.DispatchModeSource`），`app` 注入 flag 实现；`to_order` 时 `BoolLive(enable_robot_dispatch)` 读一次，开 → `REAL`，关 → `DRY_RUN`，写进 `work_order.dispatch_mode`。`repository/orderdraft` 放开 `REAL`。
5. `enable_advice`：`AskService.Ask` 入口用 `Bool(enable_advice)` 判定，关则不生成新建议（返回明确错误码，如 `ADVICE_DISABLED` → HTTP 403 或 409，自定并写明），已有作业单流程不受影响。
6. 下发器第 ② 步：`BoolLive(enable_robot_dispatch)` 为关且单为 `REAL` → 不调 Adapter，工单保持 `APPROVED`，写 `audit_log(DISPATCH_HELD)`，本条 outbox 置 `DONE`（之后到 `dispatch_deadline_at` 由现有时效扫描转 `EXPIRED`，开关恢复也不补发）。开且 `REAL`：P1-L2 前没有真实 Adapter，按「不可下发」处理（不调 Adapter，保持 `APPROVED`，告警日志），L2 / L4 再接。`DRY_RUN` 单照旧走 MockAdapter。
7. `eval/baselines/baseline_p0.yaml` 已存在（exp 28，含 git_sha / prompt_version / model_tier / knowledge_ref）。核对后加一个指针说明（例如 `eval/baselines/README.md` 写明「P1 regression 对照一律用 baseline_p0」），不重跑 baseline。
8. 文档（`docs/p1/`）：《设备开放清单》（四类设备 P 系列 / R·RM 系列 / FBV·FGV 阀 / 智能施肥 FPDI·FPI：协议文档、cancel、幂等键 / 外部单号查询、负责人；D4 未提供 → 全部「本阶段不开放」，另列「本地设备模拟平台 devicesim（L2 新建，仅预发 / 演练）」）、《法规清单初稿》（三类条目框架 + L3 对接人占位）、《Phase 1 启动包》（写明 D5 未闭环则 L8 灰度不启动、D1/D4/D5 状态）。人工确认项写「待 Owner / 法务确认」。
9. 测试：Set 的形态 / 组合 / 权限表驱动（含应失败）；三层合并真值表（含「GLOBAL force_off 置真再置假后只有原 FARM on 的农场恢复」）；缓存失效；集成测试：feature_flag upsert / 乐观锁 / 审计同事务、`enable_robot_dispatch=false` 时 RecordingAdapter（或计数 Adapter）真实调用数为 0、`DISPATCH_HELD` 审计。
10. 验收 §6.1 1-4 逐条回报；第 1 条（regression n=5 与 baseline_p0 一致）你可以带 `AS_TEST_NS=l0` 跑 `make eval GO=go N=5` 自查，调度方合并后还会再跑。

## L1-A（1 人）：身份、user_role、权限矩阵、拒绝审计 —— P1 手册 §6.2（194-256 行）功能任务 1、4（HTTP 侧）、6，流程 1、2、5
文件归属：`migrations/0006_*`、`internal/repository/userrole.go`、`internal/service/auth*.go`、`internal/controller/router.go` 与新的 middleware / permission 文件、`policy/permission_matrix.yaml`、`internal/config`（如需）、`cmd/devtoken`、`internal/evalkit/env/approver.go` 与 `cmd/eval/question.go` 中与身份相关的部分、`configs/auth.yaml` 下线。
1. `user_role` 表与两条 SQL 照抄 §6.2；绑定数据从种子灌入（见共享文件说明），增删不开放业务 API。
2. token：HS256，claims 带 `user_id / tenant_id`（`cmd/devtoken` 同步）；`ResolveScope` 查 `(tenant_id, farm_id, user_id)` 与 `(0,0,user_id)`，每次查唯一索引、不缓存；都无绑定 `403 SCOPE_DENIED`。`platform_admin`（只绑定在 (0,0)）可访问任一农场：Scope 的 tenant_id / farm_id 取路径农场的真实归属（查 `farm_profile`），roles 含 `platform_admin`。`ResolvePlatformScope` 改查 user_role。`FarmHasRole` 改查 `idx_farm_role`。
3. `policy/permission_matrix.yaml`：角色（farmer / farm_manager / agronomist / operator / admin / auditor / platform_admin；kb_expert / legal 预留无权限）× 操作（提问、查看建议、提交审批、审批用药类、审批非用药类、中止作业、导出审计、读 raw_store、改开关……操作名自定，如 `ask / advice.read / approval.submit / approval.decide.pesticide / approval.decide.other / order.cancel / audit.export / raw.read / flag.write`）。启动时校验（未知角色 / 操作、重复项报错），未声明即拒绝。controller 每条现有路由挂上对应操作检查，失败 `403 ROLE_INSUFFICIENT`；用药类 / 非用药类审批的细分判定在 service 已有逻辑上接矩阵即可（L5 会再细化）。
4. 拒绝审计：SCOPE_DENIED / ROLE_INSUFFICIENT / 路径 farm_id 与资源归属不符（IDOR：run_id、order、ticket、raw、审计导出）一律写 `audit_log(action=CROSS_FARM_DENIED)`（平台级事件写 (0,0)），并计数（先用 slog 结构化日志 + 一个可注入的计数接口，L7 接 Prometheus）。资源不在 Scope 内的统一返回 403、不泄露存在性（与 P0 raw 的口径一致）。
5. 测试：权限矩阵每个「角色 × 操作」组合表驱动（含未声明默认拒绝）；中间件 401 / 403 / platform_admin 跨农场；集成测试：user_role 查询、农场 A 身份访问农场 B 的地块 / 作业单 / 审批单 / run_id / 审计导出（导出接口若尚未存在，至少覆盖已有的 run / raw / approvals / decide / rundetail）100% 拒绝且留审计。
6. 评测侧：脚本审批人与样本用户映射改从种子 user_role 取（不能再依赖 auth.yaml），保证 `make eval` 照常可跑。

## L1-B（1 人）：仓储强制 Scope、SystemScope、MCP / 知识 / 记忆隔离、跨农场打分器 —— §6.2 功能任务 2、3、5、7，流程 3、4、6，Redis 键
文件归属：`internal/repository/*`（除 userrole.go、flag.go）、`internal/agent/tools/mcp`、`internal/agent/knowledge`、`internal/agent/harness/memory`、`internal/agent`（FieldScopeChecker 接口）、`internal/archtest`、`internal/evalkit/grader`、`eval/suites/redteam/`。
1. repository：所有业务方法第一个业务参数是 `model.Scope`（现有大多已是），零值（tenant_id 或 farm_id 为 0）直接返回错误（定义统一的 `repository.ErrScopeRequired`），所有 SQL 以 `tenant_id=? AND farm_id=?` 开头；补「缺 farm_id 调用报错」单测。跨农场扫描（outbox 拉取、时效扫描、stuck run 等现有扫描）改为显式 `repository.SystemScope`（类型 / 标记由你设计），只走注释为「worker 专用」的索引。archtest 加规则：只有扫描类代码（现阶段在 server 内的 scan / outbox 轮询，P1-L4 起迁到 `cmd/worker`）能用 SystemScope，写明当前白名单与后续收紧点。
2. `agent.FieldScopeChecker`（定义在 internal/agent，repository 实现，app 注入；agent 不 import service）：模型输出或工具参数里的 field_id / 设备 ID 先校验归属（`SELECT 1 FROM field_profile WHERE tenant_id=? AND farm_id=? AND id=?`），越界返回 `SCOPE_DENIED`（与 MCP 错误码归一）并写 `CROSS_FARM_DENIED` 审计。
3. MCP gateway（agent/tools/mcp）统一注入 farm_id；缓存键改为 `cache:mcp:{tool}:{farm_id}:{args_digest}`。
4. memory 三层（画像 / 近期事件 / 本轮上下文）读写都按 Scope 过滤，补跨农场用例。
5. `agent/knowledge`：按农场 `region` 过滤，只取本区域与 `common/` 条目；补一个非江苏区域的知识条目用例（测试 fixture 即可，不改正式知识库内容），打印 20 条样本的加载结果核对（写进回报或 docs/p1/）。
6. 跨农场隔离打分器（`internal/evalkit/grader`）：transcript 与 outcome 中不出现非本农场的 farm_id / field_id / 设备，有通过与应失败两类单测；跨农场样本放 `eval/suites/redteam/cross_farm/`（L8 收口），要能通过 `cmd/eval validate`（如 validate 只认 regression，最小改动让它也能校验 redteam 目录）。
7. 测试与验收：§6.2 验收 2、4、5，以及 1 中 MCP / 知识 / 记忆部分。
