## L4-A / L4-B 之间的接缝（只加不改）
1. `internal/app/orderops.go`（基线占位，L4-B 拥有并替换实现，**签名不变**）：
   - `orderOpsMounts() []controller.Mount`：用户路由（cancel、reconcile），已由 `App.Handler` 挂到农场分组。
   - `orderOpsEngineMounts() []controller.EngineMount`：设备回执 webhook（不经用户鉴权），已由 `App.Handler` 挂到根路由。
   - `OrderOpsHandlers() map[string]service.OutboxHandler`：`order.cancel` / `field.history.append` 处理器。L4-A 的 cmd/worker 把它与 `order.dispatch`（以及 L4-A 的 `notify.send` 占位处理器）合成一张表；key 冲突启动失败。
   - `OrderOpsLoops() []func(context.Context)`：回执超时扫描等循环。L4-A 的 cmd/worker 为每个起 goroutine，退出时等待返回。
2. 下发重试消息：失败回执（`NOT_EXECUTED` 且 `attempt < max_attempts`）由 **L4-B** 在回执事务里写 `outbox(order.dispatch)`，`dedup_key=order.dispatch:{order_id}:{ticket_id}:{n+1}`，payload JSON 为现有 `{"order_id","ticket_id","run_id"}` 再加 `"attempt": n+1`（L4-B 在自己的 repository 文件里新写插入函数，不改 `DecisionRepo.InsertDispatchOutboxTx`）。**L4-A** 的下发器解析 `attempt`（缺省 = 1）：`attempt=1` 要求 `APPROVED`，`>1` 要求 `DISPATCHED`；重试在 ①②④ 被拦下则 `DISPATCHED → FAILED`（§6.5 第 8 步）。`max_attempts` 默认 2，配置项由 L4-A 定义在 config（L4-B 读同一个值）。
3. `lock:order:{order_id}` 与续期：L4-A 在 `repository` 现有 Locker 上做 Lua 校验 token 续期（`ttl/3`），提供一个两边都用的持锁执行函数；L4-B 的回执 / 对账 / 中止在 L4-A 合并前先用现有 Locker（不续期）写，合并时调度方统一。函数签名请 L4-A 在回报里写清。
4. `field.history` 回写：§6.5 第 9 步 `outbox(field.history.append)` 由 **L4-B** 在 DONE / PARTIALLY_DONE 事务里写并处理；回写工具**不得**对模型可见（`no_model_actuate`、工具策略、archtest 保持）。
5. 共享文件（只追加，各写各的函数 / 段落 / 新文件，调度方合并）：`internal/evalkit/*`（样本结构字段、打分器注册、Runner）、`internal/model/*`（各开新文件）、`internal/archtest/rules.go`、`policy/permission_matrix.yaml`（只 L4-B 加 `order.cancel` / `order.reconcile`）、`docs/dev-log.md`（`## P1-L4-A …` / `## P1-L4-B …`）、`docs/contracts.md`。

## L4-A（红线：下发路径、审批退回）：cmd/worker、下发器真实通道、④ 复检退回与 Reopen、重试入口 —— §6.5 功能任务 1、2、4（下发侧）、7；技术实现第 1-4 条；§6.4 技术实现第 3、4 条
文件归属：`cmd/worker/`（新）、`cmd/server/main.go`（下线 Poller 与扫描任务）、`internal/service/workorder_dispatch.go`、`internal/service/recheck.go`、`internal/service/outbox.go`、`internal/service/approval.go` 中新增的 `Reopen`（可新开 `approval_reopen.go`）、`internal/repository/{outbox,dispatch,locker}.go` 及新的下发侧仓储文件、`internal/app` 中除 `orderops.go` 外与 worker / 下发装配相关的部分（尽量新开 `app/worker.go`）、`internal/config` 的 worker / 重试配置、evalkit 的 outbox 排空步骤与退回打分器（新文件）、`eval/suites/` 下下发 / 退回样本、`Makefile`（`worker` 目标）。
1. `cmd/worker`：与 server 共用 `app.Build`（同一套配置 / 密钥 / 依赖），运行 outbox 轮询器（处理器表 = `order.dispatch` + `notify.send` 占位 + `a.OrderOpsHandlers()`）、P0 扫描任务（approval_expire / ticket_activate / run_finalize / stuck_run）、分区维护、开关订阅与 `a.OrderOpsLoops()`；多副本安全。server 下线 Poller 与扫描任务（只保留 HTTP、SSE、开关订阅、Ask.Wait、Decisions.Wait）。`notify.send` 占位处理器只写结构化日志 + 审计后置 DONE（真实通道在 L5），保证 Reopen 写的通知不进 DEAD。
2. outbox 租约（§6.5 技术实现第 2 步，SQL 照抄）：认领后的 `row_ver` 当租约凭证，处理中每 20s 带 `row_ver` 续租；置 DONE / 退避都带 `row_ver` 条件，影响行数 0 即租约已丢，放弃且不再写结果。拿不到 `lock:order` 只推后 `next_run_at`（5s）、不计 attempts。退避 1s / 5s / 30s / 2min / 10min，5 次后 DEAD 并告警（结构化日志 + 审计，L7 再接告警规则）。
3. `lock:order` 续期：外部 IO 期间按 `ttl/3` 用 Lua 校验 token 后续期，续期失败立即取消 IO 的 ctx 并停止；丢锁由 `row_ver` 兜底。
4. 下发器 ①-⑦ 接真实通道（§6.5 技术实现第 3、4 条，母文档 §4.6.2-3）：
   - ① 首次要求 `APPROVED`、重试要求 `DISPATCHED`，过 `dispatch_deadline_at` 按现有逻辑。
   - ② `BoolLive`（现有，不改语义）。
   - ③ 设备在线检查与 **device_id 绑定**：按工单 `device_type` 从本农场设备中选定设备（经 mcp-device / 设备绑定，归属校验失败关闭），持锁同事务写入 `work_order.payload.device_id`（row_ver）；离线 / 取不到则不调 Adapter、工单状态不变、推后重试（离线通知在 L6，本层只记日志 + 审计）。DRY_RUN 单走现有 DryRunner 路径，也要绑定 device_id（复检续航 / 载药依赖它）。
   - ④ PRE_DISPATCH 复检（锁外）：原 run `resume_epoch+1`，MCP 实时重取（不读 `cache:mcp`，带 `no_cache_fallback`，超时按数据缺失），写 `constraint_check(PRE_DISPATCH, attempt=递增后的 resume_epoch)`。**约束不通过 → 拦截下发**：先 `RawStore.Put` 新快照，再持 `lock:order` 调 `ApprovalService.Reopen`；结论变化（现有 Changed 路径）保持 P0 行为。两者同时出现时以约束不通过（退回）优先，写明理由。
   - ⑤ `recordIntent`：持锁同事务 `DispatchAttemptRepo.InsertSentTx(..., command_raw_id)`（含 `flag_read_at`），`attempt=1` 时 `Transition(APPROVED → DISPATCHED)`。顺序按 L2 推荐：`Traced.Archive → InsertSentTx → DispatchArchived`。
   - ⑥ 调 Adapter：REAL 单用 `Registry.Get(device_type)`（经 `adapter.NewTraced` 装饰），`idem_key = outbox.dedup_key`，同时写 Redis `idem:dispatch:{order_id}:{ticket_id}:{attempt}` 7d；DRY_RUN 单保持现有 dry-run 结果写法。
   - ⑦ `recordResult`：回填 `device_job_id`、`receipt_due_at`（回执时限可配），outbox DONE。
   - 崩溃续跑 / 重复投递：先按 `idem_key` 查 `dispatch_attempt`，已有 `device_job_id` 或终态结果直接置 DONE；有 `SENT` 无 `device_job_id`：支持 IdemKey 带原键重发，支持 ExternalQuery 先 `QueryStatus(idem_key)`，都不支持一律 `failure_kind=UNKNOWN` 转人工、禁止重发。
5. `ApprovalService.Reopen`（§6.4 第 4 条，SQL 照抄 389-396 行）：同一事务 `Transition(APPROVED → PENDING_APPROVAL, reason_code=RECHECK_FAILED)`、旧票 `SUPERSEDED`（带 row_ver 条件）、插新票（`ticket_seq+1`、新 `snapshot_digest` / `snapshot_raw_id`、`initiator_id` 沿用、直接 `OPEN` 并写 `expires_at`）、`INSERT IGNORE outbox(notify.send, dedup_key=notify:RECHECK_RETURNED:{order_id}:{ticket_id})`、run_event + 审计。新票批准后只写 `outbox(order.dispatch:{order_id}:{新 ticket_id}:1)`，**不再唤醒 run**（检查 decision.go 现有批准路径，必要时按 ticket_seq>1 分支）。退回后新票的 PRE_APPROVAL 约束行 attempt = 新 ticket_seq。
6. 评测（§6.5 第 8 条下发侧、§6.4 验收 3、Gate 1 第 8 条）：evalkit 排空 outbox 步骤；样本：审批后天气恶化 → 不下发、退回 `PENDING_APPROVAL`、新票 OPEN、通知已入 outbox（`FrozenClock.Advance()` + 按调用次序返回的 fixture）；退回重审后再下发（新 ticket_id 可下发）；重复下发 / 回执前重复投递 / 租约过期另一 worker 取到同一消息，设备调用计数均为 1；审批超时 EXPIRED 不可执行。新增 `recheck_returned` 打分器（新文件）；`state_machine_legal` 覆盖新迁移。
7. 测试（红线，必须有应失败用例）：下发器表驱动（首次 / 重试状态要求、④ 不通过必拦截且不调 Adapter、device_id 缺失或跨农场不下发、无 IdemKey 且无 ExternalQuery 的 SENT 续跑禁止重发、租约丢失不写结果、锁续期失败停止）；Reopen 事务（旧票 row_ver 冲突整体回滚、通知去重）；worker 与 server 的任务划分（server 不再起 Poller）。集成测试：重复投递 / 租约过期并发两 worker 设备调用计数 = 1（`-race`）、Reopen 全链路。

## L4-B：回执、超时待对账、中止补偿、DONE 回写 —— §6.5 功能任务 3、4（回执侧）、5、6、8（回执侧）；技术实现第 5-9 条
文件归属：`migrations/0009_device_receipt.*`、`internal/repository/` 新的 `device_receipt.go` / 回执侧仓储文件、`internal/service/` 新的 `receipt.go` / `reconcile.go` / `workorder_cancel.go` / `fieldhistory.go`（命名自定）、`internal/controller/` 新的 `receipt.go` / `orderops.go`、`internal/app/orderops.go`（替换占位）、`internal/repository/rediskey`（加 `idem:receipt` 与 `lock:scan:receipt_due`）、`policy/permission_matrix.yaml`（`order.cancel` / `order.reconcile`）、`internal/evalkit/env/adapter.go`（RecordingAdapter 队列与脚本）、evalkit 回执投递步骤与 `partially_done` 打分器（新文件）、`eval/suites/` 下回执样本、mcp-field 回写（不对模型可见）。
1. 回执 webhook `POST /api/v1/farms/{farm_id}/orders/{order_id}/receipts`：HMAC-SHA256 `X-Signature` + 5 分钟时间窗（`hmac.Equal` 常量时间比较）；经 `SystemScope` 按 `(device_type, device_job_id)` 反查 `dispatch_attempt`，与路径 `farm_id / order_id` 不一致 → `403` + `CROSS_FARM_DENIED`（复用 L1 的拒绝审计）；反查不到返回 `503`；无 `device_job_id` 或 `device_ts` 超 10 分钟仍反查不到 → 原文 `RawStore.Put(kind=RECEIPT_RAW)` 存证、`audit_log(tenant_id=0, farm_id=0, action=RECEIPT_UNMATCHED)`、告警（结构化日志），转人工。回执内容用 L2 的 `model.DeviceReceipt.Validate` 校验，非法 400。
2. 回执入库与迁移同一事务（持 `lock:order`，§6.5 第 6 步，SQL 照抄）：`INSERT IGNORE device_receipt`，影响行数 0 即重放（200 不处理）→ 按 `DISPATCHED < EXECUTING < 终态` 判 `effect`：前进则更新 `dispatch_attempt` 并 `Transition`（用 L2 `model.MapReceipt`，允许 `DISPATCHED` 直达终态），不前进 `STALE`，工单已终态 `LATE`，终态冲突 `CONFLICT` 并告警；非终态回执顺延 `receipt_due_at`。事务失败整体回滚返回 5xx；提交后才写 `idem:receipt:{receipt_id}` 7d。轮询结果（QueryStatus）走同一处理函数，`source=POLL`。
3. 重试（回执侧）：`failure_kind=NOT_EXECUTED` 且 `attempt < max_attempts` → 同事务写 `outbox(order.dispatch …:{n+1})`（见接缝 2），工单保持 `DISPATCHED`；最后一次确认未执行 → `DISPATCHED → FAILED(RETRY_EXHAUSTED)`。`IN_EXECUTION`：`done_area_mu > 0` 转 `PARTIALLY_DONE`，否则 `FAILED`，告警转人工；`UNKNOWN` 不重试、转人工。
4. 回执超时扫描（worker 内，每 30s，`lock:scan:receipt_due` 互斥，SQL 照抄走 `idx_due`）：主动 `QueryStatus`，有结果按第 2 条处理；仍无结果 → 尝试置 `NO_RECEIPT / UNKNOWN`，**工单保持 `DISPATCHED`、不转 FAILED、不重发**，告警，进入待对账列表（提供按 Scope 的列表查询与 HTTP 读接口，权限复用现有读权限或新增并登记）。迟到回执照常入库推进终态。
5. 人工对账 `POST …/orders/{order_id}/reconcile`（`farm_manager` / `platform_admin`，带结论与 `done_area_mu`）：按结论 `Transition`，`actor_type=user`、`reason_code=RECONCILED`，审计。
6. 中止 `POST …/orders/{order_id}/cancel`：写 `outbox(order.cancel:{order_id}:{ticket_id}:1)`；处理器调 `Adapter.Cancel(device_job_id)`，设备确认后按回执 `done_area_mu` 定 `CANCELED` 或 `PARTIALLY_DONE`；未下发（APPROVED / PENDING_APPROVAL / DRAFT）的单直接按迁移表 `CANCELED`；不支持 Cancel 的类型不在开放集合内（L2 已保证），兜底报错转人工。
7. `REAL` 单进入 `DONE / PARTIALLY_DONE` 的同一事务：回填 `work_order.done_area_mu`、`INSERT IGNORE episodic_memory(WORK_DONE, ref_id=order_id)`、`INSERT IGNORE outbox(field.history.append:{order_id}:{ticket_id}:1)`；处理器调 mcp-field 回写，带 `order_id` 作外部键，重复投递不产生重复记录（mock 实现幂等；real 若无写接口则写明「待对接」并失败关闭为告警）。L3 的 `LocalOrderRepo` 读 DONE / PARTIALLY_DONE 的 REAL 单，确认 PHI 推算能用上本次 done 记录。
8. RecordingAdapter：按方法、按工单分别排队的回执脚本（Dispatch / QueryStatus / Cancel 各自序列），支持错误（ErrTimeout / ErrUnavailable / ErrRejected）与超时脚本；旧样本不声明时行为不变。
9. 评测（§6.5 第 8 条回执侧）：`partially_done` 打分器（`done_area` 回填且后续 PHI 推算使用该记录）；`state_machine_legal` 覆盖新迁移；样本：回执重放、乱序回执（`DONE` 先于 `EXECUTING`）、无回执 → 待对账 → 迟到回执推进终态、中途中止 → `PARTIALLY_DONE` 且出现在 `field.history`、`NOT_EXECUTED` 重试一次后成功 / 耗尽转 FAILED。
10. 测试（红线：回执 / 补偿也属下发路径，必须有应失败用例）：签名错误 / 过期时间窗 / 跨农场 / 反查不到 / 重放 / STALE / LATE / CONFLICT 表驱动；超时扫描不转 FAILED、不重发；对账与中止的权限拒绝；集成测试：`uk_receipt` 重放、回执与 Transition 同事务回滚、超时扫描多实例互斥。
