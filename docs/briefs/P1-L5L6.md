## L5（红线：审批闸门与路由、权限矩阵）：风险矩阵、二人确认守卫、驳回原因、时效与即将过期、通知通道、审批页数据、导出 —— §6.6 功能任务 1-7；技术实现第 1-6 条
文件归属：`migrations/0010_approval_l5.*`、`policy/risk_matrix.yaml` 与 `internal/agent/harness/policy/risk.go`（加载 / 校验 / 判定）、`internal/service/approval.go`（开票定级、Activate 通知）、`internal/service/decision.go` 与 `internal/repository/decision.go`（驳回原因、生效守卫）、`internal/controller/decision.go` 及新的 `controller/rejection.go`、`internal/service/scan.go`（新增 `approval_expiring`）、`internal/repository/rediskey`（`lock:scan:approval_expiring`）、新的 `service/notify.go`（替换占位处理器）与 `configs/texts/notify.zh-CN.yaml`、`policy/permission_matrix.yaml` 与 L1 权限登记（`rejection.export`）、`internal/evalkit/approver/*`、`cmd/eval/question.go`、新打分器文件、`eval/suites/` 下审批样本。
1. 风险矩阵（技术实现第 1 条）：`risk_matrix.yaml` 升 v2，把「SPRAY 一律 HIGH」换成规则：`PESTICIDE`（用药类，即 SPRAY）、`LARGE_AREA`（面积阈值可配）、`NEAR_THRESHOLD:{metric}`（PRE_APPROVAL `constraint_checks[]` 通过但离阈值在可配裕度内）任一命中 → `HIGH` + `confirm_required`；命中原因按出现顺序写 `approval_ticket.risk_reasons`（JSON 数组，取值见 §6.6 SQL 注释）。各档 TTL、可审批角色写在同一文件；用药类 `required_role` 固定含 `agronomist`（加载校验，缺则启动失败）；未列出的作业类型仍开票失败。裕度、面积阈值是草拟值，yaml 注释写「待业务确认」。Reopen 新票沿用旧票定级的现有行为不变。
2. 审批路由与拒绝（功能任务 1、验收 1、3）：P0 校验顺序与错误码不变（`TICKET_CLOSED / TICKET_EXPIRED / SNAPSHOT_STALE / ROLE_INSUFFICIENT / SAME_APPROVER`），每步失败写审计。核对：用药类非 agronomist → `ROLE_INSUFFICIENT`；审批人 = 发起人 → 拒绝；`HIGH` 第一人 `APPROVE` 只记 `first_approver_id`、票仍 `OPEN`；第二人 `CONFIRM` 时生效 UPDATE 追加 `first_approver_id IS NOT NULL AND first_approver_id <> ?` 守卫（§6.6 SQL 照抄，影响行数 0 按现有冲突处理）。生效事务、`dispatch_deadline_at`、`outbox(order.dispatch:…:1)` 沿用 P0 / L4。
3. 驳回原因（功能任务 5、验收 4）：`REJECT` 请求 `reason_code` 必填（`DOSAGE / TIMING / PRODUCT / EVIDENCE / OTHER`），`OTHER` 时 `reason_text` 必填（≤512）；缺失 / 非法 → 400 + 审计，票据与工单不变。在 P0 驳回事务内 `INSERT rejection_reason`（`advice_id`、`run_id` 从工单取，`operator_role` 取本次校验通过的角色）。`idem:approve` 重复点击行为不变。
4. 驳回导出（技术实现第 6 条）：`GET /api/v1/farms/{farm_id}/rejections?from=&to=` 返回 CSV（SQL 照抄）；`from/to` 必填，跨度上限可配（默认 31 天），超限 400；权限 `rejection.export` 只给 `farm_manager / agronomist / auditor`，登记进 L1 权限矩阵与 archtest 路由权限表。CSV 列名用英文字段名，`reason_text` 做 CSV 转义（防公式注入：以 `= + - @` 开头的前置 `'`）。
5. 时效与即将过期（功能任务 3、技术实现第 5 条、验收 2）：P0 `approval_expire` 已在 worker，核对两类过期（`PENDING_APPROVAL` 过 `expires_at`、`APPROVED` 过 `dispatch_deadline_at`）都转 `EXPIRED`，下发器 ① 自查时效。新增 worker 任务 `approval_expiring`（`lock:scan:approval_expiring` 60s，`SystemScope`，SQL 照抄）：命中的 `OPEN` 票写 `notify.send(EXPIRING_SOON)`，`dedup_key` 保证每张票只提醒一次。
6. 通知（功能任务 6、技术实现第 1 条）：`Activate` 同事务写 `notify.send(PENDING_APPROVAL)`；处理器替换占位（见接缝 4）：接收人 = `PENDING_APPROVAL / EXPIRING_SOON` 取本农场 `required_role` 内用户（排除发起人）；`RECHECK_RETURNED` 取发起人 + `required_role`；`DEVICE_OFFLINE` 取本农场 `farm_manager` + 发起人。无接收人 → 审计 `result=FAILED` + Warn，消息置 DONE（不空转）。通道投递失败返回错误走 outbox 退避。文案从 `notify.zh-CN.yaml` 取，缺 key 启动失败。
7. 审批页数据（功能任务 4、技术实现第 1 条）：待审批详情 API 返回完整快照、高亮字段（药剂、用量、时间窗）、与同地块上一张同类 `REAL` 工单（DONE / PARTIALLY_DONE，可复用 `repository/localorder.go`）的字段差异、PRE_APPROVAL 与最近一次 PRE_DISPATCH 的 `constraint_checks[]`；差异也进快照并参与 `snapshot_digest`（`RawStore.Put` 先于事务，顺序不变）。没有上一张同类单时差异为空并注明。amis 片段见「已定决策」。
8. 评测（功能任务 7、验收 2）：新增 `expired` 打分器（`FrozenClock.Advance()` 越过时效后作业单 `EXPIRED`、设备调用计数 = 0、下发被拒有审计）；脚本审批人加「非授权角色审批」行为（声明以哪个角色 / 用户审批，期望 `ROLE_INSUFFICIENT` 或 `SAME_APPROVER`）；`approve_after` 已有则核对；样本：用药类非农艺师审批、审批超时 EXPIRED、已批未下发超时 EXPIRED、HIGH 单只一人通过不 APPROVED、第二人同第一人被拒、驳回缺原因被拒、LARGE_AREA / NEAR_THRESHOLD 定级（看 `risk_reasons`）。`samples_hash` 会变，回报里写新样本数。
9. 测试（红线，必须有应失败用例）：风险矩阵加载校验（用药类缺 agronomist、HIGH 无 confirm、未知作业类型）与判定表驱动（三种原因单独 / 组合 / 都不中）；生效守卫（first_approver 为空 / 等于本人时 UPDATE 影响 0 行，不 APPROVED）；驳回缺 reason_code / OTHER 缺文本；导出权限拒绝（operator、跨农场）与时间跨度超限；即将过期扫描只提醒一次、多实例互斥；通知处理器四种 kind + 未知 kind + 无接收人。集成测试：`0010` 迁移下的驳回入库与导出 SQL、生效守卫、`approval_expiring` 扫描。
10. 验收 §6.6 第 1-4 条逐条回报；第 5 条标「待签字」并附 amis 片段。

## L6（红线：下发路径、无依据建议）：故障矩阵、文案表、LLM 降级、MCP 缓存回落、设备离线、降级事件、故障样本 —— §6.7 功能任务 1-5；技术实现第 1-5 条
文件归属：`policy/fault_matrix.yaml`（新）与加载 / 启动校验（新文件，如 `internal/agent/harness/policy/fault.go`）、`configs/texts/zh-CN.yaml`（新）与加载器、`internal/agent/graph/*`（降级分支、规则层模板、拒答文案取表）、`internal/agent/harness/*`（降级事件与审计，只记不判）、`internal/agent/llm/*`（不可用判定）、`internal/agent/tools/mcp/{call,finish,gateway}.go`（超时回落、`max_staleness`、`source='cache'`）、`configs/tools.yaml` 的缓存段、`internal/service/{outbox,dispatch_device,workorder_dispatch}.go` 中设备离线分支、`model/audit.go` 投影表加 `DEGRADED`、`internal/evalkit/env/fixturemcp.go` 与模型桩的故障注入、新打分器文件、`eval/suites/` 下故障样本。
1. 故障矩阵与文案（技术实现第 1 条、功能任务 2）：`fault_matrix.yaml` 声明 `LLM_UNAVAILABLE / MCP_TIMEOUT / KB_MISS / DEVICE_OFFLINE` 各自的错误码 → 行为 → 文案 key → 告警项（告警项先只是名字 + 级别，L7 接告警规则）。启动时（`app.Build` 或其加载入口）校验：四个码齐全、每个都有 `zh-CN.yaml` 文案与告警项，缺一项启动失败（`cmd/server`、`cmd/worker`、`cmd/eval` 共用）。与 L2 MCP 错误码归一：`TIMEOUT` 与 `UPSTREAM`（手册写作 `UPSTREAM_UNAVAILABLE`，以代码现有 `mcp.ErrUpstream` 为准，不改名）都归 `MCP_TIMEOUT`。现有 `graph/assemble.go` 的拒答文案只把故障相关的改为取表，其余不搬（不做无关重构）。
2. LLM 不可用（技术实现第 2 条）：`agent/llm` 按 `configs/model.yaml` 重试 1 次仍失败即判不可用（区分超时 / 5xx / 连接错误与内容不合规：后者不算不可用）。建议图选择 / 解释节点失败后，`agent/graph` 降级分支判断「知识已命中且含规则建议 + 候选非空」，满足走规则层模板（数值仍由 `calc` 算，引用照常带 `Citation`），`degraded=true`；不满足 → `REFUSED`，文案取 `LLM_UNAVAILABLE`。输出校验（validate 节点）照常执行，降级输出不能绕过。`harness` 只记 `DEGRADED` 事件与审计。
3. MCP 超时回落（技术实现第 3 条、功能任务 3）：超时或 `UPSTREAM` 时 gateway 读 `cache:mcp:{tool}:{farm_id}:{args_digest}`，`now - collected_at ≤ max_staleness`（按工具配置：天气 1h、作物 24h；正常读的新鲜期不变，天气 10min）才用；写缓存的 TTL 改为该工具的 `max_staleness`，正常读仍只认新鲜期内的值。回落时 `tool_call.source='cache'`（现有 `source` 字段存上游来源，核对取值不冲突）、`Citation.collected_at` 带原采集时间、写 `DEGRADED(fault=MCP_TIMEOUT, action=CACHE_FALLBACK, staleness_sec)`。超限 / 无缓存按「数据缺失」拒答（`kb_miss_refuse` 覆盖缓存过期）。`device.*` 不缓存；`bypassCache()` 覆盖的调用（epoch>0 的时效调用、`pre_dispatch` 复检）不回落，超时即按复检不通过 / 数据缺失处理。
4. 设备离线（技术实现第 4 条，L4-A 下发器第 ③ 步）：现状是 `ErrDeviceUnavailable` → `DEVICE_UNAVAILABLE` 审计 + 推后 5s（`outboxDeferDelay`，与拿不到 `lock:order` 共用）。改为：设备离线 / 选不到时不调 Adapter、工单状态不变，同一事务 `NotifyOutboxWriter.InsertTx(model.NotifyDedupKey(DEVICE_OFFLINE, order, ticket))` 只通知一次；本条消息按 §6.7 SQL 照抄推后 1 分钟（`last_error='DEVICE_OFFLINE'`、不计 `attempts`、带 `row_ver` 租约条件，影响行数 0 即租约已丢不再写结果）。拿不到 `lock:order` 仍推后 5s，不要合并两种推后。L4 的等待上限逻辑保留：过 `dispatch_deadline_at`（无时效时超 `dispatch.device_wait_max`）首次单 → `EXPIRED`、重试单 → `FAILED`。工具传输层错误仍按基础设施故障退避，不算离线。写 `DEGRADED(fault=DEVICE_OFFLINE)` 事件需要 run_id，从 payload 取。
5. 降级事件（技术实现第 5 条、功能任务 4）：所有降级经 `EventStore.AppendTx` 写 `run_event(event_type='DEGRADED', actor='system')`，payload 按 §6.7 SQL 的 `fault / action / staleness_sec`；`model/audit.go` 投影表加 `DEGRADED`（审计动作名自定并登记），同事务写审计。建议卡已有 `degraded` 字段，核对降级路径都置位。
6. 评测（功能任务 5、验收 4）：`FixtureMCP` 按工具声明故障（超时 / UPSTREAM / 返回指定采集时间的缓存）；模型桩声明不可用（每次调用返回错误）；设备离线用 DRY_RUN 单（L4 也给 DRY_RUN 绑定设备）声明设备工具全部离线，`FrozenClock.Advance()` 越过时效后断言 `EXPIRED`、设备调用 = 0、`DEVICE_OFFLINE` 通知入 outbox 恰 1 条。四类故障每类至少一条，另加：MCP 缓存在 `max_staleness` 内回落成功（`source='cache'`、`collected_at` 为原值）、超限拒答、LLM 不可用但不满足规则层条件 → REFUSED。新增 `degraded_matrix` 打分器（结局与矩阵一致、`DEGRADED` 事件存在、文案 key 正确），故障样本标红线，要求 n=5 下 pass^5 = 1。
7. 测试（红线，必须有应失败用例）：矩阵加载缺码 / 缺文案 / 缺告警启动失败；LLM 降级条件表驱动（知识未命中 / 无规则建议 / 候选空 → REFUSED，降级输出不过校验时仍被拦）；缓存回落边界（= `max_staleness` 可用、超 1s 拒答、`device.*` 与 `bypassCache` 不回落）；设备离线：不调 Adapter、通知只入一次（重复处理两次仍 1 条）、推后 1 分钟不计 attempts、租约丢失不写、拿锁失败仍 5s、等待超限转 EXPIRED。集成测试：设备离线推后 SQL 与通知去重、`DEGRADED` 事件与审计同事务。
