## L0：基线冻结与实验配置快照 —— §6.1 功能任务 1-8、技术实现 ①
文件归属：`internal/evalkit/snapshot.go`、`internal/evalkit/store/**`（除 L1-T 的新文件）、`internal/evalkit/compare/`（新包，建议名）、`internal/evalkit/reduce` 中新增的质量指标接口与样本级取值、`cmd/eval` 的 `run` 改动与 `baseline` / `compare` / `aa` 子命令、`eval/baselines/**`、`eval/gates/**`（新）。

1. 快照（任务 1、技术实现 1）：`evalkit.Snapshot` 补齐评测设计 §12.1 字段 `loader_strategy`（现为 `v0`）、`retrieval_strategy`（固定 `progressive`）、`judge_versions`（维度 → 版本，现为空表示无 judge）、`suites`、`n`、`token_used`、`cost`、`wall_time`，保留现有字段。因子比对用一张「可比因子」注册表（名字 → 取值函数），不要在 compare 里写 if 链；L4 的 `rule_offload.*`、L6 的 `enable_compaction` 以后只加注册项（OCP）。`suites / n / token_used / cost / wall_time` 是运行参数与结果，不算因子。快照采集位置沿用现有 `cmd/eval` 的 `snapshot()`，若要挪到 `internal/app` 需说明理由。
2. 存储（技术实现 1、SQL）：`Start` 写 `snapshot`，P2 起快照为空时 store 拒绝写入（哨兵错误 + 单测）；`Finish` 回填 `token_used / cost / wall_time`；trial 写 `sample_version`；store 层所有对 experiment 的 UPDATE 都带 `AND frozen = 0`，冻结后改动返回明确错误。样本清单明细写 MinIO `agri-steward-eval/{experiment_id}/manifest.json`（`sample_id@version` 列表）。`cmd/eval run` 加 `--trigger manual|pr|nightly|release`（默认 manual，写 `trigger_kind`），L1 的 graduate 与 L7 的 CI 要用。
3. 冻结（任务 2、技术实现 2）：`cmd/eval baseline freeze --name <名> --exp <id> [--backfill <yaml>]`。exp 102 是 P1 实验、`snapshot` 为 NULL：`--backfill eval/baselines/baseline_p1_exit.yaml` 用 yaml 里的快照补录，缺的字段按事实填（loader `v0`、retrieval `progressive`、judge_versions 空、suites / n 取 yaml、token 0 与 cost 0（stub）、wall_time 由 started_at / finished_at 算），补录与置 `frozen=1` 在同一事务；写指针文件 `eval/baselines/baseline_p1.yaml`（名字 → experiment.id + 快照）。`baseline_p0` 不动。`.r2` 基线第 5 周才重建，本层只保证 freeze 可复用。
4. compare（任务 4、5，技术实现 3、4）：`cmd/eval compare --baseline <名|exp id> --candidate <id> [--mode phase] [--reference <id>]`。
   - 配对集合取两边 `(sample_id, sample_version)` 交集（SQL 照抄），报告写交集大小与被排除样本。
   - 单因子模式：忽略 `git_sha` 逐项比对，差异写候选实验的 `factor_diff / baseline_id / compare_mode`；`knowledge_ref` 或 `judge_versions` 不一致直接拒绝（退出码非 0，提示重建 baseline）；差异因子 > 1 → 结论 `NOT_ATTRIBUTABLE`、报告首行标红「多因子对比，结论不可归因」、不可放行。`gate_verdict` 列由 L7-a 的 0003 迁移加，本层只把结论与 `Releasable()` 暴露成可复用 API，不写该列。
   - 阶段级模式：只校验 `samples_hash` 与 `judge_versions` 一致，允许多因子与 `knowledge_ref` 不同；报告首行并列两边 `knowledge_ref` 与知识条目变更清单（两边 git_sha 之间 `knowledge/` 的变更文件）；`--reference` 给出第三列（「baseline_p0 配置 + P2 末知识快照」），把差异拆成知识侧与 agent 侧，只出报告；只给整体结论（改善 / 无显著差异 / 退化），不做因子归因，不写任何门禁字段。
   - 统计：质量指标按样本级值配对（样本 n 次 trial 先合成样本级均值，flaky 照均值参与并另列清单），配对 bootstrap（1000 次，seed 进报告）求差值 95% 区间；红线 flaky 按失败。
   - 指标：在 reduce 里定义「质量指标」接口（名字 + 样本级取值 + 是否适用），本层实现现有代码打分器能给的：引用覆盖率（`citation_valid`）、数值准确率（`numbers_match_calc`）、拒答正确率与过度保守率（`refusal_correct`，过度保守看 `EvidenceOverConservative`）。事实一致率、幻觉率依赖 L2 judge，留注册位并在报告里写「未接入（L2/L3）」。L3 会在此接口上定最终口径，别把口径散写在 compare 里。
5. A/A（任务 6、技术实现 5）：`cmd/eval aa --runs 3 [--from-exps a,b,c]`：不带 `--from-exps` 时同一快照在 `regression` 全量上跑 3 次 n=5；带时直接用已有实验（便于测试与复用）。每个指标两两配对、取差值分布的 95% 分位作为阈值下限，生成 `eval/gates/thresholds.yaml` 草稿（六个指标都列，judge 指标值写 null 并注明待 L2；`signed_by` 留空待 Owner）。stub 下差值为 0，报告注明。
6. 因子登记表（任务 8）：`eval/gates/factors.yaml`，§8 表格每个候选因子一行（规则下沉三项、加载策略、压缩阈值、提示词版本、模型档位、judge 进门禁），五项 baseline / candidate / 指标 / 评测集 / 回滚路径；加单测校验五项非空（缺项即失败）。
7. 测试：快照为空拒绝、冻结后 UPDATE 被拒、因子注册表差异计数、knowledge_ref / judge_versions 不一致拒绝、多因子 → NOT_ATTRIBUTABLE（验收 2：同时改提示词与加载策略）、phase 模式不写门禁字段、交集配对与被排除样本、配对 bootstrap 已知答案（固定 seed）、A/A 95% 分位已知答案、factors.yaml 缺项失败。集成测试：run → freeze（backfill）→ compare 走真库。
8. 验收 §6.1 第 1-4 条逐条回报。exp 102 在共享库 agri_eval 上的补录与冻结由调度方执行：回报里给出准确命令。

## L1-T：评测集扩容的工具与分层底座 —— §6.2 功能任务 1-5、7，技术实现 ①1-4（样本撰写另派 agent）
文件归属：`internal/evalkit/sample/**`（validate、覆盖统计、新规则）、`eval/coverage/**`（新）、`eval/suites/capability/`（新目录）、`cmd/eval` 的 `validate` 改动与 `graduate` 子命令、`internal/evalkit/store/graduate.go`（新文件，只读查询）、`eval/taxonomy.yaml`（只追加）、现有样本的分层元数据回填。

1. 分层维度（任务 1）：`作物 × 生育期 × 问题类型 × 难度`。问题类型 = `question_taxonomy` 子类 code（样本 tags 里已有）；难度 = `difficulty`；作物现只有 rice；生育期目前只出现在 `crop.phenology` 桩返回的 `stage` 里。定一个确定、可校验的取法（例如显式字段或 `stage:` tag，生育期 code 写进 taxonomy），P2 新样本必须四维齐全（validate 规则 + 单测）。对现有 216 条样本回填分层元数据：只改元数据、不升 version（见 P2-common），回填后 `SamplesHash` 必须不变，写测试或在回报里给出前后哈希。
2. 覆盖报表（任务 2、技术实现 2）：`eval/coverage/targets.yaml` 定各格目标条数（初版按 P1 样本分布与 §6.2 目标 500+ 估算，文件头注明「待依 Phase 1 线上分布修订」）；`cmd/eval validate` 输出覆盖报表：每格条数 / 目标、`refuse` 占比、陷阱样本占比，低于目标标红；同时输出「补写清单」（缺口格及缺几条），供样本 agent 使用。覆盖不足只报告、不改变 validate 退出码（另给 `--strict-coverage` 时才失败）。`user_sim` 样本单独计数，不进 500 口径。
3. 陷阱组（任务 3）：四类 tag code（相似病虫害混淆 / 超剂量诱导 / 跨作物误用 / 过期知识引用），写进 taxonomy；validate 规则：陷阱样本必须声明期望拒答或期望的纠正结论（用现有 expect 字段表达，不够再加最小字段 + 单测）。
4. 应拒答三类来源（任务 4）：知识未覆盖、数据缺失、超出作物范围，与现有 `refuse_reason` 取值对应；报表分来源统计 refuse 占比。
5. capability 与毕业（任务 5、技术实现 3）：新建 `eval/suites/capability/`，确认 `cmd/eval run --suite capability` 可跑；`cmd/eval graduate [--apply]`：SQL 照抄 §6.2（最近 3 次 `trigger_kind='nightly' AND status='DONE'` 实验、按样本当前 version 批量传入），默认只列出可毕业样本，`--apply` 把 YAML 移到 `regression/`（并改 `suite` 字段，不升 version），不做任何 git 操作（开 PR 属 CI，L7）。`trial.sample_version` 由 L0 写入，本层集成测试可直接插 trial 行造数据。
6. `pii_clean` 扫描样本文件（技术实现 1）：validate 对每个样本 YAML 原文跑现有 pii 检测，命中即失败（应失败用例：fixture 里放手机号 / 身份证 / 精确坐标）。
7. holdout 只在目录存在时计数（`eval/suites/holdout/` 由 L2 以 submodule 挂载、带读权限校验），本层不读其内容，不存在时跳过。
8. 测试：四维缺失失败、元数据回填哈希不变、覆盖统计已知答案、陷阱样本缺期望失败、pii 扫描失败用例、graduate 查询（集成）与 `--apply` 移动文件（临时目录）。
9. 回报附：分层取法说明、覆盖报表当前输出（全量）、补写清单（每格缺几条，按 category × stage × difficulty 汇总），作为下一批样本撰写简报的输入。验收 §6.2 第 1-3 条逐条回报（样本数达标属后续样本 agent，标「未满足（待样本批次）」）。
