## 共同规则

1. 合入顺序（§7.2-3）：L4 / L5 / L6 的 candidate 一律「开关关闭」合入。合入前在开关全关下：
   - 默认行为逐字节不变；`make eval` 报告除时间外不变；快照 `samples_hash` 不变；
   - 回归与红线全绿。
   「开关打开」的对比报告单独提，不在本批合入灰度。
2. 一个因子一个开关（§7.2-2）。开关与快照 / 对比因子的对应已在接缝里登记（见下表），不要再加因子名：
   - `rule_offload.operation_window` / `rule_offload.tank_mix` / `rule_offload.pest_priority`：三态 `{"mode":"off|shadow|on"}`，因子名即开关名；
   - `enable_loader_v1`：布尔，因子体现为 `loader_strategy`（v0 / v1）；
   - `enable_compaction`：布尔，因子名即开关名。
3. 评测打开开关：`cmd/eval run ... --flags rule_offload.tank_mix=shadow,enable_compaction=on`。开关以 FARM 行写进评测种子，整个实验不变；快照记录 `flags`，`resume` 按快照里的 flags 重放；`compare` 把未记录的开关视为 off，所以 `baseline_p1` 仍可比。
4. 开关只经 `agent.FlagModeOf` / `agent.FlagOn` 读（`graph.Config.Flags`，可空）。读失败、Reader 为空、取值非法一律按 off（失败关闭），只记日志，不让 run 失败。
5. 红线代码（`output_validator` 拒收规则、`calc` 下沉项、`compaction` 白名单断言）先写应失败测试，再写实现；拒收规则合入即常开，不受任何开关与农场覆盖影响（母文档 §4.6.2-10）。
6. 不改 `knowledge/` 内容（`knowledge_ref` 是 Pinned 因子，一改就要重建 baseline）。确需改知识条目，单独提交并在回报里写明，调度方决定是否重建 baseline。
7. 新增代码打分器或红线样本会改报告与 `samples_hash`，与第 1 条冲突。这类改动放单独的「评测资产」提交，回报里分开写：
   - 第 1 条的「不变」在评测资产提交之前的那个提交上验证；
   - 新红线打分器必须补红线样本，并补进 `eval/smoke/smoke.yaml`，否则 L7-a 的冒烟覆盖测试会失败（每个红线打分器至少 2 条）。
8. 分层：controller / service / repository / model + agent/。生产代码不 import evalkit；注入 Clock；DB 只经 repository；定版 SQL 用 GORM 原生 Exec / Raw；配置用 Viper；日志用 slog；err 必查并用 `%w` 包装。
9. 不改 `.gitignore`；不提交 `migrations/`、`eval/out/`、`web/amis/**/*.json`；不 push，不动 main；不改 `eval/suites/holdout`。
